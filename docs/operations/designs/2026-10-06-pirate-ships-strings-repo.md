# Pirate Ships: репозиторий строк вместо копий файлов в ветках

**Статус:** предложение, 2026-10-06. Решают команда игры (схема и раскладка
в Unity) и администратор (где хостить репозиторий). Текущий план до решения
не меняется.

Связанные документы:

- `docs/operations/plans/2026-10-06-pirate-ships-weblate-branch-workflow.md` -
  текущий план (модель API-first);
- `docs/product/guides/game-repo-integration-contract.md` - плейбук
  интеграции.

## Коротко

- **Рекомендация:** отдельный маленький Git-репозиторий только со строками
  (`Localization_*.json` и их `.meta`). Пишет в него только Weblate. Игра
  подключает его как git submodule, и каждая ветка игры хранит не копию
  файлов, а ссылку на версию строк.
- Это официальная схема Weblate, а не обходной путь. FAQ `faq-submodule`
  описывает отдельный репозиторий переводов как submodule. Раздел
  `docs/admin/continuous.rst` для монолингвальных форматов советует
  добавлять новые строки в Weblate и оставить ему всю правку файлов.
- **Что уходит:** `pull-from-weblate`, правило «pull перед слиянием»,
  снимок в ветку `localization`, текстовые конфликты JSON при слиянии
  веток. Старая ветка больше не может вернуть старый текст.
- **Что остаётся:** скиллы «добавь ключ», «обнови исходник», «обнови
  перевод», `delete-key` через API без изменений. У ключа по-прежнему один
  текст для всех веток, поэтому правило `<key>_v2` для экспериментов
  остаётся.
- **Два этапа.** Этап 1 делаем мы с администратором: Weblate получает
  настоящий Git-репозиторий с историей. Он заменяет шаг 3 «Шагов с нашей
  стороны» (снимок в `localization`), от команды ничего не нужно. Этап 2
  делает команда: один коммит в `master` (файлы -> submodule), слияние
  `master` в живые ветки, вместо `pull-from-weblate` одна git-команда.

## Зачем менять текущую схему

Модель API-first из текущего плана рабочая, но держится на дисциплине и на
своём коде:

1. Файлы `Localization_*.json` лежат копией в каждой ветке игры. Их
   обновляет свой скилл `pull-from-weblate` (ZIP, фильтр ключей, табы,
   имена `cn`/`jp`/`kr`/`pt`).
2. При слиянии веток Git сливает JSON как текст. Ветка со старой копией
   возвращает старый текст, если её не обновили перед слиянием (правило 4
   плана; так было с «Картечница» -> «Мортира»).
3. Технически ничто не мешает поправить файл в ветке руками. Именно так
   Weblate и игра разошлись.
4. У компонента нет Git (`vcs=local`): нет внешней истории и резервной
   копии. Для снимка в `localization` подключение к Git всё равно нужно.

Модель API-first выбрали потому, что SCM-Manager 1.x не отдаёт клон
`master`. На маленький отдельный репозиторий это ограничение не действует.

Больше частей ради того же, что делает submodule |

**Опыт сообщества.** Godot держит переводы в отдельных репозиториях
(`godot-editor-l10n`, `godot-docs-l10n`), но в движок переносит их копией:
мейнтейнер вручную делает коммиты «Sync translations with Weblate». Это наш
вариант A, только в одну ветку. Связку «отдельный репозиторий плюс
submodule» описывает сам Weblate в FAQ, жалоб на неё в трекере Weblate не
нашлось. Неудобства submodule - общие для Git (Pro Git): detached HEAD,
`git pull` не обновляет содержимое submodule, после переключения веток он
отмечен изменённым. Для репозитория, который люди только читают, их снимает
настройка `submodule.recurse=true`.

## Рекомендуемая схема (D)

### Как устроено

```text
          Weblate, компонент pirate-ships/localization-json (Git)
            ^  API: добавь ключ, обнови исходник и перевод, удали
            |  интерфейс: переводчики, MT, судья
            v  push (пишет только Weblate)
     репозиторий строк, ветка main
       Localization_*.json + .meta, каждая правка - коммит с автором
            ^  ссылка на коммит (gitlink)
   +--------+---------+-----------+
 master  release/*  halloween  feature-X        <- ветки игры
```

- В репозитории строк только `Localization_*.json` и их `.meta`. Писать в
  него может только служебная учётка Weblate, разработчики и CI - только
  читать. Правило «тексты только через Weblate» становится правами
  доступа, а не договорённостью.
- В Weblate тот же компонент `pirate-ships/localization-json`. Адреса API
  в скиллах не меняются, история правок, флаги и комментарии сохраняются
  (этап 1).
- Ветка игры хранит ссылку на коммит репозитория строк. Чтобы обновить
  строки в ветке, ссылку сдвигают на свежий коммит и коммитят.

### Раскладка в Unity

Unity объединяет все папки `Resources`, поэтому submodule можно подключить
так, что путь загрузки не изменится:

```text
Assets/Localization/Resources/Data/      <- корень submodule
    Localization_ru.json
    Localization_ru.json.meta            GUID переносится из игры как есть
    ...
```

`Resources.Load("Data/Localization_ru")` найдёт файл и здесь, код загрузки
не меняется. `.meta` папок `Assets/Localization`,
`Assets/Localization/Resources` и `Data` лежат в репозитории игры, `.meta`
файлов - в репозитории строк с прежними GUID. Маска Weblate
`Localization_*.json` файлы `.meta` не затрагивает. Больше ничего в
репозитории строк держать нельзя: всё, что в нём лежит, попадает в
`Resources` и в сборку.

Уточнить у команды: грузит ли игра файлы только через `Resources` и не
читают ли редакторские скрипты и скиллы `Assets/Resources/Data/Localization_*.json`
по пути к файлу. Такие пути придётся поменять.

### Ежедневная работа

Ниже `<путь>` - `Assets/Localization/Resources/Data`.

| Ситуация | Что делать |
| --- | --- |
| Новый ключ в любой ветке | «Добавь ключ», как сейчас (API, MT на 15 языков), затем `git submodule update --remote <путь>` и коммит ссылки |
| Нужен свежий текст в ветке | `git submodule update --remote <путь>` и коммит |
| Правка RU существующего ключа | «Обнови исходник» или интерфейс Weblate. Ветки получат её при следующем обновлении ссылки |
| Правка перевода | «Обнови перевод» или интерфейс Weblate |
| В эксперименте нужен другой текст существующего ключа | Новый ключ `<key>_v2`, как в текущем плане: у ключа один текст для всех веток |
| Переименование, удаление | В Weblate (`/source/<id>/rename-key/`, `delete-key`), затем обновить ссылку |
| Слияние веток | Обычный `git merge`, ссылки сливаются сами (ниже) |
| Релиз | `POST /api/components/pirate-ships/localization-json/repository/` `{"operation": "push"}`, `update --remote` в релизной ветке, проверка полноты, сборка. Ссылка - точная версия строк в сборке |
| Хотфикс текста в выпущенной версии | Правка в Weblate, затем `update --remote` в ветке хотфикса. Вместе с ней придут и более новые тексты из main; чаще всего это и нужно, а исключения см. «Долгоживущие ветки» |
| Массовая загрузка RU (новое событие) | Загрузить файл в Weblate с добавлением новых строк или скилл через API. Коммит в репозиторий строк в обход Weblate - только под блокировкой по `docs/admin/continuous.rst`: lock, push, коммит, pull, unlock |

`push` через API сначала коммитит ожидающие правки
(`Component.do_push`), поэтому скиллу не нужно ждать `commit_pending_age`.

### Почему старая ветка больше не возвращает старый текст

В main репозитория строк пишет только Weblate, поэтому история линейная: из
двух ссылок одна всегда потомок другой. При слиянии веток Git сам сдвигает
ссылку на более новую («Fast-forwarding submodule»), если оба коммита есть
локально. Иначе он отмечает конфликт, и решение у него одно: взять более
новый коммит (`git submodule update --remote` после слияния). Если ветка
ссылку не трогала, остаётся ссылка `master`. JSON при этом не сливается
вообще.

Если ссылку всё-таки откатят назад, Weblate это не затронет: следующий
`update --remote` вернёт актуальный текст. В схеме A старый текст оставался
в файлах ветки, пока его не перезапишет `pull-from-weblate`.

Сдвиг ссылки делает локальный Git. Если ветки сливают на сервере, такое
слияние может показать конфликт, который локально решается сам: это стоит
проверить на SCM-Manager.

### Долгоживущие ветки

По умолчанию у всех веток игры один main репозитория строк. Ветка релиза
замораживает тексты сама: её ссылка стоит на месте, пока её не сдвинут.

Если ветке до слияния нужны свои тексты существующих ключей, официальный
способ - отдельный компонент Weblate на ветку репозитория строк с translation
propagation (`docs/faq.rst`, «How do I translate several branches at
once?»). Для событий Pirate Ships это не рекомендуем: каждое событие дало
бы дубли строк в Weblate, лишний MT и слияние JSON между ветками
репозитория строк. Правило `_v2` проще. Компонент на ветку стоит оставить
для редкого случая: долгая поддержка старой версии со своими переводами.

### Что меняется в правилах и скиллах

| Сейчас (план API-first) | В схеме D |
| --- | --- |
| Правило 1: новый ключ в любой ветке | Без изменений |
| Правило 2: эксперимент - `<key>_v2` | Без изменений |
| Правило 3: правка существующего текста из `master` или в Weblate | Без изменений: правка действует для всех веток |
| Правило 4: `pull-from-weblate` перед слиянием и релизом | Перед слиянием не нужно. Перед релизом - `update --remote` |
| Правило 5: переименование и удаление только в Weblate | Без изменений |
| Правило 6: `validate-localization` сравнивает файлы с Weblate | Проверяет, что ссылка указывает на последний коммит main, и полноту переводов в файлах submodule |
| `pull-from-weblate` | Удалить. Вместо него `push` через API, `git submodule update --remote <путь>` и коммит |
| «Добавь ключ», «обнови исходник», «обнови перевод», `delete-key` | Без изменений, в конце вместо `pull-from-weblate` - то же обновление ссылки |
| Снимок в ветку `localization` | Не нужен: история в репозитории строк |

Глоссарий в эту схему не входит. Он остаётся отдельным компонентом Weblate,
MT берёт термины оттуда. В репозиторий строк его класть нельзя: всё, что
там лежит, попадает в `Resources`.

### Где хостить репозиторий строк

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| SCM-Manager рядом с игрой | Всё в одном месте, те же учётки, для команды ничего нового | Нужен TLS на внешнем адресе (обратный прокси на `corp.herocraft.com`) или VPN с сервера Weblate. SCM-Manager 1.x без поддержки |
| Свой Forgejo или Gitea | Weblate поддерживает их вебхуки и push, HTTPS из коробки | Новый сервис, который надо обслуживать. Разработчикам нужны учётки |
| GitHub или GitLab, приватный репозиторий | Обслуживать нечего, полная поддержка в Weblate | Тексты неанонсированного контента у внешнего провайдера - решение политики компании |

Вебхуки в схеме D не нужны: в репозиторий строк пишет только Weblate, и
забирать ему оттуда нечего. Поэтому отсутствие вебхуков у SCM-Manager 1.x
не мешает, и если администратор даст TLS, естественный выбор - первый
вариант. TLS нужен в любом случае: без него не сделать и шаг 3 текущего
плана.

### Внедрение

**Этап 0. Решения** (одна встреча):

- команда: согласие на submodule, ответы про загрузку файлов (раскладка
  выше);
- администратор: где репозиторий, TLS, учётки. Служебная учётка пишет
  только в этот репозиторий, пароль `localization.service` перед этим
  меняется. Разработчики и CI только читают.

**Этап 1. Мы и администратор, команда не участвует.**

1. Репетиция на dev. Берём копию компонента с `vcs=local`, переносим его
   историю в пустой репозиторий, сверху коммитим `.meta`, переключаем
   компонент на Git на месте. По коду Weblate существующий каталог
   репозитория сохраняется (`sync_git_repo` клонирует, только если
   репозитория нет), а `configure_remote` добавляет `origin`. Проверить:
   - число юнитов, состояния, флаги, пояснения, комментарии и история не
     изменились;
   - правка в Weblate приходит коммитом в репозиторий;
   - переименование и удаление ключа приходят так же;
   - в тестовом репозитории «игры» с submodule две ветки сдвигают ссылку,
     и слияние проходит без конфликта.
2. Администратор создаёт репозиторий и даёт HTTPS. С сервера Weblate
   проверяем `git ls-remote`.
3. Перенос на production, с отдельным разрешением:
   - блокируем компонент и пушим ожидающие правки;
   - переносим историю Weblate в новый репозиторий через git-экспорт, хеши
     коммитов сохраняются;
   - коммитим `.meta` из `master` игры;
   - переключаем компонент: `vcs=git`, адрес репозитория и push, ветка
     `main`, `push_on_commit=True`, `commit_pending_age=1`. Weblate видит
     свою историю плюс один коммит, это fast-forward, файлы те же;
   - снимаем блокировку.
4. Итог: у Weblate настоящий Git, каждая правка - коммит с автором, есть
   внешняя резервная копия. Ветка `localization` и снимок в неё больше не
   нужны.

**Этап 2. Команда**, после этапа 1:

1. Один коммит в `master`: удалить `Assets/Resources/Data/Localization_*.json`
   и их `.meta`, добавить submodule `Assets/Localization/Resources/Data` с
   `branch = main`, поправить пути в скриптах, если они есть.
2. Каждому разработчику один раз: `git config --global submodule.recurse
   true`. Сборка и CI: `git submodule update --init`.
3. Живые ветки: слить в них `master`. Если ветка меняла старые файлы, Git
   покажет конфликт «изменено/удалено». Решение - удалить файл: эти ключи
   уже в Weblate.
4. Скиллы: удалить `pull-from-weblate`, добавить «обнови локализацию»
   (`push` через API, `update --remote`, коммит), перевести
   `validate-localization` на проверку ссылки и полноты.
5. Совместный тест: новый ключ из ветки, правка перевода в Weblate,
   слияние двух веток с разными ссылками, сборка из чистого клона.

### Риски и откат

| Риск | Что делаем |
| --- | --- |
| Переключение компонента на месте теряет данные | Только после репетиции на dev и с резервной копией компонента. При сбое вернуть `vcs=local` |
| Сборка без строк: submodule не инициализирован | CI падает, если `git submodule status` начинается с `-` |
| Ветку собрали со старыми строками | Шаг релиза `update --remote`; `validate-localization` сверяет ссылку с `origin/main` |
| Weblate не может запушить (сеть) | Правки остаются в Weblate, он показывает предупреждение и дотолкает push после восстановления |
| Добавили язык, у файла нет `.meta` | Unity создаст `.meta` локально, а мы один раз добавим его в репозиторий строк (разработчики туда не пишут) |
| Схема не прижилась | Команда отменяет коммит с submodule: файлы возвращаются в `Assets/Resources/Data`, дальше снова `pull-from-weblate`. Weblate остаётся с Git, ему это не мешает |

### Если TLS затянется

Этап 2 можно начать раньше на варианте E: submodule указывает на git-экспорт
Weblate (`https://l10n.herocraft.com/git/pirate-ships/localization-json/`),
чтение по логину и API-токену Weblate. Когда репозиторий строк появится,
история перенесётся в него с теми же хешами, и команде останется
`git submodule set-url`. Цена моста:

- сборки зависят от доступности сервера переводов;
- каждому разработчику и CI нужен свой токен Weblate;
- `.meta` в репозиторий Weblate штатно не добавить, и Unity будет
  создавать их у каждого свои;
- API production сейчас отдаёт ссылки `http://` (в том числе адрес
  git-экспорта), настройку HTTPS сайта нужно проверить.

Поэтому по умолчанию мост не рекомендуем: ждать TLS дешевле, чем
переделывать.
