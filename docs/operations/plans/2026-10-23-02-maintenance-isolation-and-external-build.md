# Изоляция старого задания и внешняя сборка — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Разрешить обслуживание после проверяемой изоляции старого задания, сохранив историю и запрет повторной оплаты, и вынести сборку с переполненного production-сервера.

**Architecture:** Состояние `archived_unknown` и постоянная запись `run_isolation` отделяют запрет запуска задания от общего maintenance gate. Они не меняют результат внешней операции. Образ собирается на рабочей станции из чистого снимка, затем проходит отдельный контроль места и разрешение импорта/установки.

**Tech Stack:** Wizard: Python, SQLite, SQLAlchemy, React/TypeScript; Weblate: Django/PostgreSQL; сборка: WSL Ubuntu и Docker, `linux/amd64`.

**Spec:** `docs/operations/reports/2026-10-23-02-maintenance-isolation-and-build-investigation.md` и ограничения пользователя от 23 октября 2026.

## Review Focus

1. Старый API одновременно успел прочитать `unknown` перед архивированием: приложение выполняется только в отдельно разрешённом окне после прекращения всех старых писателей; CLI отказывает при живой аренде или изменённом снимке.
2. Статус ошибочно возвращён в `queued`, запись изоляции повреждена/удалена: отправка и maintenance проверка закрываются, а не открываются.
3. Новый пользователь или другое локальное имя ссылается на тот же remote project: запрет платных действий действует по remote slug независимо от owner/alias.
4. Откат к старому коду: сохраняются текущая БД и архивное состояние; API только чтения, оба воркера отключены и замаскированы.
5. На сервере независимо изменились образ, схема или занятость диска: план применения прерывается; старый допуск/список очистки повторно не используется.

## Задача 2. Реализовать постоянный запрет запуска и адресную изоляцию

**Создать в Wizard:** `backend/app/services/run_isolation.py`,
`backend/app/services/isolation_contract.py` (только стандартная библиотека),
`deploy/isolate_legacy_run.py`, `tests/test_run_isolation.py`.

**Изменить:** `backend/app/services/runs.py`, `backend/app/worker.py`,
`backend/app/services/quality_only.py`, `backend/app/services/quality_preflight.py`,
`backend/app/services/quality_cycle.py`, `backend/app/services/full_quality_cycle.py`
в тех входных точках, которые могут резервировать/отправлять платные операции.

**Интерфейсы:**

- `isolate_run(database: Path, run_id: str, expected_payload_sha256: str, backup_manifest: Path, reason: str, *, apply: bool = False) -> dict` — отдельная административная CLI, без импорта HTTP-клиента и без сети. По умолчанию только dry run.
- `validate_isolation_record(job: Mapping, record: Mapping) -> dict` — чистая проверка версии 1, ID, owner, local/remote project, idempotency key, payload SHA-256, архивного статуса и отсутствия аренды; некорректное значение вызывает `ValueError`. Используется CLI и preflight без SQLAlchemy/HTTP-зависимостей.
- `validated_isolation(session, job) -> dict | None` — ORM-адаптер чистой проверки; `None` только при отсутствии и записи, и архивного статуса, повреждение даёт отказ.
- `ensure_project_not_isolated(session, remote_slug: str, local_slug: str | None = None) -> None` — общий запрет новых платных действий, независимо от пользователя и локального alias.

Запись хранится в существующей `records`: ID `run-isolation:<job-id>`, kind
`run_isolation`, owner исходного задания. JSON сохраняет причину, время UTC,
идентичность оператора, исходный статус, контрольные идентификаторы, payload hash
и digest read-only сверки. Новая таблица/миграция для этого не требуется.
Поле `jobs.data`, intent, MT-ключи и idempotency key не меняются.
