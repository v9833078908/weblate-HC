# План: Need for Greed - смена исходного языка на русский

> **Для исполнителя:** REQUIRED SUB-SKILL: `superpowers:executing-plans`, фаза
> за фазой. Прод (`https://l10n.herocraft.com`, проект `need-for-greed`,
> id 7) трогается только начиная с Фазы 3, и только после явного «да» владельца
> на результат Фаз 0-2. До этого - только чтение.

Дата: 2026-09-02. Статус: одобрен владельцем, ожидает исполнения.

## Решение владельца

Исходный язык всех компонентов `need-for-greed` становится **русским** вместо
английского. Вчера (2026-09-01) разработчик добавил новые ключи с русским
текстом, и они легли в английский перевод; после переезда эти ключи должны
быть на русском в `ru` как источник. Заметки глоссария обязаны попасть в
контекст LLM (`weblate/machinery/llm.py:157` шлёт `source_explanation` /
`target_explanation` глоссария в промпт).

## Почему пересоздание, а не смена поля

`Component.clean()` (`weblate/trans/models/component.py:5530-5543`) запрещает
менять `source_language` у существующего компонента: «Source language can not
be changed, please recreate the component instead». Прецедент с обратной
сменой (`ru` -> `en`) выполнен и задокументирован в
`docs/operations/plans/2026-08-19-space-arena-source-language-to-english.md`;
этот план повторяет ту же схему (пересоздать рядом, перенести состояние из БД,
заархивировать старое, переименовать слаги), поэтому общие механики там не
дублируются - читать оба.

Установленные факты:

1. **Вчерашних русских ключей нет ни в ките, ни на проде - они удалены.**
   Проверено по журналу изменений прода (2026-09-02, токен в `.env.local`):
   2026-09-01 в 19:56 пользователь `matios_free` девять раз добавил в
   `orders` исходную строку (`en`) с русским текстом, и каждое добавление в ту
   же секунду сопровождалось «Строка удалена» (action 63) во всех 18 языках,
   затем «Обновление ресурсов: content changed en.po». Итог: ключей
   `orderTerrain2.2Step5HelpInfo`, `orderTerrain2.2Step6HelpInfo`,
   `orderTerrain2.3Step1HelpInfo` ... `orderTerrain2.3Step7HelpInfo` (9 штук)
   на проде нет (`q=context:HelpInfo` даёт 0), в ките их нет, а тексты
   сохранились только в `details.source` записей журнала. Они извлечены в
   `analysis/data/nfg-ru-source-2026-09-02/orders-lost-keys.json`
   (`{context: {text}}`). Кириллица в `en.po` кита - только два гомоглифа в
   `ui` (`Х2` в `dailyRewardClaimDescription`, `ADORЕ` в
   `terrainProgressInfoSlide2`), это не ключи.
2. **Заметок глоссария в TBX нет: все 302 `<descrip>` содержат только
   `[Section] key`**, ни одного `<note>`. При этом план
   `docs/operations/plans/2026-08-24-need-for-greed-glossary-safety.md` на
   проде через API дописал explanation к `Ancient Tome` (юнит 86469) - в
   TBX его нет. Причина: `PATCH /api/units/<id>/` пишет `explanation` прямо в
   БД (`weblate/api/views.py:3866-3874`, `unit.save(update_fields=...)`), не
   через `Unit.update_explanation`, поэтому `PendingUnitChange` не создаётся
   и файл TBX не обновляется. **Файловый экспорт глоссария не является
   источником истины по заметкам; истина - в БД.** Заметки надо снять через
   API и вписать в TBX перед импортом. (Сам дефект API - вне объёма, завести
   отдельно.)
3. Импорт кита через мастер `create/component/?project=7#zip`: один компонент
   на ZIP, base file `ru.po`, source language Russian. Проверка «Template
   language must match source language» (`component.py:5266`) пройдёт, потому
   что `ru.po` несёт `Language: ru`. Multilingual CSV не нужен.
4. Что переживает пересоздание файлами: текст всех 18 языков, `fuzzy`
   (needs editing). Что живёт только в БД и требует переноса: флаги
   исходных юнитов (`read-only`, `ignore-*`), снятые проверки, комментарии,
   предложения, метки, скриншоты, approved-состояния, explanations
   глоссария и исходных строк, история (не переносится).
5. Матчинг глоссария: `get_glossary_units` отбирает глоссарии по
   `component__source_language` переводимого компонента
   (`weblate/glossary/models.py`), поэтому глоссарий тоже обязан стать
   `ru`-источником, иначе он инертен.

## Фазы

### Фаза 0. Замер прода (только чтение)

Токен: `PROD_WEBLATE_API_TOKEN` лежит в `.env.local` в корне репозитория
(gitignored); экспортировать в окружение перед запуском, как в

1. `GET /api/projects/need-for-greed/components/` - список, `source_language`,

   `edit_template`, `allow_translation_propagation`, все поля, отличные от
   дефолта. Сохранить целиком - они повторяются на новых компонентах.
2. Найти вчерашние ключи: `GET /api/projects/need-for-greed/changes/?timestamp_after=2026-09-01T00:00:00Z`,
   действия «New source string» / «String added» / «String updated in the
   repository», плюс `GET .../units/?q=changed:>=2026-09-01 AND language:en AND target:r"[А-Яа-яЁё]"`
   по каждому компоненту. Зафиксировать список `(компонент, ключ, текст)`.

   у скольких терминов explanation отличается от шаблона `[Section] key`
   (это и есть заметки, которых нет в TBX). Отдельно посчитать омонимы при
   `ru`-источнике: разные английские термины с одинаковым русским текстом

   секцией, как в Space Arena, Фаза 3).
4. Для семи компонентов: флаги исходных юнитов (`extra_flags != ""`),

5. Записать матрицу «что переносим / сколько» в раздел «Результат Фазы 0»

### Фаза 2. Подготовка файлов (локально, без прода)

4. **Глоссарий.** Собрать 17 файлов `tbx/<lang>.tbx` заново из `phase0.json`

## Риски

- **Заметки глоссария теряются при любом файловом экспорте**, пока дефект API
  не исправлен. Поэтому TBX собирается из БД (Фаза 2.4), и после переезда
  любые правки explanation через API снова будут жить только в БД. Заводить
  отдельную задачу на `weblate/api/views.py:3866`.
- **Ре-база источник-зависимых проверок** - неизбежное следствие смены
  источника, не дефект метода.
- **Вчерашние ключи могут быть не закоммичены** до Фазы 1; скачивание кита
  их коммитит. Если разработчик правил через UI после 09:35, кит из
  `Downloads` устарел - использовать только кит Фазы 1.
- **Откат:** старые компоненты живут до Фазы 6; откат = удалить `-ru`.
