# Pirate Ships: работа с Weblate при многих ветках, скиллы, глоссарий, Git

**Статус:** предложение после встречи 2026-10-06, не согласовано с командой.
Заменяет схему с переносом из ветки `localization`
(`docs/operations/plans/2026-08-15-pirate-ships-production-cleanup-json-migration.md`,
раздел «Согласованная схема», и
`docs/operations/reports/2026-10-06-pirate-ships-git-integration-status.md`):
на встрече команда от неё отказалась.

Все данные получены только чтением: production API (88 134 изменения с
2026-08-10), 23 ветки `Tempest_f2p`, код форка. В production и в игровой
репозиторий ничего не записано.

## Что выяснилось

### Как команда работает на самом деле

- Много параллельных веток (фичи, эксперименты), потом слияние в `master`;
  релизные ветки `release/*` берутся из `master`.
- Скилл в любой ветке шлёт ключ и RU в Weblate API, запускает перевод по
  языкам, скачивает переводы и пишет локальные `Localization_*.json`.
  Ветку `localization` команда не использует.
- Шесть аккаунтов команды (Swift, AlEfremov, dudarev, kroer, PavelV, egnu)
  состоят в группе «Administration» проекта и правят RU прямо в Weblate:
  172 правки RU по 118 ключам, из них 108 у Swift.
- Интерфейс Weblate (проверки, статистика) никто не открывает.

### Откуда расхождения

| Причина | Доказательство |
| --- | --- |
| `validate-localization` всегда отправляет RU из локальных файлов в Weblate («for consistency») | Текст `SKILL.md`. Устаревшая ветка перетирает свежий RU и заново создаёт удалённые ключи |
| `migrate-legacy-localization` копирует строки прямо в файлы и переименовывает ключи в файлах | 155 ключей только в файлах, 274 `dialog_*` -> `dialogue_*` нигде в Weblate |
| «Обнови перевод <ключ> <текст>» пишет в RU | `GET /api/units/?q=key:...` возвращает юниты всех языков, RU первым; у скилла нет параметра языка. Так в RU попал английский: `daily39_description`, `cbp_use_amulet_battle`, `cbp_use_amulet_battle2` (Swift, 2026-09-14), `tw_item_name_building_portal` (2026-09-24) |
| Удаления только в файлах | Скилла удаления нет: Claude чистит JSON, Weblate не знает |
| Устаревшие ветки | 11 из 13 свежих веток несут одни и те же 37 устаревших `tutorial_hint_*` (без `<b>`, как было до правки в `master`) |
| Правки RU из экспериментальных веток уже в Weblate | 16 ключей Weblate держит со значением из ветки, а не из `master`; 13 из них из `2026-09-22_halloween` |

Weblate сам по себе тексты не откатывал: за два месяца 46 возвратов A->B->A,
из них 38 - повторный машинный перевод после того, как RU поменяли туда и
обратно. Случай «Картечница»: Swift переименовал пушку в «Мортира»
2026-09-11, Weblate, `master` и релизная ветка говорят «Мортира», а старое
название живёт в устаревших ветках и возвращается при их слиянии или при
отправке их RU в Weblate.

### Возможности API (код форка)

| Операция | Запрос | Оговорка |
| --- | --- | --- |
| Новый ключ | `POST /api/translations/pirate-ships/localization-json/ru/units/` `{"key": "...", "value": ["..."]}` | Только на RU; в другие языки ключ появляется сам |
| Правка RU | `PATCH /api/units/<id RU>/` `{"target": ["..."], "state": 20}` | Переводы уходят в «требует переписывания», их надо перевести заново |
| Правка одного языка | `GET /api/translations/pirate-ships/localization-json/<lang>/units/?q=key:="<key>"`, затем `PATCH /api/units/<id>/` | Искать в конкретном языке и точным `key:=`; `key:` без `=` ищет подстроку |
| Удаление ключа | `DELETE /api/units/<id RU>/` | Удаляет ключ во всех языках |
| Переименование ключа | Только интерфейс: исходная строка -> «Переименовать ключ» | REST нет; переводы и история сохраняются |
| Машинный перевод ключа | `POST /api/translations/pirate-ships/localization-json/<lang>/autotranslate/` с `q=key:="<key>"` | По одному вызову на язык; общего вызова на все языки нет |
| Порог | `threshold` | LLM-движок всегда отдаёт качество 90, порог на него не влияет. Порог 30 действует только на память переводов и пропускает слабые совпадения. Пустой результат LLM - это отказ проверки ответа, а не порог |
| Глоссарий | `GET /api/components/pirate-ships/glossary-ru/file/?format=zip:xlsx`, units API для правок | Выгрузка в файл теряет флаг `terminology`; `method=replace` при загрузке разрушителен |
| Git push | `POST /api/components/pirate-ships/localization-json/repository/` `{"operation": "push"}` | Только после подключения компонента к Git |

## Как работать с ветками

Weblate не умеет ветвить строки, как Crowdin или Lokalise: у него один
набор ключей на компонент. Поэтому правило держится на ключах, а не на
ветках. Ключ - неизменяемый идентификатор, у него один текст для всех
веток.

1. **Новый ключ в любой ветке - можно.** Скилл добавляет ключ в Weblate,
   переводит и пишет в файлы этой ветки. Если ветку бросят, в Weblate
   останется неиспользуемый ключ; вреда нет, его удалит чистка.
2. **Существующий текст в экспериментальной ветке не меняем.** Нужен
   другой текст для эксперимента - новый ключ (`<key>_v2` или по смыслу)
   и ссылка на него в коде этой ветки. Старый ключ и его текст в `master`
   не трогаются.
3. **Правка существующего текста (опечатка, переименование термина) -
   только из `master`** или прямо в Weblate. Она сразу действует для всех
   веток: это и есть «Weblate источник правды».
4. **Скилл никогда не отправляет RU из локального файла в Weblate.** Файлы
   ветки - копия Weblate, а не источник.
5. **Файлы ветки обновляются только скиллом `pull-from-weblate`:** берёт
   из Weblate текущие тексты для ключей этой ветки и перезаписывает
   `Localization_*.json`. Перед слиянием в `master` и перед сборкой
   релиза его запускают обязательно: так устаревшие ветки не возвращают
   старый текст («Картечница»).
6. **Переименование ключа** - в Weblate (интерфейс или через нас), затем
   `pull-from-weblate` и замена ключа в коде. Не в файлах.
7. **Удаление ключа** - когда он ушёл из `master` и ни одной живой ветки:
   `DELETE /api/units/<id>/`. Раз в релиз - чистка неиспользуемых ключей
   по списку от нас.
8. **Проверка перед релизом:** файлы релизной ветки совпадают с Weblate
   по всем её ключам, у каждого ключа с непустым RU есть перевод на все
   15 языков. Неполный перевод - блок или предупреждение, решает ГД.

## Как это выглядит на практике

Сейчас текст живёт в двух местах - в Weblate и в файлах каждой ветки, и
скиллы гоняют его в обе стороны (`validate-localization` отправляет RU из
файлов в Weblate). Поэтому старая ветка перетирает свежий текст. После
интеграции текст живёт только в Weblate, а файлы в любой ветке - копия,
которую скилл скачивает. Из файлов в Weblate ничего не уходит.

```
            ┌──────────── Weblate ────────────┐
            │  один текст на ключ для всех     │
            │  переводы, MT, судья, глоссарий  │
            └───▲──────────────┬───────────────┘
   добавь ключ │              │ pull-from-weblate
   (только API)│              ▼ (только скачать)
   ветка feature-A    ветка feature-B    master    release/*
   Localization_*.json - копии, в Weblate не отправляются
```

### 1. Новая фича в ветке, нужны новые строки

```
ветка feature-A
  "добавь ключ shop_new_title: Новый магазин"
    -> скилл: ключа нет в Weblate -> создать RU
    -> перевод EN -> перевод остальных 14
    -> pull-from-weblate: записать в файлы ЭТОЙ ветки
    -> человек коммитит в feature-A
```

Почти как сейчас. Скилл сначала проверяет, что ключа нет, а пустой перевод
- ошибка, а не `""`. Если ветку бросят, в Weblate останется неиспользуемый
ключ - вреда нет, его удалит чистка.

### 2. Опечатка или переименование термина в существующем тексте

```
master (или прямо в интерфейсе Weblate)
  "обнови исходник item_name_cannon_buckshot: Мортира"
    -> PATCH RU в Weblate -> перевод всех языков
    -> pull-from-weblate в master
```

Правка сразу действует для всех веток: каждая получит её при своём
следующем `pull-from-weblate`. «Обнови» делится на две команды: «обнови
исходник» (RU, только из `master`) и «обнови перевод <ключ> <язык>
<текст>» (один язык, RU не трогает).

### 3. Эксперимент: другой текст для существующего ключа

```
ветка experiment-B
  НЕЛЬЗЯ: менять текст ability_desc_fire (он общий для всех веток)
  НУЖНО:  "добавь ключ ability_desc_fire_v2: <новый текст>"
          + в коде этой ветки ссылаться на _v2
```

Эксперимент приняли - `_v2` приходит в `master` слиянием, старый ключ
удаляем. Бросили - `master` ничего не заметит. Так закрывается утечка
экспериментальных правок: сейчас 15 правок из `2026-09-22_halloween` уже
попали в Weblate поверх текста `master`.

### 4. Ветка жила долго и сливается в master

```
feature-A (2 недели)
  -> перед слиянием: pull-from-weblate
     (файлы ветки получают всё, что поменяли в Weblate за 2 недели)
  -> merge в master: в Localization_*.json нет конфликтов или они тривиальны
```

Сейчас 11 из 13 свежих веток несут одни и те же 37 устаревших строк; без
этого шага каждая вернёт в `master` старый текст (так было с
«Картечница» -> «Мортира»).

### 5. Релиз

```
release/*
  -> pull-from-weblate
  -> validate-localization (только чтение):
       файлы = Weblate по всем ключам ветки?
       у каждого ключа с непустым RU есть 15 переводов?
  -> да: собираем; нет: перевести пропуски в Weblate, повторить pull
```

Блокирует ли неполный перевод релиз или только предупреждает, решает ГД.

### 6. Переименовать или удалить ключ

```
переименовать: в Weblate (интерфейс или через нас)
               -> pull-from-weblate -> заменить ключ в коде
удалить:       ключ ушёл из master и всех живых веток
               -> "удали ключ X" (DELETE в Weblate) -> pull-from-weblate
```

Сейчас это делают только в файлах, Weblate не знает - так появились 274
`dialog_*` и 26 лишних ключей.

### 7. Глоссарий

```
master: Localization/Glossary/glossary.csv  (Excel, руками)
  glossary-pull  : Weblate -> CSV, коммит
  правка руками  : коммит в master
  glossary-push  : CSV -> Weblate (только из master)
```

Машинный перевод берёт термины только из Weblate, поэтому правка CSV
действует после `glossary-push`.

### Что меняется в скиллах, коротко

| Скилл | Сейчас | После |
| --- | --- | --- |
| `weblate-push-translate` «добавь» | Создаёт ключ и переводы, пишет файлы; при ошибке `""` | То же плюс проверка «ключа нет», EN первым, пустой перевод - ошибка; файлы через `pull-from-weblate` |
| `weblate-push-translate` «обнови» | Пишет новый текст в RU | «Обнови исходник» (только `master`) и «обнови перевод <язык>» |
| `validate-localization` | Отправляет RU из файлов в Weblate | Только сравнивает и выдаёт список |
| `migrate-legacy-localization` | Копирует строки мимо Weblate | Удалить |
| `pull-from-weblate` | - | Новый: Weblate -> файлы текущей ветки |
| `delete-key` | - | Новый |
| `glossary-pull` / `glossary-push` | - | Новые |

Git-интеграция (раздел ниже) эти пути не меняет: ветку `localization`
сливать не нужно, это только снимок для истории и проверки.

Одной фразой: **добавлять - в любой ветке; менять существующий текст -
только из `master` или в Weblate; файлы только скачиваем из Weblate и
никогда не отправляем обратно; перед слиянием и релизом -
`pull-from-weblate`.**

## Глоссарий

Глоссарий - отдельный компонент `glossary-ru`, его можно получать и
править через API так же, как тексты. Машинный перевод берёт термины
только из Weblate, поэтому файл в репозитории - копия для людей и
скиллов.

1. Файл `Localization/Glossary/glossary.csv` (вне `Assets/`, Unity его не
   видит): строка на термин, колонки `ru`, `explanation`, `flags` и 15
   языков. Лежит и меняется только в `master`.
2. `glossary-pull`: по каждому языку
   `GET /api/translations/pirate-ships/glossary-ru/<lang>/units/`, свести
   по RU, записать CSV и время синхронизации в
   `Localization/Glossary/.sync`, закоммитить. Можно по расписанию.
3. Человек правит CSV (Excel, руками) и коммитит в `master`.
4. `glossary-push` (только из `master`): сравнить CSV с версией на момент
   последней синхронизации и с текущим Weblate. Новая строка - `POST`
   термина и переводов с флагом `terminology`; изменённая ячейка -
   `PATCH /api/units/<id>/`; удалённая строка - `DELETE`. Ячейка,
   изменённая и в CSV, и в Weblate, не применяется, а выводится как
   конфликт. Затем `glossary-pull`.
5. Мы до запуска проверяем на dev-стенде удаление термина во всех языках
   и сохранность флага `terminology`, и исправляем код китайского
   `zh_CN` -> `zh_Hans`.

## Второй язык

Сейчас второй язык не задан ни в проекте, ни в компоненте. Если его
задать, LLM получает в каждом запросе, кроме RU-исходника, ещё и готовый
английский перевод строки как справку. Вывод: **английский как справка -
да, перевод через английский (RU -> EN -> остальные) - нет.**

Почему не перевод через английский:

- В форке это настройка движка `source_language=secondary` на весь
  проект. Тогда сам EN перевести нельзя (движок отказывается от пары
  en -> en), строки без готового EN тихо пропускаются, а RU исчезает из
  запроса.
- Ошибка в EN копируется во все 14 языков. EN сейчас не вычитан: 0
  подтверждённых строк из 3 936, 118 с проверкой `repeat-drift`.
- Наш замер на китайском
  (`docs/product/measurements/2026-09-17-dual-reference-zh-assistant-assessment.md`)
  не показал выигрыша ни у EN как исходника, ни у двух исходников.
  Внешних измерений для RU -> TH/VI/ID через EN с современными LLM нет.

Что делаем:

1. Мы задаём компоненту `localization-json` второй язык English (на
   компоненте, не на проекте, чтобы не задеть глоссарий).
2. Перед этим закрываем 5 строк EN «требует переписывания» и 118
   `repeat-drift`, выборочно вычитываем EN. Справка берётся только из
   EN в состоянии «переведено» и выше.
3. Скилл переводит новый ключ в таком порядке, чтобы EN был готов как
   справка для остальных:
   1. `POST .../ru/units/` `{"key": "K", "value": ["..."]}`;
   2. `POST /api/translations/pirate-ships/localization-json/en/autotranslate/`
      `{"mode": "translate", "auto_source": "mt", "engines": ["openrouter"], "threshold": 80, "q": "state:empty AND key:=\"K\""}`;

   Режим только `translate`: при `fuzzy`/`suggest` EN не станет справкой.
4. Один вызов «на все языки» в API нет. Если 16 вызовов неудобны, это
   доработка на нашей стороне (эндпоинт или задача на компонент), её
   приоритет обсуждаем отдельно. Перевод через EN только для th/vi/id
   возможен лишь после доработки кода и A/B-проверки.

## Git: как закончить интеграцию

При новом процессе файлы в ветках формирует `pull-from-weblate`, поэтому
перенос из `localization` в `master` больше не нужен. Подключение
компонента к Git остаётся полезным, но как снимок, а не как канал
доставки:

- Weblate пушит полный набор файлов в ветку `localization`. Это история
  всех изменений в репозитории игры, резервная копия и эталон для
  проверки перед релизом (правило 8).
- Команда ветку не сливает; скиллы читают Weblate через API, как сейчас.

Порядок: ротация пароля `localization.service`, креды на production,
`ls-remote` с production, затем параллельный компонент на `localization`
с push по расписанию. Делать после сведения, когда Weblate и `master`
совпадают. Если команде снимок не нужен, этот этап можно отложить без
ущерба для процесса.
