## Ограничения

- Без отдельного явного разрешения не обновлять production, не выполнять
  merge, не перезапускать службы и не изменять настройки рабочего сервера.
- Старое задание с неизвестным результатом не возобновлять; не посылать
  повторные платные запросы. Изоляция задания, если понадобится для безопасного
  запуска воркера, выполняется только по отдельно проверенной процедуре и с
  разрешения пользователя. Включение внешних записей — отдельный этап.
- Не подменять production локальной БД и не перезаписывать новые переводы старым
  снимком. Не публиковать ключи, пользовательские данные и резервные копии в Git.
- Два кода развёртываются по отдельности; существующий интерфейс и прямой доступ
  пользователей к Weblate сохраняются. Запись в Weblate через визард первоначально
  выключена; иные пути доступа и исполнители задач учитываются отдельно.

## 1. Проверка совместимости и подготовка выпуска вне production

### Контракт двух процессов и необходимая доработка

Обычный Weblate сохраняет действующие модели/routing, размеры пакетов,
streaming, retry/fallback, overwrite, partial/error semantics, глоссарий,
защищённые токены, права, редактирование и загрузки. Вход в Wizard не требуется.
Одинаковые входные данные, настройки и тестовые ответы должны давать прежние
запросы, изменения строк и состояния заданий; побуквенное совпадение реальных
генераций LLM не является проверяемым контрактом.

Для визарда сохраняется проверенное поведение: SSO/делегация, локкит и языки,
восстановление по квитанциям, запрет повторной отправки при неизвестной оплате,
429/backoff, весь цикл качества и неизменность переводов в verify_only.

В `weblate/trans/judge.py:_run_batch` сейчас `durable = run is not None`.
Обычное задание судьи с ProducerRun поэтому тоже отключает streaming, isolation,
повторы и fallback. В `judge_loop.py:repair_targets` durable/retry также зависят
от наличия run_id. Отключения SSO и внешних записей визарда для изоляции недостаточно.

- [ ] Ввести явную серверную границу режима заданий визарда; проверить callers
  в `weblate/api/producer/`, `trans/mt_operations.py`, `quality_execution.py`,
  `judge.py`, `judge_loop.py`, `autotranslate.py`, machinery и tasks. Не определять
  режим по одному лишь run, имени пользователя, модели или заголовку клиента.
- [ ] Ограничить новую политику восстановления и отправки этим режимом;
  обычному Weblate сохранить прежние ветви. Исторические задания без признака
  не переклассифицировать в задания визарда. Не ослаблять финансовые запреты
  для уже зарегистрированных неизвестных операций. Если строгая изоляция требует
  изменения контракта, согласовать конкретное исключение до реализации.
- [ ] Добавить парные проверки production-базы `03ef9d8` и исправленного кандидата
  с одинаковыми mock-ответами: MT, streaming, транспортный сбой, 429/fallback,
  partial repair, overwrite, placeholders/glossary, usage и итоговые состояния.
  Для визарда отдельно доказать отсутствие повторной оплаты и использование
  сохранённого ответа. Не вызывать настоящие платные модели.
- [ ] Проверить обычные UI/API сценарии загрузки, правки, MT, судьи и принятия
  результата; матрицу SSO on/off и Session/Token/Bearer. Использовать типы
  операций и языков проектов, наблюдавшихся 27–28 октября. Рабочие данные
  не использовать в изменяемых тестах и не переносить тестовые БД на production.
- [ ] Повторить после доработки затронутые тесты визарда, сборку и browser E2E;
  зафиксировать новые SHA. Перенос разрешается только при выполнении обоих

## 2. Резервные копии и подготовка короткого окна

- [ ] Сохранить старый запущенный образ Weblate по неизменяемому ID и старый
  выпуск визарда; проверить, что они доступны для запуска. Сохранить конфигурацию,
  состав контейнеров/томов, журналы и указатели версий без публикации секретов.
- [ ] Предварительно сделать и проверить резервные копии базы Weblate, файлов
  и Git-репозиториев проектов, базы/файлов визарда и журналов запросов. Проверить
  хеши и восстановление в изолированном окружении; сохранить приватно.
- [ ] Перед переключением закрыть приём новых заданий, определить и дождаться
  завершения текущих операций либо безопасно приостановить обработку. Не считать
  отправленный запрос отменённым. Зафиксировать в том числе неопределённые операции.
- [ ] В согласованное окно изолировать все писатели, включая фоновые и прямые
  API-пути, и сделать финальные согласованные резервные копии **до** любых
  изменений задания или миграций. Если требуется изоляция старого задания,
  повторно проверить доказательства, провести её без возобновления и сделать
  второй снимок. Сверить контрольные показатели и журналы до/после.

## 3. Переключение Weblate, затем визарда

- [ ] Заблаговременно доставить проверенные артефакты и подготовить конфигурации
  без запуска новой версии и без изменения работающих данных. Проверить URL HTTPS,
  сертификат, callback OIDC, идентификатор клиента, права пользователей и связь
  между серверами. Настроить ссылку через `WEBLATE_WIZARD_PUBLIC_URL`; секреты
  передавать только через защищённую конфигурацию.
- [ ] В разрешённое окно переключить Weblate на проверенный образ и согласованные
  миграции; проверить доступность, журнал ошибок, БД, существующие проекты и
  обычный вход/редактирование через Weblate. Не включать визардные записи.
- [ ] Затем переключить API визарда на подготовленный выпуск с внешними записями
  и платными операциями выключенными. Воркеры запускать только после проверки
  состояния очереди и защиты старого задания. Сохранить существующую БД и файлы.
- [ ] Проверить переход из Weblate, единый вход, разграничение прав, список
  проектов, локкит, переключение этапов и режим «только проверка» без изменения
  реальных переводов и без оплачиваемых запросов. Если безопасный тест невозможен
  в production, выполнить его на стенде и ограничить production-проверку чтением.
- [ ] Сверить количества и контрольные показатели переводов и журналов относительно
  финальной точки, статус задач, отсутствие новых подозрительных запросов и ошибки
  сервисов. Зафиксировать фактическую длительность перерыва и работающие версии.
- [ ] Только после отдельного согласования включить новые задания/внешнюю запись;
  повторно проверить защиту неизвестных операций. Старое задание не возобновлять.

## 4. Откат

- [ ] При ошибке удержать внешние записи и приём заданий выключенными; сохранить
  журналы и текущее состояние операций. Не запускать повторно неопределённые запросы.
- [ ] Если новые версии изменили данные, сохранить новый согласованный снимок до
  отката. Определить, проходили ли миграции и совместимы ли старые версии с текущими
  схемами; не откатывать миграции и не восстанавливать БД поверх новых переводов.
- [ ] При доказанной совместимости вернуть прежний выпуск визарда и настройки,
  затем прежний образ Weblate и настройки; включать воркеры лишь после проверки
  очереди и защиты старого задания. Новые journal-задания не передавать старому
  коду, который не понимает их запрет повторной отправки; они остаются на паузе.
  Проверить доступ, проекты и показатели данных.
- [ ] Если совместимость старого кода с новой схемой не доказана, остановить
  переключение назад и использовать заранее отрепетированный forward-fix либо
  отдельный план восстановления с сохранением новых данных. Простое восстановление
  старого бэкапа допустимо только после оценки расхождений и отдельного согласования.

Короткий перерыв — цель, а не гарантия: оценить время по репетиции и размеру
актуальных данных; при невыполнении контрольных условий окно не начинать.
