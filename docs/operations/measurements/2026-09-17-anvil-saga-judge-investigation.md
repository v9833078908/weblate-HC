# Anvil Saga: исследование запусков LLM-судьи и контекст продолжения

Дата: 2026-09-17.
Статус: исследование не завершено; производительность по этапам не измерена.
Назначение: передать следующей сессии факты, ограничения доказательств,
решения пользователя и открытые вопросы без повторного восстановления чата.

## Главное для следующей сессии

Пользователь считает текущую работу судей неприемлемо неоптимальной.
Нужно понять причину длительности и числа запросов, а не просто уменьшить
размер запуска или спрятать проблему за ограничением интерфейса.

Два прогона Anvil Saga обработали по 2000 строк за примерно 5 ч 20 мин
и 9 ч 11 мин, зарегистрировав 3004 и 3031 HTTP-попытку. У них один
Celery task ID, второй создан спустя 14407 с при лизинге 14400 с.
Они пересекались по времени и по 291 обработанной строке.

Это свидетельства проблемы надёжности и повод для диагностики
производительности, но **не разложение причин медленной работы**.
Мы ещё не знаем, сколько времени заняли судейство, repair, повторы,
провайдер, локальная обработка и конкуренция исполнителей.

Никакая реализация или production-деплой в этой сессии не выполнялись.
Новые платные LLM-запросы не запускались. Все production-проверки были
read-only. Настройки, ключи и переводы не менялись.

## Запрос и решения пользователя

Последовательность обсуждения:

1. Проверить на проде статус судей Anvil Saga: запуск был вчера,
   возникло подозрение на исчерпание лимитов.
2. Объяснить кап и проблему «запустил проверить проект, получил отчёт,
   хотя всё не проверено».
3. Предложить решение из первых принципов, затем переоценить его по Парето.
4. Составить эффективный план без overengineering.
5. Перед планом проверить размеры лок-китов на проде. Рассмотреть отдельно
   запрет запуска на уровне проекта.
6. Уточнение пользователя: **исключить из плана именно отказ до запуска
   при превышении капа**. Это не отмена существующего капа.
7. Обсудить повышение капа до 10000; изменение не разрешено и не сделано.
8. Пользователь указал, что судьи работают неоптимально, и запросил
   сохранение полного контекста для другой сессии.

Текущие границы:

- Кап остаётся 2000, действующее усечение выборки сохраняется.
- Запрет project-level запуска пока не согласован и не входит в план.
- Отказ при превышении капа не входит в план.
- Кампании, автоматическое продолжение, денежные бюджеты и жёсткий
  часовой дедлайн не согласованы к реализации.
- План написан, но разрешения исполнять его или деплоить нет.
- Пользователь хочет переосмыслить производительность; текущий план
  надёжности не считать полным ответом на этот запрос.

В базе обнаружены четыре task ID с двумя ProducerRun; больше двух run
на task ID в той выборке не было.

Во всех четырёх парах интервалы recorded started/finished перекрываются.
Для failed/orphaned markers это не доказывает, что процесс всё это время
жил. У четвёртой по времени отличающейся пары первый marker был закрыт
оператором; причина повторной доставки не доказана.

Три разрыва близки к live visibility timeout 14400 с. Вместе с
`acks_late=True`, `reject_on_worker_lost=True` и веткой создания нового run
это сильная гипотеза редоставки по лизингу. Прямого worker/broker лога
«received дважды» с нужным task ID не получено. Поиск в 36-часовом окне
не дал совпадений; фактическую полноту retention не доказали.

Не повторять прежние чрезмерные утверждения:

- «всякий запуск дольше четырёх часов гарантированно дублируется»;
- «четвёртая пара точно вызвана worker loss»;
- «второй run и все его 3000 запросов оплачены впустую»;
- «почему не было третьего run — известно».

## Кап, выборка и отчёт: что подтверждено кодом

Проверялись локальные исходники; их полное совпадение с установленным
production-кодом в этой сессии отдельно не проверялось.

- `weblate/trans/defaults.py:DEFAULT_JUDGE_MAX_UNITS_PER_RUN = 2000`.
- `weblate/settings_docker.py` читает `WEBLATE_JUDGE_MAX_UNITS_PER_RUN`.
  Это серверная настройка, не поле пользовательской формы.
- `weblate/trans/autotranslate.py:AutoTranslate.preview_judge_scope`
  сортирует по position/pk и берёт первые N; BatchAutoTranslate распределяет
  общий cap между переводами. Непереведённая выбранная строка не заменяется
  следующей только потому, что для неё не получилось получить перевод.
- Превышение cap сейчас не отказывает всему запуску: остаток записывается
  как SKIPPED/CAP и summary.cap_remainder; run может быть completed.
- `judge_limit` — внутренний параметр, не внешний per-run override.
- `docs/admin/config.rst`, секция JUDGE_MAX_UNITS_PER_RUN, всё ещё описывает
  полный отказ при превышении. Это расхождение с проверенным поведением;
  документацию нельзя использовать как доказательство наличия отказа.
- Повторный запуск пересчитывает живой фильтр. Сам по себе cap не является
  курсором «следующие 2000». В наблюдавшихся run был `NOT has:judge`.
  Рекомендация «27 раз нажать запуск, и всё будет проверено» отозвана.
- `weblate/trans/views/judge.py:producer_run`, `_filter_outcome` и
  `weblate/templates/producer-run.html`: предупреждение сохраняется и
  отображается; Matched/checked уже существуют. Неверно, что cap полностью
  скрыт или предупреждение только transient flash.
- Проблема UX: completed одинаков для полного и усечённого запуска;
  карточка действий сосредоточена на находках, а не непроверенном остатке;
  checked включает исходы без заключения. Нельзя читать «нет замечаний»
  как «весь проект проверен».
- `weblate/api/producer/serializers.py:ProducerRunSerializer` отдаёт
  summary/failure, но не warnings.
- `ProducerRunResume` в `weblate/api/producer/views.py` принимает только
  failed run; готового продолжения cap-skipped scope нет.

## Исполнение и надёжность: точки входа следующей диагностики

- `weblate/trans/tasks.py:auto_translate`: общая Celery-задача с late ack,
  reject on worker loss и retry после WeblateLockTimeoutError.
- `weblate/trans/views/edit.py:auto_translation`: UI публикует UUID задачи,
  но не предсоздаёт producer run и не передаёт producer_run_id.
- `weblate/trans/autotranslate.py:BatchAutoTranslate._adopt_producer_run`:
  без ID создаёт новый run; существующий RUNNING допускается повторно при
  совпадении task ID. Row lock закрывается до платной работы и не исключает
  параллельное выполнение двух доставок с одинаковым ID.
- `_create_producer_run`, `perform`, `_finish_producer_run`: проверить
  идентичность run, жизненный цикл и сохранение summary при восстановлении.
- `AutoTranslate.process_judge`: есть пропуск записей с non-PENDING outcome.
  Это не mutex для двух одновременно увиденных PENDING.
- `weblate/trans/judge_loop.py:_cached_verdict`, `run_judge_batch`:
  кэш и этапы судейства/repair; ключи содержат идентичность текста/запроса
  и профиля, не только unit ID.
- `weblate/trans/judge.py`: транспорт, request attempts, batching и callbacks.
- `weblate/api/producer/views.py:ProducerProjectRunStart`,
  `ProducerRunResume`; `weblate/trans/tasks.py:publish_producer_run_dispatch`:
  предсозданные run и durable dispatch уже есть, но не заменяют runtime lock.
- `weblate/api/views.py:TranslationViewSet.autotranslate`: отдельный
  синхронный REST-вход через BatchAutoTranslate.
- `weblate/utils/lock.py:WeblateLock`: Redis-lock с TTL, FileLock fallback.
  Истечение TTL блокировки — отдельная опасность при неизвестной длительности.
- `deploy/docker-compose.yml`: в описанной topology web и Celery workers
  находятся в одном контейнере с общим `/app/data`.

Идемпотентная строка run сама по себе не даёт exactly-once выполнения.
Даже единственный исполнитель не исключает повторную оплату после смерти
между ответом провайдера и сохранением результата; для строгой гарантии
нужна поддержка идемпотентности внешней стороны или другой контракт.

## Производительность: что известно и что не измерено

Наблюдавшееся отношение wall-clock к числу обработанных строк:
примерно 9.6 и 16.5 секунды на строку. Это средние для целых run,
**не latency одной строки и не цена одного HTTP-вызова**.
Прогоны работали одновременно примерно 81 минуту, поэтому это не два
изолированных benchmark с одинаковыми условиями.

В чате была линейная экстраполяция:

- 9482 строки: примерно 25–44 часа;
- 10000 строк: примерно 27–46 часов.

Это не измерения и не обещание будущей длительности. Нельзя на этой основе
объявлять, что сутки — нормальная цена проверки лок-кита, или что меньший
cap исправляет производительность.

Пока отсутствуют:

- разбивка requests и времени по initial judge, retries, repair и re-judge;
- распределения latency, размера фактического батча и токенов;
- доля времени в provider I/O, БД, локальной сборке контекста и ожиданиях;
- фактическая степень параллелизма seats и задач;
- полная стоимость и доля unpriced calls;
- объяснение 291 повторно отобранной строки и нулевого cached;
- причина разных длительностей и несогласованностей ledger/summary/timestamps.

`repaired=0` не позволяет вычеркнуть repair из профиля: безуспешные попытки
тоже могут занимать время и деньги. 3000 HTTP-попыток нельзя объяснять
простым делением на batch size без проверки реальных стадий.

## С чего продолжить, не превращая это в новую архитектуру заранее

1. Восстановить два run по UUID и прочитать установленный production-код
   интересующих путей. Сначала использовать сохранённые attempts/usage,
   не запускать новый платный прогон для получения уже имеющихся данных.
2. Выяснить доступные поля JudgeRequestAttempt и LLMUsageLog, связать
   по run/seat/round/operation там, где связь реально сохранена. Посчитать
   количество, elapsed и токены/стоимость с отдельной категорией unknown.
   Не суммировать перекрывающиеся elapsed как wall-clock задачи.
3. Разложить реальные batch sizes, initial/repair/rejudge/retry и места
   последовательного выполнения. Проверить, какие ремонтные вызовы вообще
   попадают в JudgeRequestAttempt, а какие видны только в usage/logs.
4. Разобрать небольшой доказательный срез из 291 пересечения: версии target,
   context/profile и события изменений, чтобы объяснить повторный отбор.
5. Только после профиля выбрать самый дорогой устранимый фактор и предложить
   минимальное изменение с проверяемым эффектом. Не подменять оптимизацию
   уменьшением cap или обещанием полной проверки за N ручных запусков.
6. Отдельно воспроизвести concurrent redelivery в изолированной QA-среде
   с подставным провайдером; не менять production lease/очередь вручную.

Это направление исследования, не разрешение на реализацию, деплой,
рестарт shared dev, новые платные запросы или массовое изменение переводов.
