# План: глоссарий Spaceship Battles (Space Arena) из кита GD

**Вход:** `/Users/eli/Downloads/Spaceship Battles - Localization - Glossary (1).csv`
(336 строк, 16 колонок: колонка описания + `en,ru,de,fr,es,pt-br,ch-s,jp,kr,fa,tr,hi,id,th,vi`).

**Выход:** `/Users/eli/Downloads/SpaceshipBattles-glossary.csv` - плоская
глоссарная таблица в том же формате, что уже сделанные
`heart_abyss_glossary_temple.csv` (`ru,en,notes`),
`docs/misc/col4-glossary-append-2026-08-14.csv` (`ru,en,tr,fr,note`),

последняя колонка - авторская заметка про термин.

**Цель:** таблицу GD, где смысл термина спрятан в неподписанной колонке с
`%KEY%`-описаниями и секционными строками, превратить в файл, который
проходит гейт `Use as glossary` (детерминированный вывод профиля -> parse ->
render -> parse-back) и несёт LLM и переводчику осмысленное пояснение на
каждый термин.

## Решения по формату

1. **Плоская таблица, одна строка = один термин.** Секции складываются в текст
   заметки, отдельной колонки секции нет: детерминированный вывод профиля
   (`loc_kit_ingest/infer.py:623-638`) отказывает любой заполненной колонке,
   которая не язык и не заметка, а `section_field` он не выводит - её пришлось
   бы писать руками в профиле и терять путь визарда.
2. **Заголовки колонок под коды Weblate:**
   `ru,en,de,fr,es,pt_BR,zh_Hans,ja,ko,fa,tr,hi,Indonesian(id),th,vi,note`.
   `pt-br/ch-s/jp/kr` не резолвятся или резолвятся неверно
   (`ch-s`, `jp`, `kr` -> `None`), а колонка с заголовком ровно `id` считается
   техническим идентификатором и не импортируется
   (`infer.py:44,78`) - поэтому индонезийский подписывается как
   `Indonesian(id)`, что `langcode.language_code` разбирает в `id`.
3. **Исходный язык - `ru`** (утверждено пользователем 2026-08-18; в течение дня
   был перепроверен на `en` и возвращён к `ru`): самая левая языковая колонка
   становится source, а глоссарий виден только компонентам с тем же исходным
   языком - `get_glossary_units` фильтрует
   `translation__component__source_language`
   (`weblate/glossary/models.py:310-316`). Компонент Space Arena создаётся с
   русским источником (замеры в
   `docs/plans/2026-08-18-space-arena-language-aliases-and-sourceless-keys.md`,
   раздел «Исходный язык компонента»), поэтому и глоссарий русский. Порядок
   остальных колонок сохраняет порядок кита. Переключается константой
   `SOURCE_CODE` в конвертере.
4. **Омонимы сводятся к одной строке** (утверждено пользователем 2026-08-18).
   С `ru` как источником сталкиваются два термина: `Поддержка` (корабль
   поддержки `%SUPPORT_SHIP%`, подкатегория модулей `%CATEGORY_SUPPORT%`,
   модуль-супорт `%MODULE_KIND_SUPPORT_SYSTEM%`) и `Броня` (подкатегория
   `%CATEGORY_ARMOR%`, модуль `%MODULE_KIND_ARMOR%`, характеристика
   `%ARMOR%`) - 6 строк на 2 термина. `Двигатели`/`Двигатель` и `Щиты`/`Щит`
   различаются числом, поэтому остаются отдельными терминами: коллизия
   английских `Engine` и `Shield` существует только при en-источнике.
   Контекст термина в TBX это `(секция, термин)`, поэтому без колонки секции
   одинаковый источник даёт `tbx.duplicate_context` (`parser.py:810-816`) и файл
   не публикуется. Хуже технической причины смысловая: три записи
   `Поддержка -> Unterstützen / Beistand / Unterstützung` не инструкция, а
   противоречие для LLM и переводчика. Оставляю строку с наиболее общим
   смыслом (первое вхождение в ките), остальные смыслы уходят в заметку
   целиком: их `%KEY%` и те целевые строки, которые расходятся. Итог - 313
   терминов из 317 строк кита от 2026-08-18.
5. **Чистка ячеек:** обрезка внешних пробелов (утверждённая политика кита,
   `docs/plans/2026-08-10-loc-kit-glossary-term-description-shape.md:95-105`),
   удаление U+FEFF, удаление `#VALUE!`; U+200C в персидском сохраняется - это
   значащий ZWNJ, а не мусор.
6. **Пропуск `hi` у `Number of torpedoes` сохраняется пустым** -> профиль
   получает `allow_empty_targets`; выдумывать перевод нельзя.

## Формат заметки

Русский язык (как в COL4 и Heart Abyss), одна строка, три части:

```text
<Смысл термина>. <Правило по классу>. Ключ движка: %KEY%. Раздел: <секция>.
```

- Смысл: описание GD, приведённое к нормальной фразе (в ките это хвост после
  `%KEY% - `), текст кита не переписывается. Там, где описания нет (148 строк),
  смысл выводится из префикса ключа, без придумывания игровой механики:
  `CATEGORY_` - «Подкатегория модулей», `MODULE_KIND_` - «Вид модуля»,
  `SUBLEAGUE` - «Название ранга внутри лиги», `PILOT_RANK_` - «Звание пилота»,
  `PARAMETER_TIER_` - «Название уровня редкости» и так далее. Если такой смысл
  дословно повторяет начало правила раздела, он не печатается дважды.
- Правило по классу - один фиксированный шаблон на раздел кита: имена пилотов
  транслитерировать и переводить прозвище по смыслу; классы кораблей -
  согласовать полную и сокращённую форму; характеристики модулей - короткая
  подпись в UI, тот же перевод в описании модуля; ресурсы - не переводить
  описательно.
- Для свёрнутых омонимов добавляется часть «Тот же исходный термин в ките
  значит также: (1) <смысл> [`%KEY%`]: de=..., id=...; (2) ... - расхождение
  кита, свести к канону», где перечислены только те целевые строки, которые
  отличаются от оставленной.

Никакого обращения к OpenRouter: все заметки собираются детерминированно из
кита по шаблонам разделов, поэтому результат воспроизводим и проверяем глазами.

1. Скрипт-конвертер (одноразовый, в `docs/misc/spaceship-battles-glossary.py`):

## Верификация

1. `infer_glossary_profile` на выходном файле: schema v2 `record-map`,
   `source_lang: ru`, 14 целевых языков, 302 термина, плоская раскладка
   (`record_stride: 1`), ноль `InferenceError`.
2. Полный офлайн-прогон `python -m loc_kit_ingest` в временный каталог:
   parse -> render -> parse-back без ошибок, по одному bilingual TBX на
   целевой язык, `units == 302`.
3. Проверка контента в собранном TBX: `Корабль`, `Поддержка` и `Броня` (с
   текстом про омонимы), `Stone League` (заметка собрана из шаблона, а не из

4. `uv run prek run --files docs/misc/spaceship-battles-glossary.py docs/plans/2026-08-18-spaceship-battles-glossary.md`.
