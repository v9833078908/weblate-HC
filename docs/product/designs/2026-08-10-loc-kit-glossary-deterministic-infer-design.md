# Детерминированный разбор глоссарных таблиц в loc-kit визарде

Дата: 2026-08-10. Статус: дизайн реализован и проверен 2026-08-15.

## Проблема

Загрузка таблицы с галочкой «Use as glossary» упирается в тупик, когда
OpenRouter-анализ выключен (`LOC_KIT_PROFILE_ANALYSIS_ENABLED = False` — дефолт,
в dev-docker он не включён): превью пустое, кнопка «Create glossary component»
неактивна, а единственный предлагаемый выход — вручную написать JSON-профиль
schema v2 (record-map). Это формат для машины; пользователь его не напишет.
Реальный кит `Heart Abyss_Localization - Terms.csv` (колонки — только языки:
`ru,en,fr,it,de,ja,ko,pt-PT,zh-CN,zh-TC,es`) при этом тривиален и уже сегодня
разбирается детерминированным `loc_kit_ingest.infer` в PO-пути без галочки.

## Решение

Детерминированный вывод глоссарного профиля выполняется первым, локально и
бесплатно; OpenRouter — только запасной путь для таблиц, которые локальный
разбор не распознал; ручной JSON остаётся аварийным люком.

### 1. `loc_kit_ingest.infer.infer_glossary_profile`

Новая функция `infer_glossary_profile(sheet_name, rows, *, component)` →
`(document, notes)`, где `document` — обычный профиль schema v2 с одним
tbx-компонентом (грамматика record-map). Правила (v0):

- заголовок и языковые колонки — существующими эвристиками
  (`_find_header_row`, `_language_code`, распознавание `ru`, `pt-PT`,
  `English(en)`); колонка 0 повышается до языка, если её заголовок — код языка
  (с тем же denylist `id` и числовой демоцией, что в PO-пути);
- `source_lang` = самая левая языковая колонка;
- `initial_target_languages` = языковые колонки, заполненные в **каждой**
  строке-записи; частично заполненные распознаются, но не импортируются —
  предупреждение попадает в превью;
- строки-записи = строки с непустым термином source-языка; регионы —
  непрерывные блоки таких строк, `record_stride = 1`, `term_row_offset = 0`;
- caption-строки после заголовка (названия языков, `id-ignore`) и строки без
  source-термина → `skip_rows` с примечанием;
- секции и notes не выводятся (v0);
- любая заполненная не-языковая колонка → `InferenceError`: парсер record-map
  считает незамапленную заполненную ячейку ошибкой (`tbx.unmapped_cell`),
  угадывать назначение колонки нельзя.

Граница v0 осознанная: детерминированно проходят таблицы «только языки»
(+ caption-строки, пустые строки, секционные строки, которые импортируются как
обычные термины). Таблицы с колонками domain/note/прочее — через OpenRouter
или корректированный профиль.

### 2. Порядок анализа в `_analyze_draft_sheet`

1. `infer_glossary_profile` → существующий локальный gate
   `validate_glossary_profile` (схема, полный парс, TBX render, parse-back) —
   новый путь доверия не появляется;
2. при `InferenceError` или ошибках gate — OpenRouter, только если включён
   (rate limit, sample, строгий JSON Schema — без изменений);
3. иначе — сообщение с причиной детерминированного отказа и подсказкой про
   ручной профиль.

Заметки инференса (`notes`) добавляются к предупреждениям превью
(`_store_validated_profile(..., extra_warnings=notes)`).

### 3. Пропуск выбора листа для одностраничных файлов

У CSV/TSV всегда один лист — экран выбора листа бессмыслен. В
`_start_glossary_draft` при единственном листе: лист фиксируется сразу,
выполняется **только детерминированный** разбор (сетевой вызов внутри
атомарного POST загрузки недопустим); при успехе — redirect сразу на превью,
при неудаче — на выбор листа, как сейчас (POST выбора листа запускает полный
путь анализа, включая LLM). Многостраничные XLSX — без изменений.

## Пользовательский путь (итог)

CSV + «Use as glossary» → превью («N терминов, ru → en, ja» + примеры +
предупреждения) → «Create glossary component». Без сети, без JSON.

Отдельный шаг вне этого изменения: на переводимом компоненте включить флаг
`check_glossary` (чек «Does not follow glossary» в Weblate выключен по
умолчанию), иначе глоссарий виден только в сайдбаре переводчика.

## Что не делаем

- OpenRouter env в dev-docker (можно включить позже для нестандартных таблиц);
- кнопку «blank profile template» — с детерминированным путём она не нужна;
- изменения CLI `loc_kit_ingest` (остаётся без `--suggest-profile`);
- вывод секций/notes (v1-кандидат, если реальные киты потребуют).

## Тестирование

- standalone-тесты `infer_glossary_profile` в `loc_kit_ingest/tests/` (без БД);
- contract-тесты: при выключенном анализе одностраничный языковой CSV даёт
  готовое превью и живой TBX-компонент; фикстура `GLOSSARY_CSV`
  (domain/note_*) намеренно не разбирается детерминированно и продолжает
  покрывать LLM/ручной путь;
- живой smoke в dev-инстансе: реальный Terms.csv кликами в браузере.

## Follow-up (вне этой итерации)

- **Обновление существующего глоссария из новой таблицы** — визард всегда
  создаёт новый компонент, а живому проекту нужен повторный импорт свежего
  экспорта. План: `docs/product/plans/2026-08-10-loc-kit-glossary-update-existing.md`.
- **Выбор целевого репозитория.** Компонент создаётся с `vcs=local`,
  `repo=local:` (`LOC_KIT_LOCKED_FIELDS`), то есть глоссарий живёт во
  внутреннем git Weblate и не попадает в репозиторий игры. Weblate сам
  поддерживает и связанный репозиторий (`weblate://project/component`), и
  отдельный URL, но визард их не предлагает. Не планируется: запись и push в
  живой репозиторий из визарда рискованны, а результат достижим настройками
  компонента вручную.
- **Порядок миграции A→B (внутренний git → репозиторий игры).** Смена `repo`
  поднимает `changed_git` и перечитывает переводы из нового репозитория
  (`component.py:1250-1293`, `5637-5659`), а не заливает туда существующие:
  сначала выгрузить TBX из Weblate и закоммитить их в репозиторий игры по
  будущему filemask, только потом менять `repo`/`filemask`.
- **Конвейер для живого проекта.** Устойчивее держать конвертацию на стороне
  репозитория игры: `python -m loc_kit_ingest <kit> --profile <profile>.json`
  в CI генерирует TBX, Weblate только подтягивает изменения. Визард при этом
  остаётся инструментом первичного импорта.
