# Память импорта и восстановление после прерывания

Пик выделений Python при разборе синтетического PO из 9 483 строк уменьшился
на 30,2 %. Ниже отдельно приведены проверки разбора, полного добавления строк
и прерывания обработчика. Это разные эксперименты: цифры парсера нельзя
выдавать за потребление всей загрузки или контейнера.

Проверки выполняются локально на macOS с отдельным PostgreSQL 16. Настоящий
HTTP-сервер, перезапуск Granian и общая память production-контейнера в этом
стенде не воспроизводятся; расчёт запаса production остаётся условием выпуска.

## Метод

Синтетический PO содержит 9 483 строки, 1 840 388 байт, контексты, комментарии,
ссылки, 20 % fuzzy и 5 % plural. Пробник вызывает реальный
`Translation.load_uploaded_file(..., method="add")` для шаблона po-mono и
проходит `iterate_merge("process")`. У компонента и запроса тестовые заглушки;
базы, девяти языков и фактической записи строк нет. В каждом запуске создан
новый процесс Python. Контрольная версия — `5923d8c8`, исправленная — рабочая
копия с оптимизацией разбора. Интерпретатор и зависимости одинаковые.

Пиковая RSS получена из `getrusage` на macOS, в MiB; она включает загрузку
Django и остальных библиотек. Это не cgroup peak и не измерение Linux-контейнера.
На машине во время испытания была другая нагрузка, что видно по времени;
сравнивать скорость по этим запускам нельзя.

| Версия | Запуск | Пиковая RSS, MiB | Время, с | Строк обработано |
| --- | ---: | ---: | ---: | ---: |
| До | 1 | 298,0 | 0,643 | 9 483 |
| До | 2 | 286,7 | 1,063 | 9 483 |
| До | 3 | 273,3 | 5,178 | 9 483 |
| После | 1 | 267,3 | 0,954 | 9 483 |
| После | 2 | 267,2 | 0,502 | 9 483 |
| После | 3 | 270,2 | 0,502 | 9 483 |

Во всех шести запусках SHA-256 полей context, source, target, notes и исходного
fuzzy совпал: `7b5f6ab8a19c14dc32858910380bb55d8ca41d03305f88d4a395404a4eeb8f45`.
Снижение медианной RSS в этом ограниченном сценарии — около 6,8 %
(286,7 → 267,3 MiB). Это не прогноз снижения общей памяти сервера.

## Трассировка выделений Python

Отдельные три запуска каждой версии проведены с `tracemalloc`, включённым
непосредственно перед вызовом разбора. Пиковое количество отслеженных байт
составило во всех трёх контрольных запусках 91 015 126, во всех трёх
исправленных — 63 559 612: уменьшение на 30,2 %. Контрольная сумма и число
обработанных строк также совпали. Трассировка сама потребляет память и не
учитывает все выделения нативных библиотек, поэтому это отдельный показатель,
а не пик контейнера. До начала разбора RSS составляла 205–207 MiB; с включённой
трассировкой пик RSS составил 352–367 MiB до изменения и 326–327 MiB после.

## Воспроизведение

Пробник: `analysis/probes/import_memory_recovery_parse.py`. Подготовить два
checkout: контрольный `5923d8c8` и проверяемый, установить одни и те же
зависимости. Из проверяемого checkout запустить три отдельных процесса для
каждого checkout, задав его абсолютный путь в `PYTHONPATH`:

```sh
DJANGO_SETTINGS_MODULE=weblate.settings_test PYTHONPATH="$CHECKOUT" \
  .venv/bin/python analysis/probes/import_memory_recovery_parse.py
```

Для трассировки добавить `IMPORT_TRACE=1` к команде. На macOS `peak_rss_raw` выражен в байтах, на Linux — в KiB. Файл создан
программно; данные реальных проектов и ключи не используются.

Полный импорт в девять языков и прерывания проверяются отдельно от этого
пробника. Их результаты нельзя выводить из приведённых цифр парсера.

## Прерывание обработчика загрузки

На изолированной PostgreSQL проверен реальный `Translation.handle_upload` для небольшого PO: отдельный процесс принудительно завершали перед первой записью, после первой записи и после завершения транзакции, но до передачи результата вызывающему коду. Это проверка обработчика, не HTTP-сервера. Контрольные точки добавлены обёрткой вокруг `add_unit`; путь импорта и хранилище настоящие.

До завершения транзакции снимки строк, журнала изменений и отложенных записей остались идентичны исходным; после завершения транзакции сохранились все добавленные строки, запись о загрузке и отложенные изменения. Содержимое файлов всех переводов побайтно совпало с исходным во всех трёх случаях. При повторной загрузке существующие строки и переводы сохранились, новые строки имели по одной записи на язык и корректные ссылки на источник; после завершённой загрузки повтор пропустил все пять строк.

В этом прогоне от отправки SIGKILL до завершения повторного импорта прошло 0,711 с (до записи), 0,276 с (во время записи) и 0,547 с (после фиксации). Это локальные измерения небольшого файла, не гарантия времени для произвольного размера. Автоматическая проверка ограничивает время пятью минутами.

```sh
PYTEST_XDIST_TESTRUNUID=interrupt-test CI_DB_NAME=import_interrupt CI_DB_HOST=127.0.0.1 CI_DB_PORT=55439 CI_DB_USER=weblate CI_DB_PASSWORD=weblate DJANGO_SETTINGS_MODULE=weblate.settings_test uv run pytest weblate/trans/tests/test_upload_interruption.py --no-cov --reuse-db -q
```

Результат: 3 теста прошли. `PYTEST_XDIST_TESTRUNUID` изолирует тестовый каталог от других одновременно работающих наборов; PostgreSQL был отдельным тестовым экземпляром.

## Остаточная Redis-блокировка

В отдельном Redis 7 создана настоящая блокировка
`lock:component:update:987654` с TTL 3 600 секунд. При подключённом
`django_redis.cache.RedisCache` новый `ComponentUpdateLock` получил блокировку
PostgreSQL за 0,165 с; прежняя Redis-блокировка всё ещё принадлежала своему
владельцу. Она освобождена владельцем после проверки. Это подтверждает обход
оставшегося старого ключа новой версией, но не разрешает одновременную работу
двух поколений: условия согласованного выпуска указаны в
`docs/product/guides/import-recovery.md`.

## Статический анализ

`uv sync --all-extras --dev` и `collectstatic --noinput` завершились.
Полный `pylint weblate/ scripts/` завершился с четырьмя предупреждениями в
неизменённых `judge_loop.py`, `test_judge_client.py`, `test_judge_loop.py`.
Это не зелёный общий lint; новых замечаний к изменённому коду не осталось.

Полный mypy запущен командой проекта. На контрольном `5923d8c8` и после
исправления он сообщает одинаковые **1 257 ошибок в 155 файлах**;
новые файлы проверок и изменённые `auto.py`, `ttkit.py`, `lock.py`,
`test_lock.py` не имеют ошибок. Существующие ошибки типизации проекта
этим исправлением не устраняются.

## Полный импорт и повторная загрузка

В отдельной тестовой базе PostgreSQL и локальном Git-репозитории проверен
`Translation.handle_upload` с методом `add`: 9 383 существующие строки,
100 новых строк, исходный язык и восемь целевых языков. Данные подготовлены
пакетно с корректными связями исходных строк; перед измерением выполнен
`ANALYZE`. Все девять языков проверены на сохранность идентификаторов,
контекстов и существующих переводов. Новые строки появились один раз,
их переводы пусты и связаны с исходными строками. Повторная загрузка не
создала дублей; после неё сохранённый исходный PO повторно прочитан и содержит
9 483 строки. Это вызов обработчика без HTTP-сервера.

Три независимых процесса с короткими строками и входным файлом 377 161 байт
прошли проверку. Время вызова добавления составило 13,195 / 11,913 / 10,523 с,
повторной загрузки — 3,616 / 1,948 / 1,794 с. Выборочный максимум RSS процесса
во время добавления составил 341 184 / 328 912 / 323 072 KiB, при повторе —
338 064 / 347 840 / 350 272 KiB. Замеры выполнены на macOS с помощью `ps`
с интервалом 0,2 с; в RSS входят Django, фикстуры и другие данные процесса.
Фоновая нагрузка и сжатие памяти менялись, поэтому время и RSS не являются
сравнением версий и не позволяют оценить потребность контейнера.

Дополнительный прогон с файлом 1 837 543 байта также прошёл: 9,744 с и
выборочный пик 341 648 KiB для добавления, 1,586 с и 351 248 KiB для повтора.
Размер увеличен синтетическими комментариями по 150 символов на запись;
тексты переводов остаются короткими. Это проверка нагрузки по размеру файла,
а не репрезентативный образец конкретного игрового проекта.

Воспроизведение из проверяемого checkout с отдельной PostgreSQL-базой:

```sh
PROFILE_IMPORT_MEMORY=1 PYTEST_XDIST_TESTRUNUID=importprofile \
DJANGO_SETTINGS_MODULE=weblate.settings_test \
CI_DB_HOST=127.0.0.1 CI_DB_PORT=55439 CI_DB_USER=weblate \
CI_DB_PASSWORD=weblate CI_DB_NAME=import_e2e \
.venv/bin/python -m pytest weblate/trans/tests/test_import_recovery.py -q -s --no-cov
```

Для большого файла добавить `FULL_IMPORT_LARGE=1`. Указанные параметры базы
относятся только к изолированному тестовому PostgreSQL и не к production.

## Набор регрессий

```sh
PYTEST_XDIST_TESTRUNUID=root-regression DJANGO_SETTINGS_MODULE=weblate.settings_test CI_DB_HOST=127.0.0.1 CI_DB_PORT=55439 CI_DB_USER=weblate CI_DB_PASSWORD=weblate CI_DB_NAME=import_root uv run pytest weblate/formats/tests/test_formats.py weblate/utils/tests/test_lock.py weblate/trans/tests/test_files.py --no-cov --reuse-db -q
```

Результат: **808 passed, 93 skipped, 63 subtests passed**. Два предупреждения
об открытых файлах относятся к существующим тестам подтверждения
многоязычной таблицы. Отдельно пройдены три проверки прерывания и четыре
полноразмерных прогона, описанные выше.

Независимое ревью выявило мутацию общего PO-шаблона при дублирующихся ключах
с fuzzy; добавлен тест, проверенный красным до исправления и зелёным после.
Остальных подтверждённых нерешённых блокирующих замечаний не осталось.
