# Полный цикл качества: версия 2

Реализована локальная часть визарда для расширенного API Weblate. Наличие
этого кода не означает, что нужный API выпущен на сервере. Новые независимые
LLM-судьи в FastAPI не добавляются: владельцем проверок и записи остаётся Weblate.

## Включение и совместимость

Дополнительно к `WIZARD_EXTERNAL_WRITES=1` и `WIZARD_QUALITY_CYCLE_ENABLED=1`
нужен `WIZARD_FULL_QUALITY_CYCLE_ENABLED=1`. По умолчанию новый флаг выключен.
Новые quality-enabled задания получают `workflow_version=2` только при включении
этого флага. Уже сохранённые задания без версии продолжают прежний сценарий.

До создания удалённого проекта и платного MT worker читает `/api/producer/me/`.
Необходимы `judge=true`, `judge_seats=2`, `quality_api_version=2` и true для:

- `candidate_quality_gate`;
- `glossary_direct_scan`;
- `quality_group_recheck`;
- `quality_repeat_plan`;
- `quality_final_snapshot`;
- `quality_idempotency`.

При несовместимом сервере задание ожидает настройки без удалённой записи.
Включение флага не обходит проверку capabilities. Проверить работу с прежним
сервером полностью через старые API этим изменением не обещается.

В ответе judge estimate поле `preparation.engine` может быть `null`, когда
`preparation.missing=0`: все выбранные строки уже заполнены, предварительный
машинный перевод не требуется. Такой ответ без `blockers` разрешает продолжить
цикл. При `missing>0` движок обязателен; отсутствующие или некорректные поля
подготовки отклоняются как ошибка контракта, а не считаются готовностью.

Новый проект для задания с включённым quality cycle создаётся с
`translation_review=true`, чтобы строки были доступны судьям. Worker проверяет
ответ сервера и не меняет настройки уже существующего или восстановленного
проекта: если review выключен, обработка завершается явной ошибкой настройки
до импорта и MT. Обычные задания без quality cycle сохраняют прежний запрос
создания проекта. Judge estimate должен содержать положительное целое
`selected`: пустой объём проверки не считается готовностью полного цикла.

Новые строковые компоненты полного цикла версии 2 создаются с
`allow_translation_propagation=true`: иначе Weblate исключает их из проверки
повторов. Для глоссариев и обычных заданий запрос не меняется. В существующих
компонентах визард эту настройку автоматически не переключает.
Snapshot возвращает обязательную проблему `check_id=repeat-coverage` с причиной
`translation_propagation_disabled` для выбранных строк отключённого компонента.
Даже при PASS обоих судей такой остаток даёт `completed_with_exceptions`,
а не чистое `completed`; проблема остаётся в отчёте и причина доступна через API.

## Контракт серверной части, которую ещё нужно выпустить

Все маршруты ниже требуют существующую токен-авторизацию и object permissions.
Это целевой контракт для серверной реализации, а не описание выпущенного API.

| Операция | Маршрут относительно `/api/producer/` |
| --- | --- |
| Полный вычисляемый snapshot | `POST projects/{slug}/quality/snapshot/` |
| План унификации | `POST projects/{slug}/quality/repeats/plan/` |
| Опрос плана | `GET repeat-plans/{token}/` |
| Применение плана | `POST repeat-plans/{token}/apply/` |
| Опрос применения | `GET repeat-runs/{token}/` |
| Наблюдение неизвестного результата | `GET projects/{slug}/quality/operations/{operation_id}/` |

Snapshot POST не изменяет перевод и не вызывает платный LLM. Вход:
`{language, scope: {unit_ids}}`. Ответ: `complete=true`, `snapshot_hash`,
`scope_revision`, точный `unit_ids`, `revisions`, `judged_revisions`, `issues`.
Полный snapshot вычисляет glossary/check/repeat проблемы даже при отсутствии
сохранённых Check. Scope revision меняется при изменении любого релевантного
участника, состояния, source/context, glossary rule и repeat policy, включая ABA.

`revisions` содержит текущую opaque revision каждого выбранного unit.
`judged_revisions` содержит revision только тех unit, для которых есть актуальное
parsed evidence обоих судей с коллегиальным PASS. Факт ответа, FLAG/REJECT и
проверка старого текста не дают запись в этой карте.

Issue содержит `{group_id, kind, hard, advisory, unit_ids}`. `kind` равен
`glossary`, `repeat-drift` или `check`. Качество обязательных glossary/check
правил и необходимых repeat-групп определяет итог; advisory считается отдельно.

Decisions должны дополнительно возвращать `candidate_acceptable` и
`live_seat_results`. `seat_results` относится к кандидату, `live_seat_results`
— к текущему тексту. `candidate_acceptable=true` требует коллегиального PASS,
прохождения технических/hard glossary проверок и актуальных revision/permissions.
Этот gate повторяется сервером непосредственно при записи под блокировкой.

План принимает scope, language, issue_snapshot_hash, application_ids.
Возвращает token, status (`queued|running|ready|failed`) и groups. Каждая группа
содержит group_id, revision, unit_ids, outcome. Сервер выбирает допустимый канон
с приоритетом подходящего judge application, не разрешая запись вне scope.
Конфликтующие approved или judge-updated варианты получают объяснённый исход.

Применение возвращает token, status (`queued|running|completed|partial|failed`),
changed_unit_ids, results. Результат строки содержит unit, revision, outcome;
changed IDs должны точно соответствовать applied rows. Group-aware recheck
дополняет прежний ответ affected_unit_ids и affected_repeat_group_ids.

Mutating запросы start judge, candidate apply, recheck, repeat plan/apply передают
`Idempotency-Key` — UUID сохранённой QualityOperation. Сервер обязан атомарно
связать ключ с actor/project/body и сохранить результат. Наблюдение операции
возвращает null/404, `{state: pending}`, `{state: confirmed, result: ...}` или
`{state: failed}`. После неизвестного ответа визард только наблюдает: он не
повторяет POST, если не доказан его исход. Количество ожиданий ограничено.

Явные отказы 401/403/429 до принятия операции сохраняют возможность продолжения:
после восстановления доступа/лимита сначала проверяется отсутствие принятого
remote resource, затем допускается ограниченный повтор с тем же ключом.
Checkpoint состава scope, номера раунда и фазы выполняется одной транзакцией.

Quality JSON не содержит source/target/candidate text, prompts или raw evidence.
Для итогового файла используется отдельная обычная загрузка переводов.

## Последовательность

1. Проверить capabilities, импортировать kit/glossary и выполнить MT.
2. Сохранить точный scope и вычислить baseline snapshot.
3. Запустить один run с обоими судьями, получить решения.
4. Применить только acceptable candidates. Неполное покрытие становится
   исключениями отдельных строк; доступные строки продолжают обработку.
5. Перепроверить изменённые строки и получить новый snapshot групп.
6. Запросить server-side repeat plan с ID judge applications и применить
   допустимые группы. Остальные сохранить с причинами.
7. Перепроверить изменённых получателей и направить только их обоим судьям.
8. После новых исправлений пересоздать repeat plan по новому snapshot.
   Внешних repair-раундов максимум два; конечная оценка может быть judge-only.
9. Вычислить полный final snapshot. Открытые обязательные проблемы или отсутствие
   актуального двухместного PASS дают `completed_with_exceptions`.
10. Получить revision A, скачать данные, получить revision B. При расхождении
    повторить чтение один раз. Если стабильной пары нет, проверенный файл не
    публикуется: это техническая ошибка, не обычное строковое исключение.

`/api/producer/runs/{run_id}/quality/` визарда возвращает counts, unit census,
groups, residual_issues и scope_revision. Snapshot и исключения сохраняются
в SQLite; старые выгрузки не перезаписываются.

## Проверка готового проекта без MT

Локально добавлен `POST /api/producer/projects/{slug}/quality-runs/` визарда.
Он создаёт **новое** задание с `requested_mode=quality`. Запуск доступен через API;
отдельной формы выбора копии в UI пока нет. Карточка нового задания показывает
проверку качества, результаты двух судей и отдельный файл, без этапа MT.

Нужны обычная сессия визарда, CSRF и включённые operator flags полного цикла.
Тело запроса:

```json
{
  "parent_run_id": "id завершённого исходного задания",
  "language": "de",
  "scope": {"unit_ids": [101, 102]},
  "glossary_revision": "opaque scope_revision из текущего quality snapshot",
  "client_request_id": "новый UUID запроса"
}
```

`slug` — локальный проект **подготовленной копии**, не исходный проект.
Копию заранее создают штатным импортом с заполненными переводами. Должны
существовать owned `created-v2` binding и завершённое задание импорта копии с
подтверждённым журналом создания. Подключённый readonly-проект не становится
записываемым. Произвольный remote URL, проект или component map не принимаются.
Создание копии и применение исправлений к исходному проекту этот endpoint не делает.

Владелец, исходные ключи/тексты, язык и все ID сверяются с текущими данными
Weblate перед созданием задания и при продолжении worker. Scope должен точно
покрывать строки выбранного языка в лок-ките копии: без чужих ID, дубликатов,
частичного scope или пустых переводов. Максимум — 10 000 ID, как в snapshot API.

Поле `glossary_revision` исторически названо по глоссарию, но содержит полный
`scope_revision` Weblate, покрывающий также строки и применимые policies. Его
получают предварительным read-only `quality/snapshot/` Weblate для того же scope.
При изменении версии до запуска запрос/задание отклоняется, а не выполняется
на неподтверждённых данных. После запуска стандартный цикл пересчитывает
актуальные версии и обязательные остатки после каждого исправления.

Worker не импортирует строки, не меняет профиль/глоссарий/настройки проекта и
не вызывает MT. Перед каждым новым judge-run требуется `preparation.missing=0`
и полное `selected` покрытие. Если строка стала пустой, она не переводится
автоматически: остаётся техническая ошибка без обещания проверенного файла.
Weblate связывает judge start с оценкой и закрытым preparation scope; изменение
после оценки отклоняется как drift, а не расширяет оплаченный MT.

Два судьи, допустимые исправления и унификация работают **только в копии**.
Старое completed-задание, его snapshot и экспорт не изменяются. Новый экспорт
относится к выбранному языку; остальные ячейки лок-кита не объявляются проверенными.
Ссылка в карточке качества скачивает immutable экспорт именно этого run, а не
проектный snapshot предыдущего импорта. Исходные ключи/тексты и ID повторно
проверяются внутри окна revision A → download → revision B, не только до него.
При повторе того же `client_request_id` возвращается прежний run ID, в том числе
после завершения; другие входные данные с тем же ID дают `409`. Неизвестный ответ
после remote apply наблюдается с прежним ключом, повторная запись не создаётся.
Локальная отмена не означает завершение удалённого judge/repeat-run. Копия
остаётся зарезервированной до подтверждения всех принятых/неизвестных операций.
Новая попытка quality-only сначала наблюдает receipts и дочерние runs только
через чтение; при продолжающейся работе возвращает `409 run_active` без нового
платного запуска. Старое отменённое задание при этом не возобновляется.

## Сохранённый отчёт и цветная выгрузка

Локально добавлен пакет результата для новых заданий полного цикла версии 2.
Вместе с экспортом атомарно сохраняются финальные замечания, точные адреса
ячеек и версия проверки. Старые задания и готовые файлы не дополняются задним
числом. Серверный выпуск этой доработки требует отдельного согласования.

Карточка завершённого задания с пакетом показывает раздел «Отчёт качества»:
имя XLSX, сводку, состояния двух судей, фильтр и таблицу замечаний по 50 записей.
Фильтры: все, критические, непроверенные, рекомендации. Просмотр использует тот
же сохранённый результат, что скачиваемый отчёт, а не текущее состояние сервера.

- «Скачать итоговый файл» — лок-кит без новых служебных колонок/листов.
  Розовые целевые ячейки имеют обязательные остаточные замечания; жёлтые не
  получили подтверждённого одобрения обоих судей для текущей версии. При
  сочетании причин цвет розовый, обе причины перечислены в отчёте. Исправленные
  замечания не подсвечиваются. Исходники и соседние языки не закрашиваются.
- «Скачать отчёт» — XLSX с листами «Сводка» и «Замечания», адресами ячеек,
  причинами, состояниями двух судей и действиями. `parsed` означает только
  разобранный ответ, не одобрение. Недоступные подробности LLM не выдумываются.
- «Скачать всё» — ZIP с обоими XLSX и manifest.json, содержащим версии и SHA256.

API визарда, с существующей сессией владельца:

- `GET /api/producer/runs/{run_id}/export/?format=xlsx` — итоговый файл этого run;
- `GET /api/producer/runs/{run_id}/quality-report/?format=xlsx` — полный отчёт;
- `GET /api/producer/runs/{run_id}/quality-report/?format=json&category=all&page=1&page_size=50`
  — просмотр; category: `all`, `blocking`, `unverified`, `advisory`, размер
  страницы 1–100. Фильтр не меняет общую сводку или скачиваемый XLSX;
- `GET /api/producer/runs/{run_id}/result-bundle/` — общий ZIP.

Просмотр и скачивание не запускают MT, судей и внешние запросы. При отсутствии
пакета возвращается 404, а не пустой «успешный» отчёт. Техническая диагностика
остаётся отдельным JSON-файлом. Исправления выполняются в подготовленной копии
Weblate; затем создаётся новое quality-only задание без повторного MT.

Текущий Weblate возвращает severity сохранённого judge-run вместе с revision
текущей строки, но не отдельную revision текста, к которому относится severity.
Поэтому такая major/critical-оценка сама по себе не является основанием розовой
заливки: без актуального двухместного PASS ячейка жёлтая. Розовая заливка
основана на обязательных проблемах финального снимка. Для надёжного выделения
отдельного критического verdict судьи API должен дополнительно предоставить его
связь с текущей версией текста; это отдельная серверная доработка, не часть
данного выпуска. Поля reason/check_id сохраняются раздельно. Адрес листа в
отчёте соответствует фактическому имени вкладки итогового XLSX, даже после
переименования одинаковых имён из разных входных файлов.

Изменение не восстанавливает оформление/макросы исходного Excel: сохраняется
прежний экспорт данных. Превышение лимита длины ячейки Excel или запрещённые
управляющие символы явно блокируют публикацию пакета вместо молчаливого усечения.

## Ожидание ограничения запросов HTTP 429

При ответе Weblate `429` worker сохраняет прогресс и ставит текущее задание
на паузу, не переводя его в ошибку. `Retry-After` поддерживает количество
секунд и HTTP-дату. Если заголовок отсутствует или некорректен, используется
увеличивающаяся задержка 5, 10, 20 секунд и далее, максимум 300 секунд.
Даже при нулевой задержке следующий запрос отправляется не раньше чем через
секунду. Ожидание не удерживает worker в `sleep`: срок следующей попытки
сохраняется в SQLite и остаётся действительным после перезапуска.

Поля `rate_limit.waiting`, `attempt`, `retry_after`, `next_retry_at` видны в
карточке запуска через API и в диагностическом JSON. Данные уже подтверждённых
операций, частичное покрытие MT и исходные сроки наблюдения не обнуляются.
После паузы worker сначала наблюдает удалённое состояние: уже принятый POST
или запрос с неизвестным исходом автоматически повторно не отправляется.
Если сам POST был определённо отклонён ответом 429, после проверки удалённого
состояния допускается его повтор. Quality API при этом сохраняет прежний
`Idempotency-Key`. Лимит повторов неизвестного исхода и отказов доступа
не отменяется; определённые отказы 429 обрабатываются отдельным ожиданием.

Задание можно отменить во время паузы без ожидания её окончания. Это отменяет
дальнейшие шаги визарда, но не отзывает уже принятый Weblate перевод.

Изменение применяется к будущим проходам обновлённого worker. Уже остановленное
старой версией задание не возобновляется установкой автоматически: после
согласованного обновления нужно продолжить именно сохранённое задание, а не
создавать повторный запуск. Рабочий сервер нельзя обновлять без отдельного
разрешения и проверенного бэкапа.

## Резервная копия и откат

Перед работой сохранён baseline Git bundle и source ZIP с проверкой восстановления.
Пути и SHA256 находятся в локальном checkpoint `BASELINE.md`; исходный commit
`3a55261336ecc72fe8b8d2e8abefb5f78b81a4f5`.

Миграция 0003 только добавляет quality_groups. Перед обновлением существующей
SQLite приложение создаёт её online backup в `WIZARD_DATA_DIR/backups/migrations/`,
проверяет `PRAGMA integrity_check` и сохраняет SHA256 manifest. Ошибка бэкапа
прерывает миграцию. Это не заменяет полный pre-deploy backup файлов, конфигурации
и секретов: использовать существующие `deploy/backup.sh` и проверку восстановления.

Для отката сначала остановить именно визард и его workers, сохранив текущее
состояние. Восстановить предыдущий release и соответствующую резервную БД вместе
с файлами данных; не запускать старый код с alembic revision 0003. Workers оставить
выключенными до сверки незавершённых удалённых операций. `deploy/rollback.sh`
поддерживает полный откат; не выполнять его без согласованного развёртывания.
Восстановление визарда не отменяет удалённые изменения Weblate: для них нужен
штатный audited undo. Никогда не выполнять reset/overwrite пользовательских
