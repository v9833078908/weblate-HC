# Восстановление импорта после остановки процесса

Добавление исходных строк из monolingual PO повторно использует разобранное
хранилище только для двух представлений того же загруженного файла. Обычный
импорт переводов и другие форматы сохраняют свой путь разбора. Обработка fuzzy
копирует изменяемую единицу, сохраняя исходный шаблон.

## Блокировка компонента

`component:update` использует транзакционную advisory-блокировку PostgreSQL на
том же соединении, что и изменения компонента. Блокировка сохраняется до конца
внешней транзакции. PostgreSQL освобождает её при commit, rollback или закрытии
соединения погибшего процесса. Живой приостановленный процесс сохраняет
исключительность; таймера передачи владения нет. Ожидание другим запросом
по-прежнему ограничено пятью секундами.

Файлы репозитория дополнительно защищает существующая `repository.lock`.
Механизмы блокировки других областей, включая Redis и файловый fallback,
сохраняются. Потеря соединения с БД прерывает транзакцию; это не успешный импорт.

## Условие выпуска и отката

Старые процессы используют Redis для `component:update`, новые — PostgreSQL.
Эти поколения нельзя запускать одновременно: их блокировки друг друга не видят.
При выпуске и откате сначала остановить приём изменяющих запросов, дождаться
завершения или остановить все старые web- и Celery-процессы, затем запустить
все процессы одной версии и восстановить приём запросов. Обычный rolling restart
для этого перехода не подходит. Старые Redis-ключи не удалять вручную: после
полной остановки старой версии они не участвуют в новом механизме.

При неизвестном результате `add` проверить историю и повторить загрузку:
уже существующие ключи пропускаются. Для других методов сначала проверить
результат; этот контракт повторения относится только к добавлению строк.

В этом PR production не изменяется. Измерения и сценарии проверки:
`docs/product/measurements/2026-10-30-import-memory-and-interruption.md`.
