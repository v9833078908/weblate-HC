# План реализации внешнего визарда на FastAPI для БДХК и Weblate

> Для исполнителя: выполнять этапы последовательно, используя навык `executing-plans`. Отмечать готовые шаги в этом документе. Реализация одобрена владельцем; публикация на production и платная приёмка требуют отдельного согласования этапа 7.

**Дата:** 2026-10-01. **Статус:** реализация одобрена владельцем; этапы 1–7 выполнены; визард установлен по LAN-адресу, реальный немецкий тест 5/5 завершён. PID/health действующего БДХК сохранены. Обновлено 2026-10-02.

**Цель:** пользователь открывает визард по внешнему сетевому адресу, получает данные карточки БДХК, загружает локкит, запускает перевод через внешний Weblate и скачивает результат.

**Архитектура:** разработка в `D:\bdhc_wizard\repo`, установка на Linux-сервер БДХК в `/opt/bdhc/weblate-wizard`. Отдельный FastAPI обслуживает существующую форму визарда и собственный API; отдельный worker выполняет перевод через Weblate. Визард читает БДХК через действующий фасад и хранит свои данные отдельно.

**Стек:** Python >=3.12, FastAPI, Pydantic 2, HTTPX, SQLAlchemy 2, Alembic, Uvicorn, SQLite WAL; React 19, TypeScript, Vite, Node 24 LTS, pnpm 11.19.0; systemd. Зависимости фиксируются собственными lockfile.

**Спецификация:** `docs/product/designs/external-fastapi-wizard-scope.md` в `D:\bdhc_wizard`. Этот документ заменяет Windows-сценарий прежнего плана для данного сервера. Подготовленный комплект исходников сохраняет ценность; Windows-скрипты развёртывания в новый проект не переносятся.

## Основания и ограничения

- База переноса: `D:\Weblate\fastapi-wizard-transfer-2026-10-01`; это исходники и справочные материалы, а не готовое приложение FastAPI.
- Из роадмапа реализуется БДХК 3.1 и доработка текущего потока визарда до рабочего перевода. Новые сценарии stores, extraction, judge, split, письма и финансовые отчёты не добавляются.
- SSH-проверка 2026-10-01 подтвердила Linux-сервер `192.168.0.180`, основной API `127.0.0.1:19100`, UI карточек `0.0.0.0:18501`, фасад `0.0.0.0:19101`. Эти данные перепроверяются перед установкой.
- Работающий API запускается из `/opt/bdhc/producer-interviewer-primary/repo`. В этом каталоге не обнаружен `.git`; его нельзя использовать как рабочую копию для разработки.
- Основной API, UI карточек, фасад и Telegram-бот не перезапускаются и не изменяются для установки визарда. Отдельная БД, venv, файлы, секреты и службы визарда.
- Внешний UI и API обязательны. Доступ с рабочего компьютера проверяется до приёмки; `localhost` на сервере не считается результатом.
- До запуска — только необходимые функциональные проверки и короткая приёмка. Нагрузочные, длительные и расширенные проверки выполняются после запуска.

## Внешний адрес

Предлагаемый отдельный сетевой порт — `18511`, после проверки свободы. Для корпоративной сети аналог существующего UI: `http://192.168.0.180:18511/console/`; API того же приложения — `/api/producer/`. Это предварительный адрес, сервис сейчас по нему не объявляется работающим.

Если нужен интернет, публикуется HTTPS-адрес `https://<выделенное-имя-визарда>/console/` и API на том же origin. Назначаются DNS, сертификат, обратный прокси и при необходимости NAT/правила маршрутизатора. Backend в этом варианте может слушать только loopback: внешнюю доступность обеспечивает прокси. Расширять публикацию основного API 19100 и фасада 19101 не требуется.

Уточнение сети запрошено у владельца. Если ответа нет, план предусматривает оба варианта и не объявляет доступ из интернета согласованным или проверенным. Перед публикацией фиксируется один фактический адрес. IP `192.168.0.180` — частный; сам по себе он не обеспечивает доступ из интернета. Прежний публичный адрес локального Weblate не используется автоматически для нового сервера.

### Создание и повторное использование проекта тест

В локальной БД визарда запись «тест», черновики и задания создаются самим сервисом. Во внешнем Weblate визард создаёт отдельный проект с отображаемым именем **«тест»**, сохраняя возвращённые идентификаторы. Для новых тестовых проектов технический slug — `test-<уникальный-идентификатор>`; идентичность хранится по slug, однако модель внешнего Weblate требует уникальности и отображаемого имени. Поэтому точное имя «тест» сейчас сохраняется; если оно занято, создание прекращается без изменения существующего проекта. Разрешение имени «тест — <короткий ID>» для повторных независимых прогонов запрошено у владельца и ещё не получено. Существующий проект с таким названием автоматически не выбирается и не перезаписывается. Повторный запрос одного запуска возвращает тот же run; новый тестовый прогон создаётся явным действием и имеет свой run_id. Источник данных хранится как metadata `Star Troopers`.

После запуска сервиса этот пример можно снова загрузить и пройти обычным визардом, создав проект «тест» и выбрав тестовую карточку БДХК. Специальный API записи в БДХК и отдельный обход прав для тестов не добавляются. Для разработки и приёмки повторно используются предоставленный исходник и согласованная небольшая выборка видимых строк. Тестовые проекты и результаты не удаляются автоматически; затраты и повторный запуск MT подтверждаются обычным действием пользователя.

### Когда нужна карточка тест в БДХК

**Уточнение владельца при реализации:** для проверки реального чтения и автозаполнения разрешена заполненная карточка **Dead Shell**, `title_id=92be6259-40cd-51df-a6ba-4eb54a14f261`, UI `http://192.168.0.180:18501/?game=92be6259-40cd-51df-a6ba-4eb54a14f261`. GET v1/v2 через фасад с действующим токеном выполнены успешно; схема `12.7`, context_hash присутствует, сопоставлены шесть полей анкеты без предупреждений. Отдельная карточка «тест» поэтому не является условием проверки автозаполнения. Dead Shell служит отдельным примером интеграции; контекст этой игры не подставляется автоматически в перевод Star Troopers. Отображаемое имя тестового проекта визарда/Weblate остаётся **«тест»**.

Разработка и проверка автозаполнения не требуют создания карточки «тест»: разрешённая карточка Dead Shell проверена живыми GET и через поиск→resolve→preview→apply в локальном UI. Для реального перевода Star Troopers нужно явно подтвердить подходящую анкету; контекст другой игры не выбирается автоматически. При желании отдельная тестовая карточка создаётся штатными средствами БДХК, вне read-only интеграции. Прямая запись SQL и создание карточки через фасад в этот выпуск не входят.

## Критерий готовности

Визард доступен пользователю по согласованному внешнему адресу; карточка БДХК заполняет анкету с подтверждением; пустая/недоступная карточка допускает ручной ввод. На отдельном проекте Weblate с именем «тест», используя данные Star Troopers, пройден один реальный цикл; скачанный локкит содержит переводы и исходные ключи видимых листов, готовые target-значения сохраняются. Скрытые и veryHidden-листы не участвовали ни в одной стадии. Для полной приёмки автозаполнения пройден реальный GET-сценарий по отдельной карточке БДХК «тест». Ручная анкета при отсутствии карточки подтверждает лишь соответствующую часть контура. Сценарий доступен через обычный визард после запуска сервиса, без специальных привилегий и подмены production-проектов. Задание переживает перезапуск визарда. Действующие службы БДХК сохраняют работоспособность; новый сервис имеет самостоятельные запуск, остановку и откат.
