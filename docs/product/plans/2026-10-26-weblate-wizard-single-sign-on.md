# Вход в Wizard через учётную запись Weblate

Статус: **согласован; реализован и проверен локально, замечания ревью исправлены**.
Дата: 26 октября 2026 года. Production не изменён.

Результаты: `docs/operations/reports/2026-10-26-wizard-sso-local-validation.md`.

## Цель и границы

Пользователь нажимает «Войти через Weblate», проходит существующий вход Weblate
с теми же логином, паролем и дополнительными факторами, затем возвращается в
Wizard. При уже действующей сессии Weblate повторный ввод пароля обычно не нужен.
Wizard хранит собственную сессию и ссылку на подтверждённую внешнюю личность,
но не пароль Weblate и не его копию/хеш.

План объединяет вход и пользовательскую авторизацию операций: сохранение общего
служебного API-токена для вошедших пользователей не считается завершением работы.
Новая авторизация не меняет алгоритм перевода, маршрутизацию моделей или учёт оплаты.

Исходники для анализа:

- Weblate: `a6ec593c31f18e4808d541db2ea3926790833d7f`.
- Wizard: `c48c1edacb83a06f52610d657ced9d6aaafe1b67`.
- В Weblate API сейчас Token/Bearer/Session; готового OIDC-провайдера в кандидате нет.
- В Wizard локальные пользователи и владельцы записей привязаны к `username`;
  API-клиенты и worker получают общий токен из конфигурации.

Это анализ локальных копий, а не подтверждение фактической конфигурации production.
В документе пути Weblate относятся к его репозиторию, пути `backend/`, `console/`
и `tests/` — к отдельному репозиторию Wizard.

## Принятое устройство

Weblate выступает OIDC-провайдером, Wizard — конфиденциальным клиентом.
Использовать Authorization Code, S256 PKCE, `state`, `nonce` и серверный обмен кода.
Не писать собственную криптографию или протокол входа. Библиотеки-кандидаты:
`django-oauth-toolkit==3.4.1` для Django и `Authlib==1.9.1` для FastAPI/httpx;
точные зависимости закрепить lock-файлами после проверки совместимости и уязвимостей.
Если этот набор несовместим, согласовать корректировку, а не заменять протокол
самодельной передачей пароля.

Добавить ограниченную интеграцию в текущий fork; не обновлять Weblate целиком
до upstream 2026.11. Официальная реализация OIDC в 2026.11 — источник для сравнения
контрактов и защит, а не разрешение перенести остальные изменения релиза.

OIDC подтверждает личность. Доступ к API — отдельное расширение: OAuth access token
клиента Wizard принимается только на явном перечне используемых им маршрутов,
с проверкой scopes и обычных актуальных прав пользователя Weblate. ID token
не является пропуском в API. Существующие Token/Bearer/Session-клиенты сохраняют
поведение. Делегированному токену запрещены произвольный API, администрирование
пользователей и чтение ключей machinery.

Начальная политика сроков, подлежащая согласованию вместе с планом:

| Объект | Политика |
| --- | --- |
| Транзакция начала входа в Wizard | 10 минут; серверное хранение; одноразовое использование |
| Authorization code | 60 секунд; одноразовый, привязан к клиенту, callback и PKCE |
| OAuth access token | 5 минут |
| Refresh grant | Ротация, обнаружение повторного использования; абсолютный предел 24 часа, не продлеваемый ротацией |
| Сессия интерфейса Wizard | 8 часов, серверное хранение, новый идентификатор после входа |

Закрытие браузера само по себе не отменяет уже разрешённое фоновое задание.
Явный выход из Wizard отзывает связанную делегацию: новые внешние шаги связанных
заданий приостанавливаются. Уже принятый провайдером запрос может завершиться;
его ответ и квитанция сохраняются. Выход из Weblate не объявляется автоматическим
выходом из Wizard: общего logout в объём этого этапа не включать. Блокировка
пользователя, отзыв делегации и изменение прав проверяются Weblate при API-вызовах
и перед исполнением внешнего шага worker.

## Обязательные ограничения

- До локальных изменений сохранить исходные коммиты и приватную копию локальных
  изменяемых БД/конфигурации. Не создавать новые выгрузки production этим планом.
- Реализацию вести в отдельных ветках `y.bazenkov/...`, публикацию и авторство —
  от имени `y.bazenkov`. Не включать секреты в Git. Не выполнять merge в main.
- Production, его службы и shared dev-stack не менять без отдельного разрешения.
- Старое задание с неизвестным результатом не возобновлять ни миграцией, ни входом.
- Сохранить 1662 готовых перевода, журналы, квитанции, ключи операций и блокировки
  неизвестных результатов. Перенос личности не меняет первоначального плательщика/актора квитанции.
- В SSO-режиме запрещён неявный откат на общий токен или локальный пароль.
- Локальные права владения Wizard дополняют права Weblate, а не заменяют их.
  Вход через Weblate не открывает черновики других пользователей Wizard.
- HTTPS обязателен для реального входа; HTTP допустим только в изолированных
  тестах на loopback без реальных пользователей и ключей.

остановить новые workers и вернуть сохранённые образы/конфигурацию. Аддитивные
таблицы identity/token оставить, если проверена совместимость старого кода;
иначе выполнять заранее отрепетированный откат схемы. Старый worker не включать
с общим внешним токеном до проверки изоляции. Не восстанавливать устаревшую БД
поверх новых переводов и квитанций; полное восстановление допустимо лишь при
доказанном отсутствии новых записей после согласованного снимка. Архив с ключами
и новые данные сохраняются для сверки, а не удаляются при откате.

## Критерии завершения

- Обычный пользователь входит в Wizard через Weblate, не заводя второй пароль.
- MFA, блокировка аккаунта и права Weblate не обходятся через Wizard/API/worker.
- Пользователь не видит чужих локальных черновиков или недоступных ему проектов.
- Изменение пароля выполняется в Weblate; синхронизация копий паролей отсутствует.
- Истечение/отзыв доступа не теряет переводы, не открывает доступ через общий
  токен и не создаёт повторного платного запроса.
- Старое неизвестное задание остаётся изолированным; 1662 перевода и квитанции сохранены.
- Независимые пользователи Weblate продолжают прежнюю работу.
- Подготовлен проверенный порядок установки и отката; production пока не изменён.
