# Надёжная подгрузка строк в matrix view

**Дата:** 2026-09-16. **Статус:** реализовано в ветке
`fix/matrix-pagination-recovery` (ворктри `.worktrees/matrix-pagination-recovery`);
задачи 1-3 выполнены, узкие server-тесты (`test_matrix_load`,
`test_matrix_load_pagination_offsets`) и Selenium-регресс
(`test_matrix_load_more_pagination`, реальный проход в Chrome, включая
offline-сбой и повторную загрузку без пропуска/дубля) зелёные, `prek` по
изменённым файлам чист (кроме уже существующих repo-wide findings в
`reuse lint`/`typos`, не связанных с этим изменением). Деплой на прод не
выполнялся и требует отдельного `DEPLOY-OK`.

## Цель

Matrix view загружает строки порциями по 20 через infinite scroll. Если один
запрос `fetch()` завершается ошибкой, текущий код оставляет индикатор
`#loading-next` видимым. Следующие вызовы `loadMatrix()` считают это
признаком уже идущей загрузки и немедленно завершаются. Пользователь остаётся
на первой либо промежуточной порции строк без объяснения, возможности повторить
запрос или перейти к следующей порции.

Нужно сохранить автоматическую подгрузку при прокрутке, но сделать matrix view
восстанавливаемой после сетевой или серверной ошибки. Пользователь должен
видеть понятный статус и иметь явную, доступную с клавиатуры кнопку для
загрузки следующей порции. Повторный запрос обязан использовать тот же offset:
сбой не должен пропускать 20 строк.

## Наблюдаемые факты

- `weblate/templates/matrix.html` отдаёт пустой `<tbody>` и скрытый якорь
  `#matrix-load` с `data-offset="0"`. Первая порция тоже приходит AJAX-запросом,
  не рендерится сервером вместе со страницей.
- `weblate/static/loader-bootstrap.js:548-574`:
  1. показывает `#loading-next`;
  2. **до** выполнения запроса увеличивает `data-offset`;
  3. прячет индикатор только в успешной ветке `.then()`;
  4. не проверяет `response.ok` и не имеет `.catch()`/`.finally()`.
- Поэтому сетевой reject оставляет индикатор видимым навсегда. При следующем
  scroll handler условие `getComputedStyle(loadingNext).display !== "none"`
  возвращает `true`, и загрузка больше не запускается. А при HTTP 4xx/5xx
  HTML ошибки ошибочно вставляется в `<tbody>` как будто это строки матрицы.
- Локальная воспроизводимая проверка на `space-arena/glossary`: после успешной
  загрузки 20 → 40 строк искусственно вызванный offline reject оставил
  `#loading-next` как `inline-block`; ещё восемь прокруток после восстановления
  сети не изменили число строк.
- На production `victory-banner/victory-banner-glossary` содержит 156 source
  units, source language — `ru`; `en`, `de`, `es` и `pt_BR` из исходного URL
  допустимы. В чистом Chrome тот же URL штатно загрузил 156/156 строк.
  Батарея на девяти production glossary components (95–557 строк) также
  завершилась без сбоев при стабильной сети. Это исключает лимит конкретного
  проекта, но не скрытый failure path одного AJAX-запроса.
- Matrix view никогда не имел обычной пагинации с номерами страниц или ссылкой
  «следующая». Только скрытый спиннер и scroll trigger делают механизм
  неочевидным и не дают fallback, если скролл не происходит.
- Код matrix loader и его шаблоны не менялись в истории форка с исходного
  snapshot `711df135`; исправление закрывает давнюю унаследованную хрупкость,
  а не откат недавнего коммита.

## Решение и пользовательский контракт

1. Автоматическая подгрузка по прокрутке сохраняется. Она остаётся
   прогрессивным ускорением, а не единственным способом увидеть следующие
   строки.
2. После первой успешной порции под таблицей появляется одна обычная
   secondary-кнопка «Load more» (`type="button"`). До последней порции она
   активна, во время запроса disabled, после последней порции скрыта. Кнопка
   не является ссылкой на AJAX endpoint и не вызывает навигацию страницы.
3. Рядом живёт отдельный status element с `role="status"` и
   `aria-live="polite"`:
   - начальный и успешный idle-state не добавляют лишнего текста;
   - во время запроса: «Loading more strings…»;
   - при ошибке: «Could not load more strings. Try again.».
4. После любого reject, JSON/text parse failure или HTTP non-2xx:
   - индикатор скрывается;
   - кнопка вновь становится активной;
   - `data-offset` остаётся прежним;
   - в `<tbody>` не вставляется ответ ошибки;
   - status сообщает об ошибке. Пользователь может повторить тот же запрос
     кнопкой или следующей прокруткой.
5. После успешного ответа offset увеличивается ровно на размер запрошенной
   порции (сегодня фиксированные 20). Успех остаётся единственным событием,
   которое продвигает cursor.
6. Если сервер помечает последнюю порцию `#last-section`, hidden loader,
   кнопка и status не обещают больше строк. Пустой успешный ответ без
   `#last-section` не должен оставлять бесконечный запросный цикл: клиент
   рассматривает его как terminal state и скрывает кнопку. Это защитный
   fallback для пустого компонента или неполного успешного HTML-ответа.
7. Не добавлять автоматических повторов с таймерами. Они создадут
   неконтролируемую нагрузку и скрывают от пользователя состояние сети.
   Retry — только явный следующий scroll/click.
8. Не менять API URL, форму выбора языков, серверную авторизацию, размер
   порции или порядок языковых колонок.

## Задача 1. Сделать footer matrix view доступным fallback-контролом

**Результат.** Пользователь видит, что есть ещё строки, и может загрузить
следующую порцию даже если scroll event не сработал. Контролы корректно
объявляют loading/error state экранному считывателю.

**Файл:** `weblate/templates/matrix.html`.

**Изменения.**

- Заменить текущий единственный `<td colspan="3" class="loading-icon">` на
  footer cell с динамическим colspan:
  `{{ translations|length|add:1 }}`. Это покрывает source column и все
  выбранные переводы, а не только первые три.
- Оставить `{% loading_icon "next" %}` как визуальный индикатор текущего
  запроса.
- Оставить `#matrix-load` как скрытый holder endpoint и cursor. Не удалять
  `href`/`data-offset`: ими пользуется JavaScript.
- Добавить `<button id="matrix-load-more" class="btn btn-secondary"
  type="button" hidden>` с `{% translate "Load more" %}`. После первой
  успешной порции JavaScript снимает `hidden`; без JavaScript контрол не
  показывает неработающий AJAX endpoint. Не полагаться на CSS-класс `hidden`,
  которого Bootstrap 5 не определяет как семантический hidden state.
- Добавить рядом пустой видимый status element `id="matrix-load-status"`,
  `role="status"`, `aria-live="polite"`. Он получает текст только во время
  loading/error, чтобы не засорять чтение таблицы.
- Footer не должен выглядеть как primary action. Следовать `DESIGN.md`:
  secondary-кнопка, без теней и новых цветов; error — текстом плюс уже
  существующий danger alert/toast, не только красным цветом.

**Проверка разметки.**

- При четырёх выбранных языках footer cell занимает пять колонок.
- Табуляция доходит до «Load more», Enter/Space запускают загрузку.
- При отключённом JavaScript кнопка не обещает работающий переход: использовать
  `hidden` в исходной разметке либо disabled-контрол с понятным fallback
  только после JS-init. Выбрать первый вариант, если контракт приложения
  остаётся AJAX-only.

## Задача 2. Сделать `loadMatrix()` идемпотентной и failure-safe

**Результат.** Никакая ошибка запроса не блокирует последующие загрузки и не
пропускает строки.

**Файл:** `weblate/static/loader-bootstrap.js`.

**Изменения.**

- Рядом с `loadMatrix()` ввести маленький scoped `matrixLoading` flag и
  helper-функции для:
  - получения `#matrix-load`, `#loading-next`, `#matrix-load-more` и
    `#matrix-load-status`;
  - переключения busy state (спиннер visible, кнопка disabled, loading text);
  - переключения idle/error/finished state.
  Не создавать новый общий loading registry и не менять
  `increaseLoading`/`decreaseLoading`.
- Перестроить `loadMatrix()` так, чтобы:
  1. сначала проверять наличие loader и terminal/busy state;
  2. сохранять текущий numeric offset в локальной переменной;
  3. начинать busy state;
  4. выполнять `fetch`;
  5. явно выбрасывать error для `!response.ok`, до чтения/вставки body;
  6. вставлять response HTML только после успешного `response.text()`;
  7. лишь затем увеличивать `loader.dataset.offset` на 20;
  8. анализировать результат: если появился `#last-section` **или** response
     содержит ноль `<tr>`, переходить в finished state и скрывать кнопку;
  9. в `.catch()` возвращать idle state, сохранять offset и сообщать
     локализованную ошибку через status + `addAlert`;
  10. в `.finally()` гарантированно скрывать spinner и снимать busy state,
      кроме terminal state, где кнопка уже hidden.
- Не использовать `response.statusText` как единственный user-facing текст:
  это непереводимо и часто пусто. Использовать `{% translate %}` невозможно
  в `.js`; добавить строку через существующий JavaScript i18n wrapper
  `gettext("Could not load more strings. Try again.")`.
- Повесить click handler на `#matrix-load-more` только в существующей
  `if (document.querySelector(".matrix") !== null)` ветке. Handler вызывает
  ту же `loadMatrix()`, что и scroll — два независимых кода загрузки не
  создавать.
- Scroll listener сохранить. В busy/finished states он no-op. После error
  следующий scroll допустимо повторяет request с тем же offset.
- Не менять поведение других `fetch` в этом файле.

**Крайние случаи.**

- Первый запрос (offset 0) не удался: tbody остаётся пустым, кнопка становится
  доступной для первого retry, status сообщает ошибку.
- Ошибка после нескольких порций: уже вставленные строки остаются, повтор
  добавляет ровно следующую, а не дублирует и не пропускает её.
- 401/403/404/500: body не вставляется в таблицу; пользователь получает тот
  же recoverable error-state.
- Компонент без строк: первый пустой успешный ответ завершает loader,
  скрывает кнопку и не создаёт вечный scroll loop.
- Компонент содержит меньше 20 строк: после первой успешной порции loader
  terminal, кнопка скрыта.

## Задача 3. Добавить регрессионные тесты

**Результат.** Тесты покрывают API terminal state и пользовательский
scroll/retry contract, включая самый опасный failure path.

### Серверные тесты

**Файл:** `weblate/trans/tests/test_views.py`, рядом с `test_matrix_load`.

- Не менять `matrix_load()` и его slice `offset : offset + 21`: сервер уже
  корректно отмечает последнюю непустую пачку, включая число строк, кратное
  20. Клиентский empty-response fallback из задачи 2 нужен только для
  пустого компонента либо повреждённого успешного ответа.
- Создать 21+ source units с уже используемыми тестовыми helper-ами базового
  `ComponentTestCase`; не менять общие фикстуры ради этой проверки.
- Проверить:
  - offset 0 возвращает 20 `<tr>` и не имеет `id="last-section"`, если есть
    ещё строки;
  - final непустой batch имеет existing terminal marker;
  - каждый response содержит только строки запрошенного диапазона, без
    server-side дублей.
- Сохранить существующий assertion на два `trans_unit` SELECT query: изменение
  terminal marker не должно ухудшить query budget.

### Browser/Selenium тест

**Файл:** `weblate/trans/tests/test_selenium.py`, рядом с существующим
matrix screenshot flow.

- Создать компонент с минимум 21 строкой и двумя target languages либо
  расширить локальную matrix setup в этом тесте, не используя production data.
- Открыть matrix URL, дождаться первых 20 rows.
- Нажать `#matrix-load-more`, дождаться 21-й строки (или счётчика `>20`);
  подтвердить, что next portion стала видна. Это pin для доступного fallback,
  не зависящий от viewport/scroll timing.
- Проверить, что после final batch кнопка скрыта/не отображается и status не
  говорит, что загрузка продолжается.
- Если текущий Selenium infrastructure допускает interception, симулировать
  failed `/js/matrix/` request, затем повторный click:
  - error text виден;
  - кнопка снова enabled;
  - offset не продвинут после failed request;
  - retry добавляет следующую, а не пропущенную или дублированную порцию.
  Если interception нестабильно или отсутствует, вынести client state
  transition в маленькую тестируемую JS-функцию **только если** это не
  усложняет production code; иначе зафиксировать failure case browser smoke
  через CDP в `analysis/probes/`, не добавляя нерелевантный тестовый фреймворк.

### Static quality checks

- `uv run prek run --files weblate/templates/matrix.html
  weblate/static/loader-bootstrap.js weblate/trans/tests/test_views.py
  weblate/trans/tests/test_selenium.py`
- Узкий server test:
  `uv run pytest weblate/trans/tests/test_views.py -k matrix`.
- Если Selenium browser доступен в CI/local setup, запустить добавленный
  Selenium test. Если нет — явно отметить это в итоговом отчёте, не выдавая
  его за пройденный.
- После изменения статики выполнить `collectstatic` только в разрешённой
  изолированной test/dev среде, не перезапуская shared dev stack без
  отдельного разрешения.

## Ручная проверка до merge

В локальном dev instance с glossary >40 строк и двумя или более языками:

1. Открыть matrix view. Первая порция загружается автоматически.
2. Не прокручивая страницу, нажать «Load more» — появляются строки 21–40.
3. Прокрутить вниз — следующие порции продолжают приходить автоматически.
4. В DevTools временно перевести сеть Offline перед очередной порцией.
   Таблица не получает error HTML, spinner прекращает работу, видны error
   status и активная кнопка.
5. Вернуть сеть, нажать «Load more». Приходят именно пропущенные 20 строк,
   без дублей и без пропуска.
6. Дойти до конца. Кнопка исчезает, запросы больше не отправляются.
7. Пройти кнопкой с клавиатуры, проверить visible focus и `aria-live` в
   accessibility tree.

## Не входит в этот план

- Обычная нумерованная pagination, переход к конкретной странице или
  изменение размера batch.
- Автоматический backoff/retry, persistent loader state или фоновые задачи.
- Изменение matrix API, языковой формы, разрешений или структуры glossaries.
- Деплой на production. Он требует отдельного явного одобрения после
  реализации и проверки.

## Критерий готовности

Исполнитель может считать изменение завершённым только когда:

- один failed matrix AJAX request не блокирует ручной или scroll retry;
- retry использует прежний offset и не создаёт пропусков/дублей;
- у пользователя есть доступный явный fallback-контрол и понятный статус;
- matrix не продолжает запрашивать пустые страницы после пустого успешного
  ответа;
- узкие server tests и форматирование проходят, а browser verification
  отражена честно;
- изменённые user-facing строки локализованы;
- изменения закоммичены и отправлены согласно `AGENTS.md`, но production
  deploy не выполняется без отдельного разрешения.
