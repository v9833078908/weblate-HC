# Поддержка exact при импорте глоссария

Дата: 2026-09-08.
Статус: план подготовлен; реализация и развёртывание не разрешены.

## Цель и основания

При загрузке таблицы глоссария разрешить `exact` в существующей колонке `flags`, показать его в предпросмотре и сохранить действующее правило точной формы перевода после создания компонента или добавления новых терминов.

Основания: запрос пользователя в чате; `docs/product/guides/loc-kit-ingest.md`; `docs/product/plans/2026-08-31-02-loc-kit-glossary-source-flags.md`. Правила работы: `AGENTS.md`.

Согласованная политика: никаких автоматически назначаемых пометок. Интервью собирает требования нейтрально; фраза «Обычно особые правила не нужны» удалена из managed skill отдельно от этого плана.

## Выбранный подход и границы

Сохранить формат `<source>,<targets...>,explanation,flags`. `exact` в общей колонке означает применение правила к каждому импортируемому переводу этой строки. Отдельный русский-only exact в многоязычном файле этим контрактом не выражается. Для него нужна отдельная языковая настройка в Weblate; новые колонки и синтаксис `ru:exact` не вводятся.

Ключевое разделение: расположение правила в CSV не определяет область действия в модели. `exact` должен сохраняться на целевых Unit, а не становиться наследуемой пометкой исходного Unit. Существующая семантика `get_glossary_term_modes` остаётся неизменной. Не добавлять `exact` в `SOURCE_SCOPED_MODES`.

Не входят: изменение алгоритма glossary matching, контроль регистра, новая схема языковых колонок пометок, автоматическое назначение ограничений, переработка форматов исходных выгрузок, изменение старых терминов append-only, продакшен-команды и деплой. Добавленные позднее языки не наследуют exact автоматически.

## Наблюдаемая архитектура

- `loc_kit_ingest/parser.py:GLOSSARY_SOURCE_FLAGS` допускает только `read-only` и `forbidden`; разбор record-map выдаёт `tbx.invalid_source_flag` для exact.
- `loc_kit_ingest/model.py:GlossaryTerm.source_flags` и соответствующее поле профиля несут общую колонку пометок. Сохраняем этот существующий контракт без переименования схемы; документируем, что exact требует целевого применения.
- `loc_kit_ingest/writer.py` пишет `weblate-flags` в TBX и проверяет их при обратном чтении.
- `weblate/trans/loc_kit.py:GlossaryTermPreview`, `validate_glossary_profile` передают пометки в предпросмотр; шаблон `weblate/templates/trans/loc_kit_glossary_preview.html` показывает их.
- `append_glossary_terms` сейчас объединяет все `term.source_flags` с флагами исходного Unit (строки 1131–1138). Для exact это недостаточно: `weblate/glossary/models.py:get_glossary_term_modes` читает exact только у перевода.
- `weblate/checks/glossary.py:evaluate_glossary_terms` обходит морфологию при exact. Сопоставление сейчас регистронезависимое; изменение этого поведения не требуется.

## Общий контракт

1. Пустая flags не меняет поведение. Старые значения и их комбинации сохраняют совместимость.
2. `exact` — допустимый токен общей колонки; применяется к фактически создаваемым целевым единицам. На исходный Unit при append exact не добавляется.
3. Неизвестные токены, `exact:ru`, пустые элементы списка остаются ошибками.
4. Existing-term identity и append-only неизменны: входящие пометки не переписывают существующие термины ни на одном языке.
5. Пустые переводы, отсутствующие языки и ограничения разрешений сохраняют текущие результаты partial-success. Не создавать фиктивный перевод ради пометки.
6. Сочетания с read-only/forbidden сохраняют текущий приоритет исполнения Weblate; exact не отменяет запрет и не меняет read-only. Новые комбинации не назначаются автоматически.
7. Успех проверяется эффективными режимами целевых Unit, а не только наличием слова exact в CSV/TBX/preview.

## Задача 1 — Офлайн-разбор и передача exact

**Результат:** CSV с exact проходит parse → TBX → parse-back; существующие файлы работают по-прежнему.

**Файлы:** `loc_kit_ingest/parser.py`, `loc_kit_ingest/writer.py`; тесты `loc_kit_ingest/tests/test_parser_tbx.py`, `test_writer.py`, `test_infer_glossary.py`, `test_pipeline.py`. Схема v2 и поля профиля неизменны.

- [ ] Добавить exact в allowlist общей колонки; обновить диагностическое перечисление допустимых значений и комментарии о размещении exact.
- [ ] Исправить существующий тест `test_record_map_rejects_unsupported_source_flags`: exact перестаёт быть отрицательным примером; неизвестные и некорректные значения остаются отрицательными.
- [ ] Проверить сохранение exact существующим writer; менять writer только если поведенческая проверка обнаружит потерю.
- [ ] Добавить проверку многоязычной строки с exact, пустых flags и сохранности explanatory text. Проверить комбинированные флаги без изменения их приоритетов.

**Проверка:** `uv run pytest` из `loc_kit_ingest/`. Дополнительно временный CSV `en,ru,de,explanation,flags` с заполненными переводами и exact: `infer_glossary_profile`, затем `python -m loc_kit_ingest INPUT --profile PROFILE --out NEW_DIRECTORY` из корня через `uv run` и `PYTHONPATH` корня. До изменения exact даёт `tbx.invalid_source_flag`; после — два TBX с сохранёнными значениями и exact, без ошибок. Неподдерживаемый токен продолжает давать отказ.

Зависимости: нет.

## Задача 2 — Действующее правило после создания и append

**Результат:** exact виден в предпросмотре и действует у каждого нового перевода. На старые термины и будущие языки не распространяется.

**Файлы и интерфейсы:** `weblate/trans/loc_kit.py:append_glossary_terms`, `GlossaryTermPreview`, `validate_glossary_profile`; `weblate/trans/tests/test_loc_kit_ingest_contract.py`; существующий путь создания компонента и TBX-импорт. Использовать `Unit.update_extra_flags` и `Flags`, не прямые SQL-обновления.

- [ ] В append отделить exact от наследуемых source flags: read-only/forbidden и terminology остаются на исходнике; exact записывается на новый `target_unit` внутри существующей транзакции после успешного `translation.add_unit`.
- [ ] Не менять существующие флаги целевой единицы без необходимости: объединять через Flags; не добавлять exact старым терминам, пропущенным языкам или исходнику.
- [ ] Расширить `test_source_flags_are_previewed_and_created`: после реального подтверждения создания проверить `get_glossary_term_modes` для целевых Unit, а не только preview JSON. TBX уже переносит flags; если создание не материализует exact на переводах, исправить существующий путь переноса метаданных, не менять глобальную семантику режимов.
- [ ] Расширить `test_new_terms_merge_source_flags_with_terminology` и `test_incoming_source_flags_never_rewrite_existing_terms`: два языка, exact у новых переводов, отсутствие exact на исходнике, сохранность старых флагов и текста.
- [ ] Проверить append с пустой ячейкой, отсутствующим языком и недоступным созданием языка; результаты пропусков и границы транзакции сохраняются. Добавленный впоследствии язык не получает exact от исходника.
- [ ] Проверить наблюдаемое поведение: обычный склоняемый термин допускает грамматическую форму; exact для выбранного перевода требует заданной формы. Использовать существующие тестовые соглашения `weblate/checks/tests/test_glossary_checks.py`.

**Проверка:** в согласованном dev-контейнере `./rundev.sh test weblate/trans/tests/test_loc_kit_ingest_contract.py` и `./rundev.sh test weblate/checks/tests/test_glossary_checks.py`. Не пересоздавать shared dev stack. Выполнить реальный dev UI-сценарий загрузки/предпросмотра/подтверждения и append после отдельного разрешения на изменения dev-данных; не выдавать офлайн-проверку за этот сценарий.

Зависимость: задача 1. До изменения экспортируемых символов проверить ссылки через LSP; не вводить дублирующий путь сохранения пометок.

- [ ] Уточнить ограничение для правила только одного языка; не объявлять поддержку нового синтаксиса.

**Проверка:** повторить офлайн-шаблон с пустыми flags, со старыми двумя значениями и с exact; сравнить реальные целевые режимы после создания и append. `uv run prek run --files` для всех изменённых файлов после завершения общей работы. Код и документацию коммитить/пушить вместе после проверок; managed skill вне Git и фиксируется через managed-skill tool отдельно. Не копировать его в репозиторий только ради коммита.

Зависимость: задачи 1–2. Изменения в общих файлах выполнять последовательно; независимая подготовка документации возможна по зафиксированному контракту.

## Готовность и разрешения

План готов к рассмотрению. Выбранная семантика общей flags-колонки явно зафиксирована; поддержка ограничений отдельных языков не включена. Неизвестное фактическое размещение TBX-флагов при создании закрывается обязательным регрессионным сценарием задачи 2; одного зелёного parser-теста недостаточно.

В этой сессии поддержка exact не реализована. Утверждение плана разрешает только последующую реализацию в согласованном рабочем окружении, но не развёртывание и не изменения production. При разрешении реализации использовать ultrasuperpowers-executing-plans.
