# Судейские прогоны: защита от редоставки и честное покрытие

Дата: 2026-09-17.
Статус: одобрен к реализации 2026-09-17 после ревью
`docs/product/reviews/2026-09-17-judge-redelivery-and-coverage-plan-review.md`.
Этот план миграций не добавляет. Отдельного разрешения требуют деплой,
любые действия против живого экземпляра и платные прогоны у провайдеров.

**Порядок.** Этот план идёт **первым** и целиком, до
`docs/product/plans/2026-09-17-mt-prerequisite-before-judge.md`: он кладёт
guard исполнения и контракт покрытия, на которые тот опирается. Внутри
плана задача 1 предшествует задаче 2. Параллельное исполнение двух планов
запрещено — они правят одни и те же `perform`/`_perform`,
`_finish_producer_run`, точки входа `tasks.py`, `models/judge.py`, отчёт и
`ProducerRunSerializer`; один владелец общего файла за раз. Остальные
правила исполнения — в разделе «Интеграция, выпуск и критерий готовности».

## Цель и согласованный объём

Закрыть две ошибки без новой системы кампаний:

1. Повторная доставка одной Celery-задачи не запускает второго активного
   исполнителя и не создаёт второй отчёт о том же запуске.
2. Завершение задачи не выглядит как проверка всей выборки, если остались
   строки без заключения судьи.

Основание — обсуждение с пользователем и его последнее уточнение:
**отказ до запуска при превышении капа исключён из этого плана**.
Кап 2000, усечение выборки и доступные уровни запуска сохраняются.
Запрет судьи на уровне проекта обсуждается отдельно, не реализуется здесь.
Правила работы: `AGENTS.md`.

Не входят: уменьшение капа до 250–500; жёсткий дедлайн; изменение лизинга;
кампании, дочерние задачи и продолжение; денежные бюджеты; новые очереди;
замена моделей или ключей; изменение MT/repair/approval-политики;
дедупликация двух отдельных намеренных запусков с разными task ID;
исправление исторических данных на проде.

## Выбранный минимальный подход

Не переделывать UI-публикацию в новый outbox и не добавлять таблицу кампаний.
Для UI достаточно повторно находить один прогон по устойчивой идентичности
Celery-задачи **под блокировкой всего исполнения**. Producer API продолжает
использовать предсозданный прогон. Это намеренное упрощение предыдущего
предложения «предсоздавать всё в диспетчере»; безопасность даёт не место
создания строки, а сериализация исполнения и повторное использование строки.

Для текущего однохостового deployment использовать существующий файловый
backend `WeblateLock` в явно выбранном режиме, независимо от наличия Redis.
Добавить только параметр выбора file-only режима с прежним поведением по
умолчанию; не создавать ещё одну библиотеку блокировок. Блокировка живёт
весь вызов задачи, не истекает по времени и освобождается ОС при гибели
процесса. Не держать DB-транзакцию на протяжении LLM-вызовов.

**Граница поддержки:** все исполнители этого экземпляра должны видеть один
локальный lock directory с работающими process locks. Несколько независимых
хостов/локальных DATA_DIR этим решением не защищены. Не рекламировать такую
гарантию; перед горизонтальным масштабированием требуется другое решение.
Lock-файлы не удаляются никогда — ни исполнителем, ни фоновой задачей:
unlink под уже открывшим файл ожидающим делит их по разным inode, а
защита от этого потребовала бы inode-сверки внутри общего `WeblateLock`,
которым пользуются и блокировки компонентов. Менять корректность общего
mutex ради уборки в этом плане не будем.

Рост при этом признан прямо, а не замолчан: ключ UI-прогона — новый task
UUID на каждый запуск (`edit.py:1855,1883`), и сегодня `data_dir("locks")`
пуст, потому что файловая ветка не выбирается вовсе, то есть режим вводит
новое пространство имён размером в один пустой файл за прогон. Это
принятый остаточный эффект: при нынешнем темпе прогонов каталог остаётся
операционно незначимым годами. В объём входит только измеримость и
условие пересмотра — зафиксировать в документации, что файлы копятся, где
смотреть их число, и что чистка допустима вручную в том же окне без
активных judge-исполнителей, которое план уже требует для rollout (без
holder'ов гонки inode не существует). Отдельный GC-протокол проектировать
лишь если измеренное число файлов или задержка листинга каталога станут
заметны.

Сохраняются текущий живой фильтр и существующая политика повторной обработки.
Этот план не обещает неизменяемую кампанию или полное покрытие проекта между
перезапусками. Отчёт описывает конкретный прогон и известный ему журнал.

## Общие контракты

### Исполнитель

- Если задан `producer_run_id`, ключ блокировки строится из UUID прогона;
  иначе — из task ID с безопасным именем файла. Retry сохраняет тот же ключ.
- Блокировка берётся до adoption/создания прогона, heartbeat исполнителя,
  любых LLM/MT-вызовов и финализации; освобождается в `finally`. Место —
  тело обеих задач (`auto_translate`, `auto_translate_component`) до
  `heartbeat_task` и до конструирования `BatchAutoTranslate`: общий
  `except Exception` в `BatchAutoTranslate.perform` финализирует run как
  FAILED (`autotranslate.py:1712-1717`), поэтому contention не должен
  долетать до него.
- При занятости — отложенный Celery retry без LLM и изменения статуса
  прогона. Не возвращать ложный success и не делать горячий requeue.
  Ожидающая копия обязана сохраняться как носитель доставки: при
  `acks_late` редоставленный дубликат — единственное оставшееся сообщение
  этой доставки (исходное брокер уже восстановил именно в него). Если она
  тихо завершится, а владелец упадёт позже, прогон останется `RUNNING`
  без сообщения — прямое противоречие контракту восстановления ниже.
- Механизм фиксируется, а не оставляется на реализацию: занятость
  сигнализируется отдельным исключением (не `WeblateLockTimeoutError`,
  у которого на обеих задачах уже свой `autoretry_for` с
  `retry_backoff=600` и штатным лимитом), задачи получают `bind=True`, и
  для этого исключения вызывается
  `self.retry(countdown=60, max_retries=settings.JUDGE_GUARD_WAIT_RETRIES)`
  с явным потолком (по умолчанию 480, то есть ~8 часов ожидания — заведомо
  больше visibility timeout). `max_retries=None` здесь запрещён: Celery
  подставит bounded task-default; task-level `max_retries=None` тоже
  запрещён — он распространился бы на прочие ошибки этой задачи.
- Путь исчерпания потолка обязан не терять прогон: финализировать его
  `failed` с диагностической причиной «блокировка исполнения не
  освобождена», после чего восстановление идёт явным resume. Молча
  завершать ожидающую копию нельзя ни при каком потолке. Прочие
  `WeblateLockTimeoutError` сохраняют текущую autoretry-семантику.
- После получения блокировки состояние перечитывается. Terminal run
  возвращает существующий report URL без повторных вызовов и перезаписи
  summary. `CANCEL_REQUESTED` не превращается в новый запуск.
- UI-run ищется по task ID и проверяется по actor/scope/mode/query.
  Новый run получает существующий `idempotency_key`, производный от task ID.
  При нескольких исторических совпадениях или несовместимом запросе —
  явная диагностическая ошибка, без выбора случайного run и без LLM.
- После гибели процесса повторная доставка занимает освободившийся lock,
  берёт тот же run и использует существующий non-PENDING/cache механизм.
- Синхронный REST и вызовы без Celery task ID сохраняют свои отдельные
  намерения. Не превращать пустой task ID в общую блокировку всех запусков.

Не обещать exactly-once внешнего запроса: смерть после ответа провайдера,
но до его сохранения оставляет окно повторной оплаты. Исключаем второго
живого исполнителя одной доставки, а не это распределённое окно.

### Покрытие

Один общий расчёт для HTML и producer API, на журнале всего прогона,
**до** фильтрации и пагинации страницы:

- `recorded`: количество `JudgeRunUnit` данного прогона;
- `with_result`: PASSED + MINOR + MAJOR + CRITICAL;
- `without_result`: все остальные исходы, с разбивкой по outcome;
- SKIPPED разбивается по `skip_reason` — перечислять все встречающиеся
  значения (`permission`, `cap`, `untranslated`, а после плана
  обязательного MT и `mt-prerequisite`), не два захардкоженных имени.
  Любая причина пропуска остаётся в «без заключения» и никогда не входит
  в `with_result`; страничный фильтр `checked` уже исключает SKIPPED по
  outcome (`views/judge.py:169-170`) — это поведение сохранить;
- `cached`: подмножество записей с результатом, не добавляется к итогу;
- `scope_complete`: true/false/null по точному правилу. True — прогон
  terminal, его `scope_snapshot` непуст, каждая запись snapshot имеет
  строку журнала с исходом из `with_result`, и `summary.cap_remainder`
  равен нулю. False — terminal с усечением или с исходами без заключения.
  Null — журнал running/failed прогона и любые записи без доказанного
  знаменателя, включая UI-прогоны с пустым snapshot. Это не готовность
  к релизу.

`summary.cap_remainder` сохраняется как отдельное свидетельство усечения.
Если он расходится с cap-записями, показывать неполноту и обе величины с их
смыслом, не складывать потенциально пересекающиеся числа. Не выводить
точный полный знаменатель из частичного журнала running/failed run без
полного snapshot. Для старых записей без доказанного denominator писать
«по журналу прогона», а не «проверено всё».

Технический `status=completed` не переименовывается; `partial` уже занят
семантикой отмены. Рядом показывается отдельный результат покрытия.
Для MT-прогонов judge coverage в API равен null, HTML не меняется.

## Задача 1. Одна доставка — один активный исполнитель и один отчёт

**Результат:** concurrent redelivery не вызывает второй LLM; после гибели
исполнителя сохраняются один run и уже записанные результаты. Кап,
режимы перевода, роли и producer API dispatch не меняются.

**Файлы и интерфейсы:**
`weblate/utils/lock.py:WeblateLock`,
`weblate/trans/tasks.py:auto_translate`, `auto_translate_component`,
`weblate/trans/autotranslate.py:BatchAutoTranslate._adopt_producer_run`,
`_create_producer_run`, `perform`, `_finish_producer_run`;
настройка `JUDGE_GUARD_WAIT_RETRIES` по образцу уже существующей
`JUDGE_MAX_UNITS_PER_RUN`, то есть во всех пяти местах её цепочки:
дефолт в `weblate/trans/defaults.py:62`, app conf в
`weblate/trans/models/_conf.py:111`, `weblate/settings_example.py:1029`,
env-обвязка в `weblate/settings_docker.py:1823` и
`deploy/environment.example` (префикс `WEBLATE_`);
`weblate/trans/tests/test_judge_autotranslate.py`,
`weblate/trans/tests/test_tasks.py`,
`weblate/trans/tests/test_autotranslate.py`,
`weblate/utils/tests/test_lock.py`.
Новая таблица и миграция не нужны.

**Действия:**

- [ ] Проверить LSP references затрагиваемых символов; ограничить guard
  исполнениями, которые создают или принимают ProducerRun (judge и
  `auto_source=mt`), не сериализовать пути без прогона и разные run ID.
- [ ] Добавить file-only режим существующего lock и guard исполнения
  по общему контракту, в теле обеих Celery-точек входа до `heartbeat_task`
  и до конструирования `BatchAutoTranslate`. Ожидающая доставка не должна
  помечать чужой run FAILED через общий `except Exception` и не должна
  выдавать running-heartbeat: её liveness остаётся queued/no-update.
- [ ] Ничего не удалять из lock-каталога и не менять семантику общего
  `WeblateLock` сверх file-only параметра. Вместо GC — задокументировать
  накопление файлов, где смотреть их число и что ручная чистка допустима
  только в окне без активных judge-исполнителей.
- [ ] Повторно использовать UI-run по task ID; terminal replay сделать
  read-only. Producer API с тем же task ID также проходит guard.
- [ ] При восстановлении итоговые summary считать по всему сохранённому
  прогону, не затирать прошлые результаты счётчиками последней попытки.
- [ ] `idempotency_key` UI-прогона выводить из task ID, а `IntegrityError`
  на уникальном индексе трактовать как «run уже создан»: перечитать и
  принять существующий, без второй попытки и без failure.
- [ ] Не переписывать исторические дубли. Документировать topology-bound
  гарантию и окно неопределённой оплаты в `docs/admin/config.rst` и
  `docs/security/threat-model.rst`, без утверждения exactly-once.

**Проверка:**

- Regression с двумя реальными процессами: первый держит выполнение на
  барьере перед ответом подставного провайдера; второй получает то же сообщение.
  До фикса producer API допускает второго исполнителя, UI создаёт второй run;
  после фикса счётчик входов провайдера не увеличивается от второго процесса.
- Убить первый процесс после сохранённого батча, дождаться освобождения lock,
  повторить доставку: тот же run, сохранённые строки не отправлены заново,
  оставшиеся обработаны, итог включает обе попытки.
- Доставить сообщение после terminal состояния: ни вызовов, ни изменения
  finished/summary. Проверить отмену и отличающийся task ID того же run.
- Два разных run ID должны исполняться независимо. Отдельно проверить
  освобождение file lock при аварийном завершении процесса, не только
  штатном выходе из context manager.
- Ожидающая доставка не исчезает: после нескольких циклов ожидания она
  всё ещё запланирована, прогон и счётчик провайдера не менялись, а
  убийство владельца после этих циклов приводит к тому, что именно эта
  копия занимает освободившийся lock и доводит прогон до конца.
  Исчерпание потолка `JUDGE_GUARD_WAIT_RETRIES` финализирует прогон
  `failed` с диагностической причиной, не оставляя `RUNNING` без носителя.
- Итоговая summary восстановленного прогона совпадает с подсчётом по
  журналу `JudgeRunUnit`, а не со счётчиками последней попытки.
- Judge-прогон через `auto_translate_component` (путь add-on) проходит
  тот же guard: повторная доставка не даёт второго исполнителя и отчёта.
- File-only режим: он выбирается независимо от наличия Redis, прежний
  выбор backend по умолчанию не меняется, а lock-файл после release
  остаётся на месте (его существование не считается занятостью — повторный
  захват того же пути успешен). Утверждения про размер каталога не
  предъявлять: файлы копятся намеренно.
- Использовать process barriers и `TransactionTestCase`, не два потока
  внутри транзакционного `ViewTestCase`. Внешние LLM/VCS замоканы;
  платные запросы не нужны.

Команда существующего runner (`rundev.sh test` жёстко подставляет
`pytest -n auto`, поэтому завершающий `-n 0` не лишний: он перебивает
xdist, чтобы процессные барьеры и файловая блокировка не делились между
worker-процессами pytest):

```sh
./rundev.sh test -n 0 weblate/trans/tests/test_judge_autotranslate.py weblate/trans/tests/test_tasks.py weblate/trans/tests/test_autotranslate.py weblate/utils/tests/test_lock.py
```

Дополнительно в изолированной QA-среде с Redis/Celery: два worker процесса,
одинаковый task ID, затем kill исполнителя и redelivery; подставной HTTP
провайдер считает запросы. Сначала воспроизвести прямую двойную доставку;
не требуется ждать четыре часа или менять лизинг общего dev/prod.

## Задача 2. Неполная проверка видна первой, без изменения запуска

**Зависимость:** общие изменения `autotranslate.py` выполнять после задачи 1.
HTML/API-работа может идти независимо после фиксации контракта coverage;
для такого объёма последовательное исполнение проще параллельного.

**Результат:** продюсер видит, сколько строк имеют заключение и почему
остальные не проверены; «замечаний нет» не выдаётся за покрытие всего scope.
Сохраняются усечение по капу, все уровни запуска и исторические статусы.

**Файлы и интерфейсы:**
`weblate/trans/models/judge.py:ProducerRun` — общий вычисляемый coverage
без нового persisted поля;
`weblate/trans/views/judge.py:producer_run`;
`weblate/templates/producer-run.html`;
`weblate/api/producer/serializers.py:ProducerRunSerializer` — добавить
read-only `coverage` по общему контракту и `warnings`;
`weblate/trans/tests/test_judge_views.py:JudgeRunReportViewTest`,
`weblate/api/tests.py` — producer run endpoints.

**Действия:**

- [ ] Вынести единый агрегат coverage, не создавать по отдельной трактовке
  checked в serializer и view. Не делать запрос на каждую строку.
- [ ] В шапке отчёта и карточке действий отдать приоритет «проверка неполная»
  при cap skip, исходах без результата или незавершённом запуске; для
  неизвестного покрытия показать неопределённость, не зелёный успех.
- [ ] Показать числа и причины словами, не одним цветом. Сохранить findings,
  ссылки на строки и историю расходов. Не добавлять кнопку продолжения.
- [ ] Обновить `docs/api.rst`, `docs/specs/openapi.yaml` по принятому в repo
  способу генерации, `docs/product/guides/producer-guide-weblate.md` и
  верхнюю unreleased-секцию `docs/changes.rst`.
  Следовать `ACCESSIBILITY.md` и `docs/contributing/frontend.rst`.

**Проверка:**

- Исторический completed run с PASS и CAP-skips: заметное неполное покрытие,
  число результатов не включает пропуски; статус в БД остался completed.
- PASS + UNPARSED/DEFERRED/REFUSED/PENDING/STALE_CONFLICT: последние не
  засчитываются в `with_result`; причины видны независимо от фильтра страницы.
- Cached PASS считается один раз. Permission skip отделён от cap skip.
- SKIPPED любой причины, включая `untranslated` и будущую
  `mt-prerequisite`, не входит в `with_result`; разбивка по причинам
  присутствует в том же агрегате и не требует его правки при добавлении
  новой причины.
- Running/failed run с неполным журналом не обещает точный размер исходного
  scope. Историческое расхождение summary/ledger не маскируется арифметикой.
- HTML и API показывают одинаковые числа; чужой проект не раскрывается.
  Обычный MT-отчёт не получает судейское предупреждение.

```sh
./rundev.sh test -n 0 weblate/trans/tests/test_judge_views.py weblate/api/tests.py -k 'Judge or Producer'
```

Открыть реальный отчёт QA-прогона в браузере: неполнота видна до таблицы
на обычной и узкой ширине, ссылки и фокус работают с клавиатуры.
Использовать существующие данные либо синтетический QA-прогон без платных LLM;
production записи для демонстрации не менять.

## Интеграция, выпуск и критерий готовности

- [ ] Исполнение вести в отдельном worktree. Не включать существующие чужие
  изменения/планы про MT prerequisite и untranslated scope; при пересечении
  контрактов согласовать интеграцию, не менять MT-поведение этим планом.
  Порядок между планами: сначала этот (guard и покрытие меньше и закрывают
  класс двойной оплаты), затем план обязательного MT перебазируется на
  guard и на разбивку по `skip_reason`.
- [ ] На собранной реализации один раз запустить перечисленные регрессии
  и `uv run prek run --all-files`; проверить схему API принятым генератором.
  Команды выше — будущая проверка, не заявление о пройденных тестах.
- [ ] Зафиксировать доказательства concurrent delivery, crash/recovery,
  terminal replay и визуальной проверки. Удалить временные smoke-скрипты.
- [ ] Commit и push по `AGENTS.md` после проверки. Деплой — отдельное разрешение.
- [ ] При согласованном деплое дождаться отсутствия активных старых judge
  исполнителей: старый процесс не использует новый lock, поэтому смешанный
  rollout не обеспечивает взаимное исключение. Не применять `--force` для
  обхода этого условия; обновить все workers, не только web.
- [ ] Не менять production cap, visibility timeout или ключи. После rollout
  проверить загруженный код и отчёт без запуска платного большого прогона.

### Сверка с планом обязательного MT

`docs/product/plans/2026-09-17-mt-prerequisite-before-judge.md` меняет те же
`autotranslate.py` (adoption/`perform`/финализация summary и warnings) и тот
же отчёт, поэтому три контракта фиксируются здесь:

- Общие файлы меняются последовательно, один владелец за раз;
  `ProducerRunSerializer.warnings` добавляет тот план, который идёт первым,
  второй принимает поле как данное и не дублирует его.
- Новые причины пропуска (`untranslated` уже в `SkipReason`,
  `mt-prerequisite` появится) попадают в «без заключения» и в разбивку по
  `skip_reason`, никогда в проверенные.
- Семантика статусов не меняется обоими планами: `partial` остаётся
  результатом отмены (`_finish_producer_run` назначает его только из
  `CANCEL_REQUESTED`), а остановка после начатой judge-работы — `failed`
  с явной причиной и сохранёнными результатами. Неполнота выражается
  покрытием и причиной остановки, не новым статусом.

Готово, когда одна redelivery не порождает второго активного исполнителя
и отчёта, восстановление сохраняет результаты, а усечённый/неполный прогон
честно обозначен в HTML и API. Полная проверка большого проекта одним
действием и политика допустимого размера остаются отдельным решением.
