# Отчёт в визарде и выгрузка итогового файла с цветными отметками

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Независимые агенты — только по отдельному разрешению пользователя.

**Статус:** выполнен локально; 429 backend, 118 UI и 3 совместных теста с
изолированным Weblate прошли. Одно независимое read-only ревью: 4 Important
исправлены за один TDD-проход, Critical/отложенных Minor нет. Бэкапы и доказательства
сохраняются отдельно. Серверы, старые выгрузки и готовые переводы не менялись.
Ограничение существующего API: severity judge-run не привязана к проверенному
тексту отдельной revision, поэтому сама по себе не подтверждает розовую отметку;
при отсутствии актуального двухместного PASS строка жёлтая. Привязанный severity
потребует отдельно согласованного расширения Weblate API, здесь оно не добавлено.

**Goal:** после полного цикла показывать отчёт в визарде и отдавать согласованные итоговый XLSX и отчёт XLSX; критические замечания выделять розовым, непроверенные ячейки — жёлтым.

**Architecture:** визард формирует неизменяемый пакет результата конкретного задания из уже проверенного экспорта и финального снимка качества. Один индекс замечаний используется для отчёта, подсветки и счётчиков. Скачивание читает сохранённый пакет, не запускает MT, судей или исправления.

**Tech Stack:** существующие FastAPI, SQLAlchemy/SQLite, React/TypeScript и серверный XLSX-сериализатор визарда. Новые зависимости не предполагаются.

**Spec:** запрос пользователя от 21 октября 2026 года с уточнением: «Непроверенные строки отмечать жёлтым. Файл отчёта должен быть отображён и пригоден для скачивания в визарде»; существующие ограничения полного цикла — `docs/product/guides/full-quality-cycle-v2.md` и `docs/product/plans/2026-10-20-server-full-quality-release.md`.

## Global Constraints

- Только отдельный локальный worktree и синтетические данные. Не обновлять серверы, не менять реальные готовые переводы, не отправлять на GitHub, не объединять с main.
- До реализации сохранить Git bundle, исходники и хэши; перед тестовыми миграциями — отдельную копию тестовой БД. На текущем этапе миграция не требуется: пакет хранится в существующем Record.
- Не перезаписывать старые задания и экспорты. Старым заданиям без пакета не приписывать новую проверку задним числом.
- Сохранить текущую защиту revision A → download → revision B и атомарную публикацию при действующей lease, с учётом отмены задания.
- Не менять алгоритмы судей, применимость исправлений и финальные статусы качества ради оформления файла.
- Не добавлять листы и служебные колонки в итоговый лок-кит. Подробности и легенда находятся в отдельном отчёте.
- Подсвечивать только целевые ячейки проверенного языка. Исходный текст и другие языки не закрашивать.
- XLSX остаётся текущим экспортом данных: произвольное оформление, макросы и формулы исходной книги существующим импортом не сохраняются. Не обещать их восстановление этой доработкой.

## Review Focus

1. Одинаковый исходный текст в разных контекстах не должен приводить к подсветке чужой строки: использовать идентификаторы, не поиск текста.
2. Исправленная проблема не должна оставаться розовой из-за исторического verdict; решение относится к версии ячейки в файле.
3. Отсутствующий ответ судьи не означает одобрение, а `parsed` означает только разобранный ответ, не «перевод верен».
4. Отмена, перезапуск, конкурирующее исправление или сбой сохранения не должны публиковать разновременные файл и отчёт.
5. Повторное скачивание и чужой run_id не должны запускать обработку или раскрывать чужие переводы и секреты.

## Предлагаемый контракт результата

### Два файла

- `run-<id>-translation.xlsx`: лок-кит в прежнем расположении строк/колонок с итоговыми переводами. Для целевой ячейки с подтверждённым обязательным замечанием — сплошная светло-розовая заливка `#FFC0CB`; для непроверенной — светло-жёлтая `#FFF2CC`. Текст тёмный. При наличии обеих причин розовая заливка имеет приоритет; обе причины сохраняются в отчёте. Обычные ячейки не получают этих заливок.
- `run-<id>-quality-report.xlsx`: лист «Сводка» и лист «Замечания». В сводке: задание, язык, версия результата, итоговый статус, число проверенных и исправленных строк, число проблемных ячеек, число замечаний и групп повторов, состояние обоих судей. При нуле проблем — явно «Остаточных замечаний нет», без пустых фиктивных записей.
- В «Замечаниях»: файл/лист/адрес ячейки, ключ и unit_id, язык, исходник и текущий перевод из сохранённого экспорта, категория, важность, причина, текущее состояние проверки двух судей, требуемое действие. Исторические исправления учитываются отдельно от остатка.
- В карточке задания отображается раздел «Отчёт качества»: имя доступного XLSX, сводка и таблица его замечаний, кнопка «Скачать отчёт». Просмотр использует те же сохранённые данные, что файл, без необходимости скачивать его или открывать Excel. Добавить фильтр «Все / Критические / Непроверенные / Рекомендации» и постраничный просмотр по 50 записей, чтобы отчёт на сотни строк оставался удобным. Цвет в таблице дополняется текстовыми статусами.
- Предлагаемая кнопка «Скачать всё» отдаёт ZIP с этими двумя файлами и небольшим manifest.json с run_id, версиями, именами и SHA256. Отдельные кнопки каждого файла тоже доступны. Автоматическое открытие двух скачиваний браузером не требуется.

### Что считать критическим

Предложение для согласования: категория оформления `blocking` означает оставшуюся обязательную проблему. Она не переименовывает серверный severity.

- Неразрешённый `repeat-drift` и обязательные (`hard=true`) glossary/check — по существующему `required_issue`.
- Актуальный неустранённый verdict судьи `major`/`critical` — только если такой verdict и его привязка к текущей revision действительно получены. Исторический severity не переносить автоматически на исправленный текст.
- Несогласие судей не превращается автоматически в «критическую ошибку»: показывать фактические решения и причину ручной проверки.
- Для непроверенной актуальной версии (`not_verified`, неполный/неразобранный ответ) использовать жёлтую отметку, а в отчёте писать «Проверка не завершена», не выдумывать критический verdict. Если также есть подтверждённая обязательная проблема, применять розовую заливку и сохранять оба признака.
- Рекомендательные замечания перечислять в отчёте без розовой заливки. Полностью исправленные замечания не подсвечивать.
- Ошибка всего задания без надёжного финального снимка: доступна диагностика, но нет нового файла с утверждением о завершённой проверке.
- Не определять критичность по наличию ключевых слов в тексте причины. Не считать `seat_results=parsed` подтверждением качества.

Если существующий API не даёт актуального verdict/reason, отражать «не предоставлено» и доступные коды причин. Перед требующим расширения Weblate API изменением остановиться и согласовать отдельный объём. Публикация отчёта с уже доступными данными не должна зависеть от выдуманного содержания ответов LLM.

## Критерий готовности

Для одного нового законченного задания доступны согласованные отчёт и итоговый XLSX. Отчёт показан в визарде с именем файла, сводкой, просматриваемыми замечаниями и доступным скачиванием полного XLSX. Каждая розовая или жёлтая ячейка имеет запись отчёта с точным адресом и объяснением; все обязательные остаточные замечания и непроверенные ячейки представлены. Подтверждённые критические замечания розовые, только непроверенные ячейки жёлтые; при сочетании причин приоритет у розового, обе причины видны в отчёте. Исправленные проблемы не подсвечиваются. Просмотр и скачивание не запускают обработку, исходный проект и прежние выгрузки не меняются. Реализация этого плана сама по себе не разрешает обновление серверов.
