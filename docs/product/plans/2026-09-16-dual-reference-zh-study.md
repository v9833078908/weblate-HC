## 3. Вопросы, гипотезы и единица вывода

Разделять source компонента, язык авторства, основной вход модели,
дополнительную опору и независимую истину для оценки. RU/EN могут быть
переводами друг друга; это зависимые свидетельства, а не независимые голоса.

| Гипотеза | Вмешательство | Основное сравнение |
| --- | --- | --- |
| H1 | Готовый вычитанный EN вместо RU как основного входа | B − A |
| H2 | RU как дополнительная опора при EN-генерации | C − B |
| H3 | RU как дополнительная опора при проверке/исправлении EN-черновика | F − E |
| H4, exploratory | Переносимость выигрыша и операционная пригодность | Жанры, игры, стоимость, coverage, стресс-набор |

Основная популяция — RU-origin игровые тексты с актуальными согласованными
RU/EN. EN-origin — отдельная репликация; unknown origin — exploratory.
Настройка component source сама по себе не устанавливает авторский язык.

Единица назначения — стабильный source record; каждое условие применяется
к каждой строке. Единица зависимости — сцена/семейство шаблонов. Результат
относится к выбранным играм, модели и процессу подготовки опор. Вывод о новой
игре требует репликации на уровне игр, не увеличения числа строк одной игры.

## 4. Экспериментальные условия

| Arm | Генерация | QA / repair |
| --- | --- | --- |
| A | RU → ZH | Нет |
| B | EN → ZH | Нет |
| C | EN primary + RU reference → ZH | Нет |
| D | RU primary + EN reference → ZH | Нет |
| E | Сохранённый черновик B | EN-only review, затем EN-only edit |
| F | Тот же сохранённый черновик B | EN+RU review, затем EN+RU edit |

A–D используют одинаковые model/profile, prompt template, reasoning,
temperature, max output, retries, batch policy и технические проверки;
меняется только заявленный source/reference treatment. Роли текстов
маркируются явно. Общий глоссарий задаётся одинаковыми понятиями и ZH-терминами,
с source labels соответствующего языка. Одноязычным arms второй текст не
раскрывается через notes, examples или glossary descriptions.

E/F используют одинаковую пару действующих production-судей через LiteLLM
(два seat, независимо) и одного editor Gemini 3.7 через OpenRouter.
Каждый судья делает один review, затем editor делает один edit. Состав
панели, настройки и лимиты одинаковы в E и F. Editor вызывается
и при отсутствии замечаний и может оставить текст неизменным. Содержание
контекста отличается, реальные tokens/cost измеряются; равные лимиты не
означают равную цену. Сырые замечания reviewer сохраняются отдельно.

B не перегенерируется для E/F; C не подставляется вместо B. Syntax-only
проверка не заменяет semantic QA в контрольном E. Выигрыш F против B сам по
себе не доказывает пользу RU. D−A и C−D — вторичные сравнения. Совместная
двухъязычная генерация плюс QA — будущий эксперимент, не скрытый arm.

### Выбранные модели и маршруты

| Роль | Модель / сервис | Применение |
| --- | --- | --- |
| Генератор | Gemini 3.7 через OpenRouter | Все A–D, один замороженный профиль |
| Editor | Та же Gemini 3.7 через OpenRouter | Исправление общего B в E/F |
| Reviewer panel | Два действующих production seat через корпоративный LiteLLM | Независимая проверка в E/F, одинаковая панель |
| Независимая оценка | Human LQA в подтверждающем режиме | Судьи E/F не выставляют итоговую оценку собственной работе |

Это решение владельца после версии 1.0. LiteLLM — маршрут доступа,
а не название модели: записать точные seat model IDs, resolved aliases,
reasoning, temperature, token limits, timeout, retries, response schema,
aggregation и фактически обслуживший запрос backend. Не выбирать другую
модель по удобству, качеству первых результатов или наличию временной ошибки.

GET project machinery settings для NFG, Heart Abyss и Victory Banner
подтвердил настройки OpenRouter, но не вернул project-local model/routing.
Точный ID Gemini 3.7 не подтверждён этим endpoint. Исполнитель должен прочитать
эффективную site+project конфигурацию и текущие judge profiles перед запуском,
сохранив только безопасные поля. Не угадывать slug вроде имени провайдера и
не считать `deploy/environment.example` доказательством живой конфигурации.
Если найдено расхождение с выбранной Gemini 3.7, показать его владельцу;
не подменять модель и не перенастраивать production ради эксперимента.

Объединение замечаний двух судей должно быть детерминированным и одинаковым
для E/F; сохранить исходные ответы каждого seat, заранее описать дедупликацию
и порядок передачи editor. Не добавлять третий LLM-вызов для арбитража между
моделями. Согласие судей не становится human gold. Пропавший/неразобранный seat
не считается pass: зарегистрировать одинаковую для E/F политику retries,
неполного review и fallback. Любую смену serving model логировать отдельно.

Автоматическая модельная оценка остальных outputs, если нужна screening,
также использует LiteLLM. Это отдельная роль и отдельный бюджет: слепые
запросы не получают прежние verdicts и не смешиваются с review/repair в E/F.
Она остаётся proxy, даже если судьи относятся к другому семейству, чем Gemini.

## 5. Датасет и предлагаемый пилот

Предложение владельцу: NFG UI 30 + Tutorial 30 + Loot 30, Heart Abyss hub-1
30 диалоговых строк. Всего ориентировочно 120; целые сцены и шаблонные группы
не разрывать между splits. Число 120 — оценка объёма пилота, не power analysis.
Альтернативы: Victory Banner 90 + Heart Abyss 30; либо 11 approved EN Victory
Banner только для отладки процесса.

| Кандидат | Снимок Terra | Что ещё проверить |
| --- | --- | --- |
| Need For Greed | UI 463, Tutorial 102, Loot 154 RU/EN по metadata; UI EN approved 11 | Exact key alignment, происхождение вычитки; отсутствие historical ZH не мешает |
| Heart Abyss hub-1 | 394 заполненные пары RU/EN, 396 совпадающих ключей RU/EN/ZH, notes/context | EN approved 0; внешняя вычитка неизвестна |
| Victory Banner general | 537 выровненных пар, EN approved 11 | Кто и какую ревизию вычитал |
| Anvil Saga | RU/EN по 9482, ZH 9481 по metadata | Полное пересечение не установлено, EN approved 0 |

Критерии включения: стабильный ключ внутри component, непустые обе версии,
одна игровая ревизия, подтверждённая human review, согласованность существенного
смысла, доступные требования/контекст. Сопоставлять по component + id_hash +
context и проверить связь source unit; не по тексту и не по номеру строки.
ID сохраняется вместе с исходными текстами и их hashes, чтобы обнаружить
смену значения при том же ключе.

`state=20`, отсутствие failing checks и read-only не доказывают вычитку.
`state=30` — сигнал, происхождение которого нужно проверить. Допустимо
подтверждение внешней вычитки конкретной ревизии владельцем. Если опоры
довычитываются специально, сохранить до/после и учесть стоимость подготовки.

Calibration, pilot и holdout делятся по целым сценам/семействам близких строк.
Заморозить sampling seed, квоты, exclusions и причины до генерации. Нельзя
отбирать строки по тому, на каких из них затем выиграл EN. Логировать все
исключённые кандидаты и причины. Пересэмплирование редких жанров учитывается
в весах анализа; четыре квоты не объявляются распределением всего production.

Отдельный stress set: устаревшая/отсутствующая опора и реальные RU/EN
противоречия; synthetic perturbations явно маркируются. Его результаты не
смешиваются с prevalence чистого корпуса. До прогона определить правильное
поведение по каждому случаю: конфликт, fallback или отказ. Не давать LLM
молча выбирать, какая версия истинна.

## 6. Слепая оценка и ресурсы

Предусмотреть два режима и записать выбранный до запуска:

- **Screening:** техническая целостность, модельные diagnostics, стоимость,
  разбор русскоязычным владельцем смысла. Вывод: кандидат заслуживает или не
  заслуживает дальнейшего исследования. Это не доказательство качества ZH.
- **Confirmatory LQA:** независимые специалисты по китайской игровой
  локализации и реальная компетенция RU↔ZH/EN↔ZH; как минимум два оценщика
  и арбитраж серьёзных расхождений. Только этот режим позволяет делать
  заявленное заключение о профессиональном качестве.

До prompt tuning редактор RU↔EN с владельцем игры фиксирует карту смысла:
действие, субъект, условия, термины, допустимые адаптации, ограничения UI.
Это не единственный идеальный ZH reference. Финальные арбитры не пишут
repair-prompts; human test labels не возвращаются генератору. Записываются
авторы карты и основания решений.

Оценка содержит target-only проход по естественности/регистру и проверку
точности по одинаковому комплекту смысловых оснований для всех arms.
Отсутствие RU-компетенции у всех оценщиков нельзя заменить обратным переводом
LLM. Скриншоты/контекст одинаковы и соответствуют ревизии корпуса. Без
рендера нельзя заявлять, что реально проверено переполнение интерфейса.

Идентификаторы arm/model, цена и LLM-критика скрыты. Порядок сбалансирован;
один rater не получает только один arm. Не показывать несколько версий
одной строки в одной сессии, кроме отдельного counterbalanced pairwise теста.
На калибровке 20–30 строк вне holdout согласовать рубрику и измерить время.
Пилот double-score целиком; основной прогон — заранее выбранная доля
(предложение 25–30%) плюс серьёзные расхождения. Хранить pre-adjudication
оценки, agreement и положительное согласие по major/critical. При низком
согласии остановить расширение и исправить рубрику на calibration, не на holdout.

## 7. Метрики и estimands

Профиль MQM: accuracy (mistranslation, omission, addition), terminology,
fluency, style/character, locale, functional. Minor — локальный дефект без
существенного изменения смысла; major — значимое искажение или существенная
правка; critical — заранее определённое тяжёлое последствие для продукта.
Severity задаётся последствием, а не названием check. Краткость ZH и
синонимия не ошибки. Одну причину не штрафовать несколькими категориями.

**Primary endpoint:** доля непригодных результатов по всем назначенным
строкам (ITT). Непригоден результат с human-adjudicated major/critical либо
без валидного перевода после предусмотренных попыток, включая abstain.
Failure — отдельная причина общего исхода, не лингвистическая critical.
В screening без человеческой LQA этот endpoint не измерен: модельные оценки
отчётливо маркируются как proxy и не подставляются в него вместо human labels.
Для каждого arm знаменатель одинаков: N_assigned. Missing human annotation
не превращать в pass: добрать разметку до analysis lock либо показать bounds
и не делать подтверждающий вывод.

Обязательные разрезы: N_assigned/N_valid/N_rated, причины missing, чистый
LQA-risk среди полученных переводов, lower/upper bounds с учётом missing
outputs, категории и severity. Снижение только API failures не считается
улучшением языка. Complete-case paired анализ — sensitivity, не замена ITT.

Для E/F отдельно оценить полный pipeline B→E/B→F и conditional repair effect
на общем наборе успешных B. Failure B остаётся в обоих pipeline denominators.
Все arms/repeats, включая E/F, сохраняются связанными при resampling.

Вторичные: error points на 100 фиксированных строк (1/5/25 — выбранные
веса, не универсальный MQM стандарт), critical и token failures, fluency,
blind preference с ties, human post-edit time на отдельном сбалансированном
срезе, стоимость/latency/coverage. Reviewer precision/recall измерять на B
до repair по человеческим ошибкам; финальное качество — после repair.

COMET/XCOMET, chrF и LLM-MQM — exploratory. Для reference-based метрики
нужен независимо проверенный ZH reference, скрытый от генерации. Без него
такую метрику опустить. Один и тот же source подаётся scorer для всех arms
в одном анализе; RU-scored и EN-scored результаты разделяются. Зафиксировать
checkpoint/tokenizer. Не нормировать A по русским словам, а B по английским.

## 8. Статистический план и правила решения

Для arm a: Y_ia = 1 при непригодном результате, иначе 0.
Разности Δ1 = pB − pA, Δ2 = pC − pB, Δ3 = pF − pE; меньше лучше.
Нулевые гипотезы: соответствующая Δ ≥ 0. Семья трёх основных сравнений —
Holm, family-wise alpha 0.05. Вторичные сравнения помечать exploratory.

До holdout выбрать веса игр/жанров и повторов. Для вывода о выбранных играх
они фиксированы как страты; resampling переносит целые независимые сцены или
семейства шаблонов с полным вектором arms. Сначала усреднить повторы внутри
строки либо использовать заранее заданную вложенную модель. Не выдавать
повторы/похожие строки за независимое N. Публиковать paired cluster CIs и
эффекты каждой игры. Если независимых кластеров слишком мало, только
описательный вывод. Для переноса на новые игры нужны новые игры как реплики.

До раскрытия holdout реализовать и проверить статистический метод на
synthetic null и planted effect с известным результатом; зафиксировать число
bootstrap/simulation iterations и seed. Можно использовать консервативные
Bonferroni simultaneous CIs для трёх разностей и Holm-adjusted p-values;
интервалы и тесты явно подписать, не выдавать обычные 95% CI за adjusted.
Альтернативный метод требует preregistration, а не выбора по результату.

Пилот оценивает variance, discordant pairs, ICC/cluster dependence, missing,
rater agreement и время. По ним симулировать размер holdout при мощности
80–90%, alpha и множественности выбранного метода. Провести sensitivity к
неопределённости пилотных параметров. Holdout не использовать для power tuning.

Предложение минимально полезного эффекта — 2 п.п.; это не согласованный
порог. Зафиксировать отдельно полезный operational effect и требуемое
свидетельство linguistic improvement. Для superiority верхняя граница
скорректированного CI ниже 0, а точечный эффект достигает полезного порога.
Чтобы заявить «эффект не меньше порога», весь CI должен лежать за этим порогом.

До holdout заполнить safety decision table:

| Endpoint | Знаменатель | Допустимая прибавка риска | Решение |
| --- | --- | --- | --- |
| Critical-only | ITT с отдельным учётом неизвестных исходов | Требует решения владельца | Верхняя односторонняя граница treatment−control ниже margin |
| Functional/token failures | ITT | Требует решения владельца | То же правило |
| Failure/abstain | ITT | Требует решения владельца | То же правило |

Определить семейство safety tests и multiplicity до анализа. Недостаточная
мощность не даёт права сказать «без регрессии». Ноль critical не доказывает
нулевой риск; bound должен соответствовать зависимости данных. Все новые
critical разобрать. Цена и время имеют отдельные пределы, выбранные владельцем.

Без полезного и устойчивого эффекта сохранить текущую политику. Если эффект
только в жанре, рекомендовать этот scope. H2/H3 могут подтвердиться независимо
от H1. Широкий CI означает «неопределённо», не равенство методов. Удачный пилот
не является основанием глобального default или rollout.

## 10. Пошаговое исполнение и контрольные точки

**Выход:** `decisions.md` с датами, формулировками владельца и статусами gates.

1. Прочитать документы и README пакета из §5a; проверить `git status`,

3. Если выбора нет, представить пользователю 120-строчный mix и альтернативы

4. Зафиксировать screening/confirmatory scope, точные профили выбранных

### Задача 1. Подготовить и заморозить корпус

1. Проверить локальный пакет из §5a офлайн-валидатором. Исходные строки
   четырёх компонентов и глоссарии уже выгружены; не повторять GET. Если

2. Проверить stable alignment, duplicates, blanks, stale/review provenance,

3. Отделить clean и stress; собрать сценовый контекст и concept glossary.
4. Выполнить воспроизводимое sampling по кластерам; записать квоты,

5. Зафиксировать hashes и splits; получить подтверждение вычитки конкретных

**Gate G1:** имеется точный воспроизводимый корпус и его eligibility report;

### Задача 2. Подготовить офлайн-инструмент и preregistration

**Предлагаемые файлы:** `analysis/probes/dual_reference_zh/prepare.py`,
`payloads.py`, `run.py`, `analyze.py`, `tests/test_protocol.py`.
Создавать только нужные части, без нового общего framework. Не импортировать
рабочие задачи Celery и не использовать API, записывающие перевод в Weblate.

1. На synthetic fixtures написать проверки реальных рисков: A/B без второй

2. Проверить, что тесты обнаруживают эти нарушения, затем реализовать
   минимальные snapshot/payload/logging/analysis функции.
3. Dry-run без сети: показать payload examples, job count, projected tokens,

   HTTP inference, а не только запись результатов.
4. Зафиксировать profiles, prompt hashes, randomization, rubric, metrics,

Предлагаемый CLI-контракт после реализации: `prepare --dry-run` строит и
проверяет задания без model calls; `run` требует study manifest с разрешённым
budget и закрытыми gates; `analyze` не вызывает модели. Агент обязан записать
точные рабочие команды и зависимости в study README, проверить их на fixtures

создания tests, scoped `uv run prek run --files <созданные файлы>`;

**Gate G2:** dry-run проверен, dataset snapshot принят, режим оценки и
расходный лимит согласованы; запуск конкретного пилота подтверждён владельцем.

### Задача 3. Калибровка и пилот

1. На отдельном calibration set отладить rubric и packets, измерить скорость
   разметки; не использовать holdout или выбранные test outputs для tuning.
2. Выполнить A–D в перемешанном порядке блоков; сохранить B неизменным.
3. Выполнить E/F с тем же B, логируя review и edit независимо.
4. Сделать заранее назначенные повторные прогоны; повторы не повышают N строк.
5. Провести выбранный режим оценки, арбитраж и pilot analysis; посчитать
   agreement, variance, paired discordance, failures, costs и cluster counts.

На 120 строк с двумя judge seat: 480 generation + 480 review + 240 edit
сегментных операций до повторов, то есть 1200 операций и 720 итоговых outputs.
Общая формула: (6 + 2J) × N, где J — число review seat в каждом из E/F.
Дополнительная автоматическая оценка и calibration сюда не включены. Двойная LQA — 1440 карточек; при t минут на
карточку это 24t часов плюс подготовка опор и арбитраж. Batch снижает число
API-вызовов, но не количество оцениваемых outputs. Реальную стоимость измерить.

**Gate G3:** пилот воспроизводим и позволяет рассчитать следующий этап;
в отчёте нет утверждения, что exploratory победитель уже доказан.

### Задача 4. Зарегистрировать подтверждающий этап

1. Симулировать power по пилоту и консервативным параметрам; предложить
   объём/стоимость или честно указать недостижимость нужной точности.
2. Утвердить полезный эффект, safety margins, экономические ограничения,
   веса, multiplicity и конечный план анализа §8.
3. Зафиксировать неизменяемый preregistration commit и закрытый holdout.
   Если prompts поменялись после пилота, явно зарегистрировать новую версию.

**Gate G4:** подтверждающий протокол и бюджет согласованы до holdout inference.
Если независимая LQA недоступна, завершить screening report с ограниченным
выводом; не заменять этот gate согласием нескольких моделей.

### Задача 5. Holdout, анализ и итоговый отчёт

1. Выполнить зарегистрированные условия без optional stopping по результату.
2. Завершить blind annotation и adjudication; заморозить ratings до unblinding.
3. Запустить зафиксированный анализ, показать все основные контрасты,
   intervals, denominators, safety endpoints и отклонения, включая неудачи.
4. Сопоставить эффект, стоимость и scope с decision rules. Сформулировать
   «подтверждено», «не подтверждено» или «неопределённо» отдельно для H1–H3.
5. Сохранить агрегатный measurement report и обновить статус этого плана.
   Продуктовые изменения предложить отдельным планом; не выполнять rollout.

**Gate G5:** итог можно воспроизвести из manifests/logs/ratings; conclusion
не шире популяции и точности эксперимента.

## 11. Остановка, отклонения и критерии завершения

Остановить отправку новых запросов при исчерпании согласованного бюджета,
смене модели без регистрации, обнаружении утечки/ошибки alignment или нарушении
идентичности общего B. Это техническая остановка, не остановка «потому что
победитель уже виден». Повреждённый блок отметить, решение о повторе принимать
по зарегистрированному правилу до просмотра его эффекта. Сохранять исходные
артефакты; новую попытку не подменять старой.

В отчёте обязательны: вопрос/популяция; диаграмма отбора и exclusions;
таблица arm settings; число assigned/valid/rated; agreement; главные эффекты
с CI и multiplicity; severity/categories; failures и coverage; стоимость;
стресс-набор; deviations; ограничения; решение по каждой гипотезе.

Исследование считается завершённым либо как подтверждающее при G5, либо как
честно ограниченный screening с выполненными согласованными задачами и
перечнем недостающих доказательств. «Неопределённо» — допустимый научный
результат, не причина скрывать данные или подбирать новый промпт на holdout.

Текущий checklist: G0–G5 открыты; research, candidate inventory и локальная
выгрузка с предложением 120 строк выполнены. Структурная часть задачи 1
проверена; согласование, review provenance и смысловая сверка остаются открытыми.
Первое действие следующего агента — задача 0, а не запуск генерации.
