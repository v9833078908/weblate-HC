# План: внутрипрогонный канон терминов (session canon)

Дата: 2026-08-17. Обновлён: 2026-08-18 (инженерное ревью gstack).
Статус: **не начат; отревьюирован, ждёт одобрения на реализацию**.

**Цель:** термин, которого нет в глоссарии, должен переводиться одинаково в
пределах одного прогона автоперевода — и по итогам прогона предлагаться в
глоссарий человеку. Механизм включается флагом настройки сервиса, по
умолчанию выключен, включается пер-проектно (для теста на проде).

## Мотивация, измеренная

- На `col4/data/fr` **84 из 146** групп с одинаковым источником переведены
  по-разному; стоковый чек `inconsistent` не пометил ни одной
  (`docs/llm-first/plans/2026-08-14-intra-component-consistency-check.md`).
  Замер не разбит на уровни A/B — сделать это частью продового замера (ниже):
  аппарат инъекции окупается, только если значимая доля групп — уровень B,
  а не точные повторы, которые кэш и так во многом дедуплицирует.
- У Cathedral механизм `first_mentions` — самый весомый рычаг конвейера:
  23.4 % строк стадии правки закрываются подстановкой канона
  (`docs/llm-first/research/2026-08-11-cathedral-localizer-analysis.md`, раздел 4.1:
  ключ `(source_lang, source_text[, semantic_tag])`, подстрочный отбор ≥ 3
  символов, **до 15 пар** в секцию `Glossary / Previous Mentions`). Оговорка:
  23.4 % — это **жёсткая подстановка без вызова модели**, что здесь вне
  объёма (v2); прямого измеренного числа для мягкой инъекции непроверенного
  машинного термина нет. 23.4 % ограничивает потенциал сверху, не снизу.
- **Ограничение охвата:** канон сессионный и непостоянный, поэтому
  структурно не лечит межпрогонный дрейф (84 группы на col4 почти наверняка
  накоплены за многие инкрементальные прогоны). Единственная межпрогонная
  долговечность — кандидаты → человек → глоссарий. Сидинг канона из уже
  существующих same-source переводов БД — возможный v2 (см. «Не входит»).

Три уровня дефекта:

| Уровень | Пример | Покрытие этим планом |
|---|---|---|
| A. Точный повтор источника под разными ключами | `幸存国家 {0}` | да |
| B. Короткий термин-юнит, позже входящий в длинные строки | «Урон» → «Получено урона» | да (подстрока/стем) |
| C. Термин, живущий только внутри длинных строк | — | **нет** (alignment-извлечение, вне объёма) |

## Внешняя валидация (2026-08-17, три независимых исследования)

- Мягкая инъекция терминов в промпт поднимает и точность терминов, и общее
  качество; жёсткое навязывание хуже гибкого (WMT25 findings
  <https://aclanthology.org/2025.wmt-1.30/>, DuTerm
  <https://aclanthology.org/2025.wmt-1.112/>).
- Переиспользование собственных принятых переводов прогона как контекста —
  опубликованный работающий механизм (SELF-RAMT
  <https://aclanthology.org/2025.wmt-1.13/>, оптимум K=3); model collapse —
  про рекурсивное обучение, не про ограниченный inference-reuse
  (<https://www.nature.com/articles/s41586-024-07566-y>).
- Few-shot остаётся человеческим: качество target'ов демонстраций —
  доминирующий сигнал ICL (<https://aclanthology.org/2023.findings-emnlp.61/>).
- First-accepted-wins — норма CAT (Phrase Repetitions
  <https://support.phrase.com/hc/en-us/articles/5709708706460-Repetitions-TMS>);
  кандидаты в термбазу через человека — стандартный workflow
  (memoQ Candidates, Smartling suggested→approved); динамический контекст в
  ключе MT-кэша — прецедент Tolgee
  (<https://github.com/tolgee/tolgee-platform/commit/77c3de4fc74e3ba1ef7cccd51dd1eb257494aa0a>).
- Ни один мейнстрим-инструмент не распространяет машинный вывод внутри
  задания без гейта; наш дизайн (инъекция в промпт + обязательный вызов
  модели) консервативнее индустрии.

## Переиспользуемые поверхности (не строим заново)

- `fetch_glossary_terms` + глоссарный матчер, `LLMGlossaryEntry` (с `flags`) —
  канон входит той же дорогой, что человеческий глоссарий.
- Alert-инфраструктура: `details` JSONField + dismissable (`alert.py:65-78`).
- `unit.machinery` (in-memory слой результата), `store_results` как точка
  принятия перевода.
- Пополевой оверрайд настроек проекта (`project.py:1332-1351`).
- `count_inflected` (`weblate/checks/morphology.py`) для стем-матчинга.

## Решения

1. **Флаг.** `session_canon` — `BooleanField(required=False)` в
   `LLMBasicMachineryForm` (`weblate/machinery/forms.py:469`), по умолчанию
   выключен. Чтение: `self.settings.get("session_canon")`. Включение на
   проде для теста — пер-проектной настройкой машинерии (пополевой оверрайд,
   `project.py:1332-1351`): глобальная конфигурация остаётся выключенной.
   С выключенным флагом поведение сервиса бит-в-бит прежнее (тест).
2. **Жизненный цикл и охват.** `self._session_canon: dict[str, CanonEntry]` +
   `threading.Lock`, инициализация в `__init__`. Никакого ensure/clear:
   инстанс умирает с прогоном. Паттерн `_secondary_context_cache` не
   копировать — он call-scoped и обнулил бы канон каждые 10 строк.
   Инстанс сервиса создаётся per-Translation (`autotranslate.py:613`), поэтому
   охват канона и кандидатов — **per-(component, target_language)**, а не на
   весь запуск автоперевода: источник один, но рендеринги в разные языки
   независимы, и межъязыковая консистентность целью не является.
3. **Ключ.** Нормализация — общий Django-free хелпер
   `weblate_customization.textkey` (NFC, casefold, вырезать плейсхолдеры
   `{0}`/`%KEY%`, схлопнуть пробелы, срезать конечную пунктуацию).
   Тот же хелпер обязан использоваться RepeatDriftCheck и гейтом
   (`docs/llm-first/plans/2026-08-10-git-localization-quality-gate.md`, Task 4) —
   две реализации группировки запрещены (контракт документарный, пока те
   планы не перейдут на импорт — риск R5). Дизамбигуация: для ключей
   ≤ 3 символов в ключ входит `unit.context` (приём Cathedral 4.1 —
   «m» метр vs минута). Источники с плюральными формами не канонизируются:
   какую форму считать каноном термина — неоднозначно, а уровень терминов —
   короткие сингулярные юниты.
4. **Наполнение — в точке принятия, не выборки.** Запись — в `store_results`
   (`autotranslate.py:685`) сразу после `self.update(unit, …)`, по
   **принятому** (сохранённому, post-autofix) `unit.target`, а не на выходе
   `_fetch_llm_batch`: канонизировать нужно то, что реально легло в файл
   (first-accepted-wins, не first-fetched-wins). Это же покрывает юниты,
   отданные из кэша переводов, — они минуют LLM-вызов, но проходят через
   `store_results`. `fetch_mt` складывает канон-движки (LLM с включённым
   флагом) в `self._canon_engines`; `store_results` зовёт
   `service.record_session_canon(unit)` для каждого. Только term-like
   источники (≤ 4 слов, ≥ 3 символов, есть буквенный токен, не только стоп-/
   служебные слова, без терминальной пунктуации предложения, не из одних
   плейсхолдеров, не плюральные) записываются. Источники, уже покрытые
   глоссарием по тому же ключу, не канонизируются. Конфликт (тот же ключ,
   другой target): первый записанный побеждает, второй логируется.
   **Недетерминизм между прогонами:** при `batch_concurrency = 2` порядок
   принятия батчей = порядок завершения futures, поэтому какой из
   конкурирующих рендерингов станет каноном, между прогонами не гарантирован;
   детерминизм есть только внутри одного прогона (и до первой инвалидации
   кэша). Приемлемо для v1; лог конфликтов — источник истины.
5. **Инъекция.** В `_get_batch_glossary` (`llm.py:1177`): канон-записи, чей
   ключ входит в источник юнита, добавляются как `LLMGlossaryEntry` с флагом
   происхождения `session-canon`, **в конце** глоссарной секции (стабильный
   префикс промпта — см. комментарий `_get_full_glossary` о кэшируемом
   префиксе). Матчинг: подстрока всегда; стем через `count_inflected`
   (`weblate/checks/morphology.py`) — только для языков источника с
   поддержанной морфологией, иначе graceful degradation до подстроки. Кап 15
   записей на запрос (потолок Cathedral 4.1; ожидаемый оптимум 3-5 по
   SELF-RAMT/BSC), ранжирование: число вхождений, длина термина. Человеческий
   глоссарный термин вытесняет канон-запись с тем же ключом всегда. Каждая
   инъекция инкрементит `occurrences` записи (инъекция = доказательство
   повторного использования; иначе термин уровня B, живущий только внутри
   длинных строк, навсегда остался бы с `occurrences = 1` и не дошёл бы до
   кандидатов).
6. **Кэш — без новой части ключа.** Отдельная часть ключа не нужна: ключ уже
   включает `get_llm_glossary_cache_part(unit)` (`llm.py:1131`), которая
   хэширует `_get_batch_glossary([unit])`; как только канон-записи входят в
   эту секцию, глоссарная часть ключа меняется сама. Задача 5 — только тест,
   что это так (и что нерелевантная запись ключ не меняет, плюральный путь
   не тронут).
7. **Кандидаты в глоссарий.** В `process_mt` после `post_process`
   (`autotranslate.py:673`), пока `self._canon_engines` в скоупе: для каждого
   канон-движка `get_session_canon_candidates()` (записи с ≥ 2 вхождениями,
   отсутствующие в глоссарии) поднимают/обновляют на компоненте
   dismissable-алерт `GlossaryTermCandidates` с `details` = список
   `{source, target, occurrences, language}`, **пер-язык** (один прогон —
   один целевой язык; details одного языка не затирает другой). Продюсер
   вносит принятые термины штатным UI глоссария (или loc-kit append), алерт
   закрывает. **Автозаписи в глоссарий нет.** Снятый (dismissed) алерт
   воскресает следующим прогоном только если множество кандидатов
   `{(source, target)}` изменилось (новые термины/рендеринги); тот же набор
   остаётся снятым — ни nag-петли, ни потери новых кандидатов.
8. **Наблюдаемость.** Каждая инъекция логируется (pk юнита, ключи записей);
   счётчики прогона: записей в каноне, инъекций, конфликтов — в тот же лог.

## Совместная работа с LLM-as-Judge (`2026-08-13-01-judge-verdict-core.md`)

Разделение ролей: канон — **предотвращение** дрейфа при генерации, судья —
**детекция** качества после, RepeatDriftCheck — детекция остаточного дрейфа.

- **Судья канона не видит — намеренно.** Независимость мест коллегии —
  измеренное ядро дизайна судьи (B2': переголосования снимали настоящие
  дефекты, 46 ошибочных снятий из 48). Вердикт судьи по канонизированной
  строке — единственная внутриконвейерная защита от плохого first-accepted
  рендеринга: если судья валит строку, у которой рендеринг пришёл из канона,
  это сигнал на весь канонический ключ, а не шум (в v1 сигнал информационный —
  человек правит по карточке судьи; автоэвикция канон-ключа — v2, риск R1).
- **Починка видит канон автоматически и бесплатно.** Стадия починки — обычный
  вызов движка перевода (план судьи, нативный механизм 1): внутри того же
  прогона канон подмешается сам; в отдельном позднем прогоне канон пуст, и
  починка опирается на глоссарий, куда частые записи к тому времени внесены
  человеком из кандидатов. Ничего специально соединять не нужно. Ограничение:
  внутри того же прогона починка юнита, упавшего из-за плохой канон-записи,
  реинжектит её же (риск R1).
- **Протухание вердикта не затронуто:** хэши вердикта считаются от текста
  перевода, канон меняет только промпт.
- **Кандидаты ревьюятся там же, где видна карточка «Оценка ИИ»** (задача 12
  плана судьи): продюсер видит вердикты по юнитам-носителям термина в
  момент решения о глоссарии. Обогащение алерта судейской статистикой —
  возможное v2, не в этом плане.

## Не входит

- Уровень C (alignment-извлечение терминов из длинных строк).
- Прямая подстановка повторов без вызова модели (индустрия подставляет
  только человечески-подтверждённое; наш канон машинный). Возможное v2
  после замера.
- Автозапись в глоссарий; персистентность канона между прогонами.
- Изменения few-shot (`_filter_confirmed_examples`) и судейского промпта.
- UI сверх алерта (отдельные страницы, кнопки «принять термин» — v2).
- Автоматическая эвикция плохой канон-записи по сигналу судьи (v2 после
  замера частоты дефекта — риск R1).
- Сидинг канона из существующих same-source переводов БД против межпрогонного
  дрейфа (v2, если остаточный дрейф после глоссарного uptake значим).

## Риски и ограничения v1

- **R1. Плохой first-accepted распространяется до конца прогона.** Эвикции
  нет: одна плохая канон-запись подмешивается во все поздние юниты, а починка
  того же прогона реинжектит её же (консистентно-неправильно хуже, чем
  неконсистентно-правильно). Смягчение: глоссарный uptake вытесняет канон
  навсегда; судья + карточка «Оценка ИИ» дают человеку сигнал. Автовытеснение
  — v2.
- **R2. Ложные инъекции от подстроки/стема** (гомографы: «мир» → «мировой»).
  Инъекция мягкая (подсказка в конце глоссарной секции, модель вправе
  игнорировать), вред низкий; шум измеряется на проде через долю строк с
  бесполезной канон-записью.
- **R3. Петля ценности зависит от ручного uptake.** UI «принять термин» — v2;
  без него постоянство держится на ручном внесении в глоссарий. Alert-усталость
  смягчена порогом ≥ 2 и воскрешением алерта только по дельте кандидатов
  (Решение 7).
- **R4. `count_inflected` — зависимость из `weblate/checks/` в горячем пути.**
  ImportError-фолбэк выключает и `textkey`, и морфологию (один warning, канон
  off / подстрока-only). Стоимость матчинга ограничена: словарь канона мал
  (≤ кап на компонент-язык), матчинг — по юниту.
- **R5. Контракт «одна нормализация» не форсируется задачей.** `textkey`
  импортируют RepeatDriftCheck и гейт, но миграцию тех планов на импорт ни
  одна задача здесь не делает — риск двух реализаций, если те планы
  зашипятся со своей. Мониторить при их реализации.
