# Полный цикл Weblate и FastAPI: состояние и план реализации

> **Для исполнителей:** использовать `executing-plans` либо
> `subagent-driven-development` после согласования реализации. Выполнять задачи
> по порядку, отмечая шаги checkbox.

**Статус:** локальная реализация серверных задач 1–4 в процессе проверки.
Визард доработан отдельно; merge и deployment не выполнены.
Результаты: `docs/product/reports/2026-10-19-weblate-quality-v2-local-validation.md`.

**Цель:** визард запускает по API перевод, двух судей, исправления, обязательную
терминологическую проверку, унификацию точных повторов, повторные проверки и
возвращает файл с достоверным итоговым статусом.

**Архитектура:** Weblate владеет переводами, проверками, выбором допустимого
варианта, записью и аудитом. FastAPI управляет последовательностью, хранит
состояние операций и строит экспорт. Producer API передаёт идентификаторы и
классификации; текст для файла скачивается отдельным штатным export API.

**Технологии:** Django/DRF, Celery, PostgreSQL; FastAPI, httpx,
SQLAlchemy/Alembic, SQLite, React/TypeScript.

**Спецификация:**
`docs/product/plans/2026-10-16-wizard-quality-cycle-canonical-repeats.md`.
Этот документ уточняет разделение обязанностей и критерии завершения,
не заменяя старые отчёты о сервере новой проверкой.

## Глобальные ограничения

- Один judge-run включает обоих судей. Два отдельных конкурирующих run не нужны.
- Вариант пригоден для автоматического применения только при актуальном
  контексте, parsed evidence обоих мест, коллегиальном PASS, допустимом состоянии
  и прохождении обязательных checks/glossary. По штатной шкале none/minor = PASS,
  major = FLAG, critical = REJECT. Один признак candidate_verified недостаточен.
- Глоссарий проверяет термины внутри фраз; repeat-drift сравнивает точные строки.
  Допустимое словоизменение не считается автоматически обязательной заменой.
- Ошибка одной строки не останавливает обработку остальных. Конфигурационные
  ошибки и отсутствие доступа не маскируются как успешный перевод.
- Не изменять approved, locked, independent, readonly и stale строки автоматически.
  Не записывать строки вне согласованного scope; участники группы за его пределами
  не становятся разрешёнными получателями только из-за членства в группе.
- Сначала индивидуальные исправления, потом новый состав групп и выбор канона.
  Исправленный судьями вариант получает приоритет после всех обязательных проверок.
  Конфликт нескольких таких вариантов нельзя разрешать номером строки.
- Максимум два внешних семантических repair-раунда; серверный внутренний лимит
  учитывается отдельно в бюджете. После лимита — объяснённые исключения.
- Любой mutating POST имеет идемпотентный ключ либо наблюдаемый remote resource.
  При неизвестном результате сначала GET-наблюдение, затем решение о повторе.
- Никаких прямых PATCH target для обхода judge/glossary/approval guards.
- Production deployment, рестарты и платные испытания не выполняются планом.

## Фокус ревью

1. Оба судьи успешно ответили, но кандидат получил major/critical: apply запрещён.
2. UI-проверка глоссария выключена: direct scan всё равно обнаруживает hard issue.
3. Судьи меняют один повтор: пересчитывается вся затронутая группа без записи вне scope.
4. Timeout после записи: повторное выполнение не создаёт дубликат изменения или run.
5. Между проверкой и экспортом меняется перевод либо глоссарий: старый snapshot не
   получает статус проверенного нового результата.

      значения, сохраняя исходную структуру и строки карантина.

**Приёмка:** содержимое файла относится к той версии, для которой выдан отчёт.

## Задача 8. Приёмка и выпуск

**Исполнители:** Weblate + FastAPI + владелец развёртывания.

- [ ] На локальном стенде использовать отдельный тестовый проект и немецкий язык;

- [ ] Пройти сценарий: судья исправляет повтор → новый вариант распространяется

- [ ] Пройти glossary-disabled, approved-conflict, partial failure, timeout,

- [ ] После review получить отдельное разрешение на deployment. Сделать резервную

- [ ] Провести ограниченную серверную приёмку; расширять использование после её PASS.

## Что требуется создать, а что переиспользовать

Судей, генерацию исправлений, glossary evaluator и repeat bulk engine создавать
заново не требуется. Часть недостающего серверного API уже написана локально.
API управления повторами, приоритет judge-updated канона, group-aware recheck,
полный snapshot и согласованное завершение являются оставшимися доработками.
Визарду нужен расширенный управляющий цикл и отчёт; второй собственный переводчик
или собственная реализация glossary/repeat правил не нужны.
