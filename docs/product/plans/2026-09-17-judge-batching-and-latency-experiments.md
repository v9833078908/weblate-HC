# Эксперименты: пакетная оценка Qwen и ускорение DeepSeek

Дата: 2026-09-17.
Статус: план для согласования. Разрешено составление документа, но не платные
запросы, реализация измерительного инструмента или изменение production.
Правила: `AGENTS.md`.

## Цель, решения и границы

Ответить последовательно на два вопроса:

1. Можно ли снизить стоимость оценки, передавая Qwen несколько строк вместо одной,
   без ухудшения качества и надёжности ответа?
2. Можно ли сократить время двухсудейской проверки, ускорив участника DeepSeek,
   без потери обнаружений, ради которых нужна пара судей?

Это план пункта 5 из обсуждения стоимости, не повторная реализация MT prerequisite,
не новая система биллинга и не миграция на одного судью. Пользователь подтвердил,
что `docs/product/plans/2026-09-16-03-mt-engine-selection-and-untranslated-judge-scope.md`
уже реализован; прежний статус этого документа не является основанием повторять
работу. Настоящий план не устанавливает статус внедрения его дальнейших дополнений.

В объёме: фиксированный корпус, человеческая разметка, ограниченный runner,
два последовательных A/B-эксперимента, независимое подтверждение финальной
конфигурации и отчёт с решением adopt/reject/inconclusive.

Не входят: изменение prompt/rubric/back-translation, удаление glossary/context,
каскад/QE, смена MT-движка, repair, увеличение cap, новая конкурентность запросов,
изменение lease, массовая перепроверка production и автоматический rollout.
Обычные переводы, approved-состояния и сохранённые production-вердикты неизменны.

Предпочтение: сначала ширина Qwen, затем один кандидат на место DeepSeek.
Не менять обе переменные одновременно. Если первое плечо отвергнуто, второе
проверяется с прежним Qwen batch=1, а не блокируется навсегда.

### Что установлено, а что не установлено

| Наблюдение в двух Anvil-прогонах | Следствие для эксперимента |
|---|---|
| DeepSeek batch=2, Qwen batch=1; 3004/3031 HTTP attempts на 2000 строк | База около 3000 объясняется настройками, не массовыми retries |
| Cached input составляет 77,74% суммарного input | Считать экономию со скидками кэша; не обещать выигрыш как на некэшированном prompt |
| DeepSeek: 89,23% completion — reasoning; медиана запроса 10,35/21,98 с | Главный кандидат на ускорение — генерация DeepSeek |
| Qwen: reasoning=0, медиана 2,01/2,18 с | Повторное «отключение thinking Qwen» ничего не оптимизирует |
| Различаются состав и длины строк двух запусков | Нельзя сравнить 5 ч 20 мин и 9 ч 11 мин как одинаковую нагрузку |
| Все 5997 Anvil usage rows без provider cost; 38 attempts без usage | $4,23/$5,38 — estimate, не invoice; неизвестные расходы остаются неизвестными |
| Есть повторная оценка одинакового контента конкурентными исполнителями | Нагрузочную проверку через Celery проводить только после отдельной защиты исполнения |

Количество исходных запросов без retries и округления отдельных групп:

| Плечо | DeepSeek batch | Qwen batch | HTTP на 2000 строк |
|---|---:|---:|---:|
| Контроль A0 | 2 | 1 | 3000 |
| A2 | 2 | 2 | 2000 |
| A5 | 2 | 5 | 1400 |

Это арифметика HTTP, не проценты экономии денег или времени. В реальном корпусе
считать сумму округлений по component/language группам; языки и разные проектные
контексты в одном запросе не смешивать. Batch DeepSeek в эксперименте A не менять.

Дополнительные основания:

- `docs/product/measurements/2026-09-03-judge-thinking-passthrough.md`:
  действующий Qwen no-think уже измерен; у DeepSeek no-think исчезли шесть
  прежних обнаружений на маленькой выборке. Согласие со stored verdict не
  равно human recall; это сигнал риска, не универсальная оценка качества.
- `docs/product/measurements/2026-08-13-phase0-measurements.md`:
  историческая пара давала более высокий recall, чем один судья. Старые модели,
  разметка и языки не валидируют сегодняшние aliases. Старый sealed test не
  использовать для нового подбора параметров.
- `docs/product/plans/2026-08-27-judge-set-ab-openrouter-vs-litellm.md`:
  полезен принцип screening → frozen winner → независимая проверка и оценка
  пары. Старые model IDs, параметры и статус не переносить как текущие.

Внешние первоисточники, разобранные в архиве:

- [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching):
  стабильный prefix и реальные cache-read rates; правила OpenAI не являются
  гарантией того же поведения корпоративного LiteLLM.
- [xCOMET](https://aclanthology.org/2024.tacl-1.54/): отдельное направление
  QE без длинной генерации, не основание подменить нынешний A/B внедрением QE.
- [Phrase AI Unit Calculation](https://support.phrase.com/hc/en-us/articles/14032731809052-AI-Unit-Calculation),
  [Crowdin usage limits](https://support.crowdin.com/crowdin-ai/#ai-usage-limits):
  прозрачные единицы расхода и ограничения, но не цена нашего judge.

Практики TMS поддерживают измерение полезности и расхода, но публичные документы
не раскрывают их внутренние batch sizes и число судей. Проценты маркетинговой
экономии не являются целевыми показателями HCGameLoc.

## Общий протокол измерений

### Среда и запрет скрытых изменений

Исполнение в отдельном worktree и изолированной QA-БД без фоновых workers,
способных самостоятельно отправить deferrals/repair. Корпус — разрешённая
зафиксированная копия, не динамический query к живому проекту.
Экспорт production-строк и доступ к production требуют отдельного разрешения.
Работа с локальным runner не требует выкладки защиты redelivery; любой поздний
Celery/production smoke требует её отдельно подтверждённого внедрения.

Использовать настоящий `run_judge_batch` и его scheduler с обоими seats:

    run_judge_batch(
        units,
        writable_ids=set(),
        user=None,
        use_cache=False,
        candidate_severities=(),
        mutating_repairs=False,
        evidence_run_id=experiment_invocation_id,
    )

Это наблюдаемый интерфейс `weblate/trans/judge_loop.py`, а не новая API.
`evidence_run_id` генерируется для каждого исполнения. Ledger пишется только в
QA-БД; «read-only» здесь относится к текстам и состояниям переводов, не к ledger.
Не запускать `AutoTranslate.process_judge` ради этого эксперимента: отсутствие
записей repair само по себе не исключает state projection и снятие approval.

Никакого MT, candidate creation, автоматического drain или live projection.
Проверить source/target/state до и после каждого исполнения. Пустые и неполные
переводы исключать с явным учётом до LLM, не заменять другими строками молча.

### Фиксация конфигурации и границ оплаты

Один запуск runner — один процесс с локальными настройками плеча; не менять
Django settings конкурентно в процессе. До отправки фиксировать безопасный
resolved profile каждого seat: alias/upstream/revision, batch, reasoning,
prompt schema, temperature, response format, stream, deadlines, retry policy,
adaptive policy и source commit. Полный `JudgeSeatProfile` сериализовать нельзя:
он содержит `api_key`. Изменение alias revision в середине сравнения делает
блок несопоставимым, а не молча новой точкой того же плеча.

В исследовании batch=2/1 — датированный baseline. Перед запуском проверить
его актуальность через разрешённые metadata/settings; если production уже другой,
перерегистрировать контроль, не выдавать историческую конфигурацию за текущую.

Перед платной стадией согласовать численно: число уникальных строк, повторов,
плеч и HTTP attempts (включая retries/fallback), максимальную длительность и
денежный предел. Без этих значений paid mode отказывается запускаться.
Dry-run выводит scope по языкам, формулу calls и расчётную стоимость с оговорками.
Ключи остаются в окружении процесса; не копировать их или заголовки в файлы.

Для измерений отключить автоматический fallback во всех плечах: иначе оценивается
другая модель. Отказ учитывать как отказ; надёжность fallback этим не проверяется.
Retries/adaptive остаются одинаковыми по политике; логировать их фактическое
влияние и ширину каждого POST. A5, сжавшийся до 1, не считается успехом batch=5.

Ограничитель расходов находится на границе каждого исходящего POST, включая
внутренние retries/isolation: резервировать попытку до отправки, а не считать
только внешние вызовы runner. Это локальный измерительный guard, не продуктовый
billing subsystem. При ошибке бюджета/авторизации или остановке запретить новые
POST; уже начатые учесть и дождаться в рамках deadline. Перезапуск runner не
повторяет завершённые блоки без явного нового разрешения; неопределённый исход
после crash остаётся unknown и расходует резерв попытки.

Локальный estimate не гарантирует жёсткий денежный предел при неизвестной цене
таймаута или неограниченном output. Для строгого денежного потолка нужен
подтверждённый provider-side limit; иначе согласовать именно ограниченные attempts
и остаточный денежный риск. Не выставлять низкий `max_tokens` ради видимости
контроля: обрезанный JSON меняет сравниваемое поведение.

### Корпус, разметка и повторяемость

- Две отдельные части: development для выбора и новый held-out для подтверждения.
  Разделять по исходной строке/семейству, а не по переводам или мутациям одной
  строки: их варианты не должны оказаться по разные стороны split.
- Покрыть en/fr/ja/ko/zh_Hans/zh_Hant для Anvil; фиксировать реальный source language.
  Выводы для иных языков не делать. Страты: UI/длинные тексты, терминология,
  контекстно неоднозначные строки, clean/major/critical; добавить глоссарные строки
  отдельно, чтобы дешёвый glossary не маскировал длинный лок-кит.
- Иметь репрезентативную случайную часть для стоимости/ложных замечаний и отдельный
  defect-enriched challenge set. Не переносить искусственную долю ошибок на
  production; агрегаты взвешивать только по известным весам реального scope.
- Human labels формируются до просмотра ответов плеч. Разметчик знает язык и
  получает source, target, matched glossary, explanation и проектный контекст.
  Спорные critical и расхождения решает второй компетентный человек; фиксировать
  неопределённую разметку отдельно, не выбирать удобный verdict модели как gold.
- Development smoke: предложено до 60 строк, по 10 на язык, один повтор; он может
  отсеять неработающее плечо, но не подтвердить качество. Основное сравнение —
  минимум три повтора каждого плеча на одинаковом корпусе. Это предложение
  объёма, не разрешение оплатить его.
- Размер held-out определить до calls по выбранным quality margins и числу
  независимых defect/clean примеров; нехватка данных означает inconclusive.
  Повторы одной строки не увеличивают количество независимых gold-примеров.
- Порядок плеч чередовать по заранее сохранённому расписанию блоков; не запускать
  все контрольные запросы утром, а кандидата вечером. Внутри повтора у плеч
  одинаковый порядок строк; между повторами использовать фиксированные seeds.
  Не смешивать разные языки/проектные контексты ради наполнения batch.
- Provider cache не выключать. Отдельно показывать первые и последующие блоки,
  фактические cache hits и стоимость. Не называть первый запрос cold без evidence.
  Прогрев, если нужен, объявляется заранее и входит в бюджет.

### Метрики и предложенные критерии решения

Считать per-seat и pair-level; у пары сохраняется текущая max-severity политика.
Измерять отдельно обнаружение gold major/critical и правильность severity;
critical→pass и critical→minor не прятать в общем «ошибка найдена».

Обязательные метрики:

- Critical misses, major recall, false flags на gold-clean, false-critical,
  уникальные полезные обнаружения каждого seat и разногласия между повторами.
- JSON/ID/cardinality failures, окончательные unparsed, timeouts, retries,
  adaptive reductions, число строк с двумя пригодными заключениями.
- HTTP p50/p95, полное wall-clock одного и того же двухсудейского scope,
  стоимость и tokens на 1000 уникальных target-language строк; длины и языки.
- Prompt/cached/completion/reasoning, provider-reported cost, estimate и unmetered
  attempts раздельно. Reasoning входит в completion, cached входит в prompt.
- Доля полезных замечаний после human adjudication; время человеческого разбора
  измерять, если заявляется экономия труда, иначе не делать такой вывод.

Нельзя удалить failed/unparsed строки из знаменателя и показать высокий recall
только по успешно разобранным. Для них показывать отсутствие покрытия; безопасный
консервативный расчёт считает отсутствие обнаружения пропуском для gold-defect.

Предложение для предварительного согласования, не уже установленная политика:

1. Ноль новых подтверждённых критических пропусков относительно контроля на
   held-out; любой такой случай останавливает принятие до разбора.
2. Односторонняя 95% граница ухудшения pair-level major/critical recall не больше
   2 процентных пунктов, роста false flags не больше 3 п.п. Считать paired,
   с группировкой зависимых вариантов/повторов по семейству исходной строки;
   показывать результаты каждого языка, не только pooled показатель.
3. Нет новых нарушений ID/перестановок и мутаций данных; верхняя 95% граница
   роста terminal unparsed/timeout доли не больше 1 п.п. Если выборка не
   различает такие изменения, вывод inconclusive, а не «всё одинаково».
4. Для A: расчётная стоимость пары на строку ниже минимум на 10%, без измеренного
   увеличения wall-clock более 5%. Для B: wall-clock пары ниже минимум на 20%,
   без роста расчётной стоимости более 5%. Показывать paired интервалы эффекта;
   если они не отделяют выигрыш от шума, не принимать вариант автоматически.

Пороги — предложенная инженерная политика; владелец утверждает их и доступный
объём human review до платного сравнения. Нулевая наблюдаемая потеря на малом
корпусе не доказывает отсутствие потери вообще. После просмотра held-out нельзя
ослабить критерий и назвать это прохождением исходного gate.

## Задачи и зависимости

### Задача 1. Зарегистрировать корпус, плечи, бюджет и измерительный runner

**Результат:** воспроизводимый manifest и безопасный offline-verified инструмент;
до отдельного согласования он не отправляет платные запросы.

**Файлы и интерфейсы:** новый `analysis/probes/judge-cost-latency-ab.py`;
артефакты под новым `analysis/data/judge-cost-latency-ab/` с уникальной директорией
на эксперимент. Это предлагаемые пути, сейчас они не являются готовыми командами.
Продуктовые границы: `weblate/trans/judge.py:resolve_judge_seat_profile`,
`request_verdicts`, `_payload`, `_parse_reply`; `weblate/trans/judge_loop.py:run_judge_batch`.

Использовать существующие probes как образцы, не запускать их вслепую:
`analysis/probes/judge-rollout-canary.py` уже показывает no-repair контракт, но
выбирает первые строки одного языка и собирает ledger по глобальному PK watermark;
для A/B нужны frozen scope и собственные run/evidence IDs.
`analysis/probes/litellm-complement-smoke.py` — старый одноразовый smoke с ручной
сборкой payload и историческими thinking helpers, не универсальный benchmark.
`analysis/probes/col4-judge-eval.py` содержит историческое scoring, но не текущий
transport-контракт; статистические подходы сверить, старый payload не копировать.

**Действия:**

- [ ] Подготовить split, labels и manifest: corpus hash, source revision,
      configuration fingerprint, seeds, расписание, лимиты, критерии решения.
- [ ] Реализовать runner вокруг текущего `run_judge_batch`, не второй judge/parser.
      Настройки одного плеча фиксируются до создания thread pool, profiles не
      подменяются без пересчёта fingerprints; каждый повтор — свежий QA state.
- [ ] Вести журнал каждого POST и блоков эксперимента с безопасными идентификаторами.
      Сводить attempts/usage/verdicts по собственным IDs, не по общему времени/PK.
      Сохранять effective batch sizes, отказы и незавершённые попытки.
- [ ] Сделать offline dry-run режимом по умолчанию. Metadata GET тоже не выполнять
      скрыто: offline использует сохранённые snapshots, refresh требует разрешения.
- [ ] Проверить corpus privacy: тексты/разметка только в разрешённом закрытом
      хранилище, права файлов ограничены; в docs публиковать обезличенные агрегаты
      и manifest hash. Ключи и сырые provider errors никогда не публиковать.

## Готовность к исполнению и открытые решения

Порядок: регистрация/offline runner → A → B → независимое подтверждение →
отдельное решение о выкладке. Общий runner и manifest имеют одного владельца;
одновременные paid A/B запуски создают лишние provider/cache/rate-limit confounders.

До платных стадий остаётся согласовать:

- Кто обеспечивает human labels по каждому языку и доступ к корпусу.
- Quality/effect margins выше либо их замена до просмотра результатов; размер
  независимого held-out и допустимый вывод при недостаточной мощности.
- Конкретные aliases/control B после разрешённой проверки доступности.
- Численные request/time/money limits каждой стадии и provider-side quota,
  либо явное принятие остаточного денежного риска неизвестных начислений.

Это prerequisites платного исследования, не вопросы, которые предлагается
молча решить расходованием ключа. Текущий документ разрешает обсудить и утвердить
эксперимент; не утверждает, что новый batch или модель уже безопаснее/дешевле.
