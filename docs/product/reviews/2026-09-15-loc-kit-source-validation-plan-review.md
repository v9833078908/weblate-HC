# Ревью плана «Валидация разметки исходника при приёме лок-кита»

**Дата:** 2026-09-15.
**Рецензируется:** `docs/product/plans/2026-09-11-loc-kit-source-validation.md`
(статус: предложен, не реализован).
**Итог:** **проблема реальна, но план не одобрять до устранения трёх P0.**
Узкий дефект `</color=yellow>` подтверждён на живом производственном
материале, а текущая target-проверка принципиально не может заметить его при
точном повторении источника. Однако документ одновременно обещает
детерминированный построчный анализ и эвристику по соседним ключам, не задаёт
восстановление после синтаксической ошибки и ставит измерение ложных
срабатываний после реализации широкого набора правил.

## Что проверено

| Утверждение | Результат |
| --- | --- |
| `</color=yellow>` проходит текущую токенизацию | Подтверждается: `TAG_PATTERN` допускает после имени `=` или пробельный атрибут (`weblate/trans/protected_tokens.py:13-20`). Быстрый runtime-smoke вернул `closing_tag_matches=True`. |
| Точный перевод такого источника не получает `game-markup` | Подтверждается. Smoke на строке `SpawnRate` вернул одинаковые списки `markup_tokens`, `placeholders_match=True`, а обе причины вернуть `True` в `GameMarkupCheck.check_single()` ложны (`weblate_customization/src/weblate_customization/checks.py:393-411`). |
| Дефект не синтетический | Подтверждается полным LQA-экспортом Anvil Saga: `SpawnRate` содержит источник и FR target с тем же `</color=yellow>` (`analysis/data/anvil-saga-fr-lqa-golden-2026-09-11.json:92237-92239`). Аудит уже классифицирует его как дефект русского источника (`docs/operations/audits/2026-09-11-anvil-saga-fr-lqa.md:482-484`). |
| Предложенный `TAG_START` не ловит перечисленную обычную пунктуацию | Подтверждается throwaway-smoke с точной регулярной идеей плана: `HP > 50`, `<3`, `a -> b`, `Урон < 10`, `2 < 3 > 1`, `Стоимость: {0} (около 5 <)` и `<basic>` не дали tag-находок. |
| В доступных данных проблема распространена за пределами Anvil Saga | Пока не доказано. Полный Anvil export содержит 8 074 уникальных source string и один такой случай; полный export Heart Abyss/hub-1 — 370 строк, сохранённая частичная выгрузка Need for Greed — 331 уникальная строка; выборки repeat-drift ещё по восьми проектам — 107 source string. Других кандидатов закрывающего тега с атрибутом там нет. Подключённый MCP вернул 0 проектов, поэтому это не является текущим полным census production. |
| Имеющийся UI уже выводит parser warnings | Подтверждается: `create_component_from_kit()` кладёт все не-ERROR диагностики в `kit_info["warnings"]` (`weblate/utils/views.py:776-823`), а `CreateFromZip` выводит первые пять и счётчик остатка, не блокируя создание (`weblate/trans/views/create.py:730-737`). |

Точный pattern scan:

```regex
</(?:color|link|size|b|i|u|s|sprite)[=\s]
```

Сохранённые production-артефакты достаточны, чтобы подтвердить конкретную
дыру, но недостаточны, чтобы заранее принять все шесть новых эвристик как
высокоточные.

## Находки

### F1 (P0) — один дефект способен породить три диагностики

План одновременно требует, чтобы `source.tag_closing_has_attribute` имел
приоритет над `source.tag_malformed`, и чтобы несбалансированность считалась
по well-formed тегам. Но он не задаёт исключающие друг друга результаты и
восстановление стека.

Точная транскрипция предложенных `TAG_START` и `TAG_WELL_FORMED` на строке
525591 дала три результата: closing attribute `</color=yellow>`, malformed
начало `</color`, и unbalanced для оставшегося корректного `</color>`. Это
противоречит приёмке задачи 2: один битый ряд должен дать ровно одну
диагностику. Обычный `</sprite>` также не соответствует приведённой грамматике
(в её ветке закрывающих тегов нет `sprite`) и станет `tag_malformed`, хотя
план требует `tag_unbalanced`.

**Необходимая правка плана.** Сначала определить один лексический проход и
таблицу приоритета/восстановления. Лексер должен возвращать валидный токен или
одну ошибку с полным span; invalid token не участвует во втором проходе стека.
Для каждого corrupt span явно выбрать единственный код; если нужен
последующий баланс, описать синтетическое восстановление, которое не создаёт
каскадную находку. Добавить тесты на `</color=yellow>{0}</color>`,
`</sprite>`, ошибочный открывающий тег рядом с корректным закрывающим и два
независимых дефекта в одной строке.

### F2 (P0) — `source.tag_inner_whitespace` не является построчным правилом

Контракт задачи 1 — `source_markup_defects(text: str)`, чистая функция для
одной строки. Но `source.tag_inner_whitespace` требует сравнения с
«соседними строками того же key-prefix». Эти строки, ключи, граница группы и
даже смысл «соседней» строки не передаются функции.

В Weblate `SourceCheck` получает `check_source_unit(sources, unit)`, а не
группу соседних unit (`weblate/checks/base.py:503-514`). В CLI parser видит
строки листа, но сейчас не имеет общего правила группировки ключей. Поэтому
одно общее правило не сможет работать в обоих слоях так, как обещает план.

**Необходимая правка плана.** Исключить этот код из `source_markup_defects`.
Либо удалить его как неподтверждённую эвристику, либо вынести в отдельный
batch/group-check с явно указанными: нормализацией key-prefix, scope
(только один component), минимальным размером группы, исключениями и
политикой при смешанных образцах. До этого нужен отдельный measured precision
на реальных строках. В текущем плане его реализация блокируется.

### F3 (P0) — калибровка и корректный production census стоят после широкого изменения

Задача 5 — единственное место, где план требует посчитать ложные срабатывания,
но она идёт последней. Так широкие правила для условных плейсхолдеров,
подстановочных токенов и внутритеговых пробелов будут реализованы без данных
об их precision; один подтверждённый тег не доказывает их все.

Кроме того, описание probe как одного `GET .../units/` не задаёт cursor
pagination. Существующий Anvil artifact явно сообщает «cursor paginated»
(`analysis/data/anvil-saga-fr-lqa-golden-2026-09-11.json:7`), а действующая
production probe сначала читает source language для каждого компонента и
затем обходит URL единиц через `paginate(...?page_size=1000)`
(`analysis/probes/source-repeat-drift.py:147-182`). Одностраничный GET даст
ложно малый счётчик на больших компонентах.

**Необходимая правка плана.** Перенести измерение в Task 0 до разработки:

1. для каждого component получить его собственный `source_language`;
2. cursor-paginate именно source translation и хранить `(project, component,
   key/context, source)` только в read-only временном выводе;
3. для каждого кода сохранить счётчик, до трёх примеров и ручную
   классификацию кандидатов/ложных срабатываний;
4. по результату выбрать первый узкий набор правил. Сейчас им должен быть
   как минимум `source.tag_closing_has_attribute`; остальные включать только
   с измеренной точностью.

## Существенные P1

### F4 — правила conditional и token ссылаются на regex, который их не валидирует

`_CONDITIONAL_HEADER` проверяет лишь начало
`identifier:cond:comparison?`; он не требует `|` в теле и не ограничивает
синтаксис comparison (`weblate_customization/src/weblate_customization/checks.py:191-193,
250-283`). Следовательно, фраза плана «не разбирается
`_CONDITIONAL_HEADER`: потерянный `|`, битое сравнение» технически неверна.
Нужна закрытая грамматика именно всего conditional DSL и набор реальных
положительных/отрицательных примеров; иначе правило будет спорить с текущим
контрактом target-проверки.

`TOKEN_PATTERN` также не может найти заявленные подозрительные формы: он
принимает только ASCII lower-case identifier, непосредственно перед `[` и
только если внутри есть `|` (`checks.py:180-188`). Кириллица и пробел перед
`[` ему не соответствуют. Нужен отдельный кандидатный детектор с corpus
калибровкой, а не переиспользование этого pattern.

### F5 — preview и лимит диагностик описаны не по текущему коду

Новый шаблон для обычного component-creation flow не нужен: warning уже
проходит от parser через `kit_info` к message framework. Task 4 надо сократить
до contract test с битой строкой и проверить, что кнопка создания остаётся
доступной.

Напротив, ограничителя списка в parser/pipeline нет: они добавляют все
`Diagnostic`; UI лишь скрывает после первых пяти, оставляя весь список в
памяти (`loc_kit_ingest/parser.py:121-303`,
`weblate/utils/views.py:819-823`). Формулировка «как уже ограничены
предупреждения импорта» неверна. Нужны явные `per-component` cap, счётчик
suppressed diagnostics и правило, будут ли первые N стабильны по row/span.

### F6 — `SourceCheck` и поставка общей библиотеки заданы неполно

Новый класс обязан реализовать `check_source_unit(sources, unit)`, а не
`check_single`; план должен описать, как несколько дефектов складываются в
один boolean check, его description и source highlights. Иначе UI покажет
только общий `game-source-markup` без причины, хотя источник правил уже
возвращает `code`, `message`, `span`.

Отдельно, зарегистрированная проверка не должна «молчать», если
`loc_kit_ingest` недоступен. Это делает ошибку упаковки неотличимой от
здорового источника. Либо добавить pure module в обязательный image/package
контракт, либо не регистрировать check. Fallback без импорта подходит
опциональной кастомизации, но не заявленной защите source strings.

### F7 — охват source-полей и repository cleanup не определены

Для PO source ясен. Для обоих TBX grammar нужно явно перечислить, что
проверяется: source term, description, notes, section caption или только
публикуемые term/explanation. «Колонка source language» не выбирает между
этими semantic fields.

План меняет пользовательский импортный поток и добавляет check; по
`AGENTS.md` он должен предусмотреть запись в текущей unreleased секции
`docs/changes.rst`. Документация в producer guide полезна, но changelog не
заменяет.

## Условия одобрения

1. Оставить цель — ловить дефекты source, которые честный target-copy скрывает;
   она подтверждена и должна быть реализована.
2. Переписать Task 1 как single-pass lexer с исключающимися error codes,
   полным span и документированной error recovery; устранить конфликт
   `closing_has_attribute`/`malformed`/`unbalanced` и `</sprite>`.
3. Вынести `tag_inner_whitespace` из однострочного контракта в отдельный
   измеренный batch design либо удалить из этой поставки.
4. Начать с paginated read-only Task 0 и сузить первый релиз до
   измеренно-точных правил; приложить результат в
   `docs/operations/measurements/` до production rollout.
5. Заменить ложные ссылки на `_CONDITIONAL_HEADER` и `TOKEN_PATTERN` полными
   grammar/candidate contracts; зафиксировать scope TBX field-ов.
6. Переиспользовать существующий warning UI, добавить настоящий cap, explicit
   SourceCheck contract, обязательную доставку shared module и changelog.

После этих правок защита в двух слоях остаётся правильным направлением:
offline ingestion предупреждает до записи, а source check покрывает UI/API/VCS
пути. В текущем виде реализация создаст дублирующие диагностики, не сможет
выполнить одну из объявленных проверок и даст невалидный production measurement.
