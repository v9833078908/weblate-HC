# Ревью плана «Mass fix for failing checks»

**Дата:** 2026-09-08.
**Рецензируется:** `docs/product/plans/2026-08-25-mass-fix-failing-checks.md`
(статус: awaiting approval, ни одна задача не начата).
**Итог:** переработать перед одобрением. Ядро верное: `check:=<id>` выбирает
именно активные срабатывания, `Unit.translate()` - единственный поддерживаемый
путь записи, `unit.edit` (а не `source.edit`) - правильное право, форма
предпросмотра по образцу search-and-replace уместна. Но есть один P0
(номер `ActionEvents` уже занят), одна незакрытая архитектурная развилка
(второй массовый мутирующий путь рядом с `reapply_autofixes`), одна
недоописанная задача (Task 3 не доводит source до файлов), непроверяемая
гарантия детерминизма у терминальной пунктуации, потерянное взаимодействие с
судьёй, ошибка в i18n-каталоге, отсутствие обновления threat model и неверная
инструкция по тестам. Плюс девять устаревших ссылок на строки.

## Находки

### F1 (P0) - `ActionEvents = 105` уже занят

План (строки 198-202) требует `FIX_FAILING_CHECK = 105` «после текущего
максимума 104». Фактически `104` - `ALERT_REOPENED`, а `105` - уже
`JUDGE_RESOLUTION` (`weblate/trans/actions.py:646-653`). Исполнитель, следуя
плану буквально, получит коллизию значений enum и историю, в которой судейские
разрешения и массовые правки неотличимы.

Исправление: взять свободное значение (`106`) и запретить перенумерацию
существующих действий - они уже persisted в `Change`. Решение о членстве в
наборах при этом остаётся верным: `ACTIONS_CONTENT`
(`weblate/trans/actions.py:709-737`) и `ACTIONS_SHOW_CONTENT` (`:757-770`) -
да, `ACTIONS_REVERTABLE` (`:692-708`) - нет.

### F2 (P0/P1) - Появляется второй массовый мутирующий путь

`reapply_autofixes` уже прогоняет активный `AUTOFIX_LIST` по историческим
юнитам и обслуживает часть тех же дефектов (терминальная пунктуация, пробелы).
Два механизма расходятся по всем существенным правилам:

| | `reapply_autofixes` | движок плана |
| --- | --- | --- |
| Кто запускает | оператор в контейнере | пользователь с `unit.bulk_edit` |
| Актор в истории | бот, `AUTO` | запросивший пользователь, действие 105/106 |
| Source и template | исключены | Task 3 специально добавляет template-каскад |
| VCS | свой scoped commit на repository root, чужие pending отвергаются | обычные pending, коммит по общим правилам |
| Отбор | по автофиксам | по строкам `Check` |

Строка 374 («`reapply_autofixes` stays as is») эту развилку не решает, а
скрывает: один и тот же дефект в одной и той же строке будет исправлен
по-разному в зависимости от того, кто первым дошёл. Перед одобрением план
обязан выбрать один из вариантов и записать его:

1. **Владение по дефектам.** Автофиксы остаются единственным владельцем
   детерминированной косметики; UI-движок не берёт safe-tier вовсе и работает
   только по review-tier. Тогда safe-режим из плана исчезает, а объём Task 1
   резко сокращается.
2. **Владение по времени.** Автофиксы - на записи, UI-движок - на историческом
   корпусе; `reapply_autofixes` признаётся устаревшим и получает срок вывода.
3. **Осознанное сосуществование** с явной таблицей, кто чей дефект чинит, и
   тестом, доказывающим идемпотентность после прогона обоих.

Пока это не решено, план создаёт две разные политики безопасности для одной
мутации.

### F3 (P1) - Гарантия «фикс всегда снимает чек» для терминальной пунктуации недоказуема в заявленном виде

План (137-143) обещает общий помощник, который «добавляет или снимает
языкоуместный знак», и контракт «фикс обязан сделать чек пройденным». Код
терминальных чеков устроен сложнее, чем таблица знаков:

- `EndStopCheck` пропускает `th`/`jbo`, не проверяет источники короче пяти
  символов, разрешает пару «источник `...` / target `…`», у CJK принимает
  `：`, а в общем случае принимает целый набор `. 。 । ۔ ։ · ෴ ။ ።`
  (`weblate/checks/chars.py:293-331`).
- `EndColonCheck` `:341-366`, `EndQuestionCheck` `:378-412` (греческий - свой
  набор), `EndExclamationCheck` `:427-446` (`eu` требует `¡`, интерробанги
  исключены), `EndInterrobangCheck` `:449-454` - у каждого своя логика.
- Французской таблицы терминальных знаков в коде нет вовсе: для `fr`
  существуют только правила отбивки (`chars.py:29-39`,
  `PunctuationSpacingCheck` `:650+`).

Отсюда два следствия, которых в плане нет.

Первое: **чеки пересекаются**. Источник, кончающийся `.`, и target,
кончающийся `?`, роняет одновременно `end_stop` и `end_question`. Движок
работает по одному `check_id` за проход, поэтому «дописать точку» превратит
`?` в `?.` и уронит второй чек, а «снять вопрос» - смысловая правка. План
частично это ловит правилом «target уже кончается другим терминальным знаком →
manual» (170), но тогда сам этот класс и составляет основную часть корпуса, и
реальная доля исправимого резко ниже заявленной. Правило про пересечение надо
сформулировать явно и измерить долю manual **до** разработки UI на 250 строк.

Второе: помощник должен зеркалить исключения самих чеков, иначе фикс будет
предлагать изменение, не снимающее чек. Надёжнее инвертировать контракт:
фикс вычисляется, затем **чек перезапускается на результате**, и любой
неснявшийся случай уходит в manual. План это делает (167-169), но тогда
таблицу языков нужно описывать как оптимизацию, а не как гарантию.

### F4 (P1) - Task 3 не доводит source до файлов и требуется он ради одного чека

Цепочка проверена целиком: `Unit.translate` `:2452-2460` → `save_backend`
`:1752-1760,1842-1843` → `update_source_units` `:1891-1925` →
`update_unit_from_source_change` `:1983-1997` → `update_source_unit_state`
`:1949-1981`. План описывает её верно по существу, но:

- `update_source_unit_state` ставит `source`/`num_words` (`:1952-1954`), а
  `PendingUnitChange` создаётся только внутри ветвей, которые план и хочет
  подавить (`:1955-1981`). Одного `unit.save()` (`:1996-1997`) для записи в
  файл недостаточно. План это осознаёт (225-229), но требование
  «создать pending вручную для каждого записываемого sibling» - это и есть
  самая рискованная часть работы, и она описана одним абзацем.
- `previous_source` участвует в сериализации юнита
  (`weblate/trans/models/unit.py:1309-1325`) и показывается в UI только для
  fuzzy-строк. Подавляя fuzzy, план обязан зафиксировать, что
  `previous_source` при этом **не** обновляется, иначе следующая настоящая
  правка источника потеряет базу для сравнения.
- Прокидывание kwarg реально безопасно: у каждого из методов ровно один
  вызывающий (`:1843`, `:1907`, `:1995`), плюс прямой `save_backend` в тесте
  `weblate/trans/tests/test_edit.py:2612`. Требование - только keyword-only с
  дефолтом.

Отдельный вопрос соотношения цены и выгоды. Task 3 нужен ровно ради
source-side `ellipsis` (по census плана - 316 строк на весь инстанс). Он
меняет поведение общего пути записи ради косметики в одном чеке. Прежде чем
одобрять, план должен ответить: почему нельзя (а) не чинить source массово
вовсе, (б) починить `...` на входе - в loc-kit/конвертере, где источник
рождается, или (в) принять fuzzy как честное следствие изменения источника.

### F5 (P1) - Судья в плане отсутствует

Массовая правка target через `Unit.translate()` меняет текст, а значит
`JudgeVerdict.target_hash` перестаёт соответствовать (`is_stale`,
`weblate/trans/models/judge.py:869-871`), активный круг исчезает и
`run_checks` снимает `judge-*` строки. При ручном сохранении в редакторе
судейская перепроверка ставится в очередь явно
(`weblate/trans/views/edit.py:957-958`, `:883-901`), а движок плана этот путь
не проходит - он вызывает `Unit.translate()` напрямую.

То есть массовый прогон по компоненту с судейскими вердиктами молча обнулит
судейское состояние сотен строк и не поставит перепроверку. Это не обязательно
плохое решение (перепроверка платная), но оно должно быть **решением**: план
обязан сказать, что делает с вердиктами - оставляет устаревшими без действий,
показывает счётчик «вердиктов устарело: N» в результате задачи, или ставит
перепроверку по явному чекбоксу. Сейчас об этом нет ни строки, а взаимодействие
с судейским отчётом (changed-since-run) - самая заметная часть продукта.

### F6 (P1) - Не описан контракт полноты покрытия и исключение custom-чеков

Полный текущий census `get_fixup`: `BeginSpaceCheck`
(`weblate/checks/chars.py:176-181`), `KabyleCharactersCheck` (`:213-217`),
`EndSpaceCheck` (`:248-253`), `DoubleSpaceCheck` (`:274-275`),
`ZeroWidthSpaceCheck` (`:535-536`), `KashidaCheck` (`:620-621`),
`PunctuationSpacingCheck` (`:719-745`), `MarkdownLinkCheck`
(`weblate/checks/markup.py:571-575`), `ConsistencyCheck`
(`weblate/checks/consistency.py:493-499`). Отсюда три поправки:

- `FixupType` (`weblate/checks/base.py:36-38`) - union: не только
  `("regex", …)`, но и `("plurals", list[str])`, который отдаёт
  `ConsistencyCheck`. Формулировка Architecture (29-31) описывает контракт
  неполно, а `apply_fixup_python` (156-161) обязан обрабатывать оба варианта
  или явно отвергать `plurals`.
- `md-link` наследует `default_disabled = True`
  (`weblate/checks/markup.py:524-526`), то есть в safe-списке лежит чек,
  который в обычном компоненте не срабатывает. Это надо назвать, иначе tier
  выглядит как покрытие, которого нет.
- `KashidaCheck` использует синтаксис модуля `regex` (`\p{sc=Arab}`,
  `chars.py:608-617`), несовместимый со stdlib `re`. Обещанный в Task 1
  «parity test: каждый фикс применяется одинаково через Python `re`» на этом
  чеке невыполним как написано.
- Кастомные чеки (`game-*`, `cyrillic-leak`) не имеют `get_fixup` вовсе
  (`weblate_customization/src/weblate_customization/checks.py`), и план
  правильно оставляет их вне механизма. Но это стоит написать в разделе
  Out of scope прямо, потому что для продюсеров именно они и являются
  «ошибками».

Заодно: требование «флаги ограничены `gui`» (146) не отражает текущий
контракт - JS создаёт `new RegExp(value[1], value[3])` без белого списка
(`weblate/static/editor/full.js:577-588`). Ограничение можно вводить, но как
новое правило, а не как констатацию.

### F7 (P1) - Task 4 опирается на прогресс, которого нет

`auto_translate` (`weblate/trans/tasks.py:991-1120`) **не** вызывает
`current_task.update_state(PROGRESS)`; отдельный помощник
(`weblate/trans/tasks.py:363-367`) пишет только `{progress}`.
`store_task_metadata` (`weblate/utils/celery.py:51-78`) хранит ровно
`component_id`, `translation_id` и опционально `user_id`. Task API
(`weblate/api/views.py:4955-4967`) отдаёт `completed/progress/result/log` и не
различает `queued`/`running`/`failed`. Опрос в
`weblate/static/loader-bootstrap.js:1725-1810` обновляет ширину полосы и текст,
но `aria-valuenow` после первичного рендера не трогает, и `aria-live`-области
в `weblate/templates/message.html:4-33` нет.

Вывод: Task 4 - не «повторить существующий паттерн», а «спроектировать
жизненный цикл и доступность там, где их нет». Это надо признать в объёме.
Дополнительно два практических требования, которых в плане нет:

- Доступ к задаче проверяется по кэшированным `component_id`/`translation_id`/
  `user_id` (`weblate/api/views.py:4889-4909`). Задача в scope Project не имеет
  ни одного из этих ключей, поэтому без явной стратегии метаданных flash будет
  опрашивать 404.
- Кнопки прерывания у общего flash нет, но у другого виджета есть
  (`weblate/templates/component-progress.html:40-41`,
  `loader-bootstrap.js:1704-1718`). Новая задача не должна случайно попасть в
  этот путь.

### F8 (P1) - i18n: часть строк обязана жить в `djangojs.po`

Task 6 (351-357) отправляет все новые строки в `django.po`. Но любые строки,
которые появятся в `loader-bootstrap.js` (прогресс, итог, объявления для
скрин-ридера), обслуживаются `JavaScriptCatalog` (`weblate/urls.py:942`) и
должны быть в `djangojs.po`; в `django.po` они скомпилируются, но в интерфейс
не попадут.

Второе: дубль `msgid` при одинаковом `msgctxt` - фатальная ошибка
`compilemessages`, то есть неподнимаемый production-образ. Кандидаты на
коллизию уже есть в `weblate/locale/ru/LC_MESSAGES/django.po`: `Fix string`
(:17484), `Cancel` (:17893), `Scope` (:3375), `Language` (:3664 и
контекстный :11948), `Browse` (:11350), `Failed` (:13539), `Completed`
(:13756), `Review` (контекстные :4176, :25841), `Check` (:6369). Правило для
плана: переиспользовать существующие записи либо вводить `msgctxt`, и прогонять
`compilemessages --locale ru` после каждого слияния, затрагивающего каталог.

### F9 (P1) - Threat model не обновляется

План добавляет аутентифицированный POST-маршрут, который массово мутирует
содержимое переводов и ставит фоновую задачу. `AGENTS.md` требует сверяться с
`docs/security/threat-model.rst` при изменении публичных эндпоинтов и
прав/мутаций, а сам документ (`docs/security/threat-model.rst:1038-1048`)
называет условия ревизии. В Task 6 обновления threat model нет. Нужно добавить:
границы радиуса действия, оба права, CSRF, отсутствие undo, поведение очереди
и лимиты.

### F10 (P1) - Инструкция по тестам неверна

Строки 104-109 обещают, что чековые тесты идут на хосте «без БД».
`weblate/checks/tests/test_chars_checks.py` действительно `SimpleTestCase`, но
`weblate/checks/tests/test_source_checks.py` импортирует `django.test.TestCase`
и содержит `FixtureTestCase`/`FixtureComponentTestCase` (в частности класс
`MultipleFailingCheckTestCase`), то есть требует настроенный PostgreSQL и
`collectstatic`. Поскольку `ellipsis` - source-чек, Task 1 без БД не
проверяется. Инструкцию надо привести к реальности либо перенести чистые тесты
фикса в DB-free файл.

### F12 (P2) - Обещание «пары кликов» не выполняется на реальных данных

Предпросмотр работает по одному `check_id` и по 250 применимых строк за проход.
Для `anvil-saga/locale_v1-02-import-explained-3/en` (снято с UI: `end_stop`
470, `end_exclamation` 342, `end_question` 150, `end_interrobang` 24,
`end_colon` 1) это минимум **семь** review-проходов, не считая manual и stale.
Раздел Goal стоит переписать честно: safe-tier - действительно два
подтверждённых клика, review-tier - конвейер разбора порциями. Иначе приёмка
разойдётся с ожиданием заказчика.

## Пропущенные соображения

1. **Глоссарные компоненты.** `run_checks` для глоссария запускает только
   `CHECKS.glossary` (`weblate/trans/models/unit.py:2181-2183`). Движок должен
   явно исключать глоссарные компоненты, иначе пересчёт после правки поведёт
   себя иначе, чем отбор.
2. **`propagates = "repeat"` и соседи.** `repeat-drift` пересчитывает соседей
   группы в той же транзакции. Массовая правка внутри одного компонента может
   каскадно пересчитывать те же группы многократно; нужен либо пропуск, либо
   измерение.
3. **Advisory-чеки.** Ранее принято, что advisory (в частности глоссарная
   морфология) не утверждает необходимость правки. Плану нужна строка о том,
   что advisory-чек не может получить `mass_fixup` никогда.
4. **Идемпотентность повторного запуска после автофиксов.** Если и `fix_target`
   на записи, и движок чинят один дефект, повторный прогон обязан давать ноль
   изменений. Тест на это в плане есть только внутри движка, но не через
   границу с `AUTOFIX_LIST`.
5. **Rate limiting.** Новый эндпоинт запускает фоновую работу по всему проекту.
   Ограничение частоты и защита от параллельных прогонов одного scope не
   описаны.

## Рекомендуемый путь

1. Исправить F1 (значение действия) - однострочное, но блокирующее.
2. Закрыть F2 решением о владении дефектами. Если выбран вариант 1, объём Task
   1 и Task 5 сокращается примерно вдвое, и safe-tier из UI уходит.
3. Снять измерение до разработки: для одного реального компонента посчитать,
   сколько строк каждого терминального чека попадает в `eligible`, а сколько в
   `manual` из-за конфликтующего знака и пересечения чеков (F3). Результат -
   в `docs/product/measurements/`. Если доля manual высока, review-tier в
   текущем виде не нужен.
4. Ответить на вопрос цены Task 3 (F4). Наиболее вероятный исход - вынести
   source-side `ellipsis` из плана целиком и починить его на входе.
5. Дописать решение по судье (F5) как отдельный пункт Task 2 и как счётчик в
   результате задачи.
6. Привести Task 4 к реальности (F7), Task 6 - к правильным каталогам и
   threat model (F8, F9), Test commands - к фактическим базовым классам (F10).
7. Обновить строчные ссылки (F11) и формулировку цели (F12).

Первые три пункта - именно те, которые меняют объём. Остальное - точность.
