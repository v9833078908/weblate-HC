3941 юнит с непрерывными id 177675-181615 и тот же шаг выборки 26, то есть
логика отбора идентична, но тождество выборки этим хэшем через две базы не
выражается. Ни один прод-идентификатор в репозитории не записан, поэтому
расхождение неразрешимо офлайн.

### Что и на чём мерялось

Золотой набор `col4-judge-golden.json`, 919 записей. Использованы

**Сплит `test` (433 записи) не тронут.** Ни один прогон его не читал;

go/no-go прогон по нему остаётся впереди и требует отдельного решения.

Контракт запроса: строгий structured output (`strict: true`), корень
схемы — объект `{segments: [{id, errors: [{span, category, severity}],
verdict}]}`, `provider.require_parameters: true`, батч 10, concurrency 4.
Вердикт выводится из максимальной severity в коде, а не берётся из поля
`verdict` модели — инвариант 4 архитектуры; расхождение между двумя
считается отдельным счётчиком и оказалось пренебрежимым (0 у
deepseek/haiku/command-a/gpt-5.4-mini, 1 у qwen, 8 у sonnet-5).

Неразобранный или неполный ответ считается сбоем транспорта, никогда не
вердиктом: один ретрай, затем запись помечается `unparsed` и не попадает
ни в flag, ни в reject.

### Пробник схемы: `temperature` несовместим с `require_parameters`

Первый прогон пробника отсеял три модели из семи с HTTP 404 `No endpoints
found that can handle the requested parameters`. Изоляция параметра по
матрице из четырёх вариантов дала однозначный ответ:

| Модель | schema+require+temp | schema+require | schema+temp | schema |
|---|---|---|---|---|
| `claude-sonnet-5` | **404** | OK | OK | OK |
| `gpt-5.4-mini` | **404** | OK | OK | OK |
| `gpt-5.4-nano` | **404** | OK | OK | OK |
| `claude-haiku-4.5` | OK | OK | OK | OK |

Reasoning-тиры не декларируют поддержку `temperature`, и при
`require_parameters: true` роутер не находит эндпоинта. `temperature`
убран из payload: гарантия соблюдения схемы (урок Cathedral — 19.6%
потерянных вердиктов на свободном тексте) важнее номинального нуля
температуры, который reasoning-модели всё равно игнорируют. Цена решения:
прогоны не побитово воспроизводимы между провайдерами.

После правки все семь моделей приняли payload. Это ровно тот класс
отказов, который в `col4-model-eval.json` в прошлый раз стоил исключения
`gpt-5-mini` и `claude-haiku-4.5` из сравнения; пробник за $0.02 закрыл
вопрос до траты на калибровку.

### Почему каскад проигрывает: механизм измерен, а не предположен

Дизайн исходил из того, что ступень A настраивается агрессивно, а ложные
тревоги снимает ступень B. Замер показывает, что первой посылки нет:
**ступень A почти не даёт ложных тревог, которые стоило бы снимать.**
Специфичность `deepseek` как ступени A — 97.6-99.2%. Соответственно
почти всё, что ступень B переголосовывает, — настоящие дефекты:

| Плечо | переголосовано | из них верно | **из них ошибочно** |
|---|---|---|---|
| cascade `deepseek` → `sonnet-5` | 48 | 2 | **46** |
| cascade `deepseek` → `qwen` | 21 | 3 | **18** |
| mirror `sonnet-5` → `deepseek` | 5 | 2 | **3** |
| mirror `qwen` → `deepseek` | 24 | 16 | 8 |

Это не свойство конкретной пары, а арифметика конструкции: если ступень B
имеет право снимать флаг, сквозной recall равен
`recall(A) × recall(B | эскалированные)` и не может превысить recall
ступени A. Каскад окупается только тогда, когда узкое место — ложные
тревоги. Здесь узкое место — пропуски, и вторая ступень их усугубляет.

Единственная конфигурация, где ступень B переголосовывает больше верно,
чем ошибочно (`qwen` → `deepseek`, 16 против 8), — это та, где сильная
модель стоит второй и фактически перепроверяет слабую. Но и она даёт
recall 87.1 против 94.0 у той же сильной модели, поставленной одной.

Отдельно стоит отметить, что каскад не бесполезен: он покупает
специфичность 98.4-100% и **нулевой ложный critical** во всех четырёх
конфигурациях. Если бы поставку блокировал ложный reject, а не пропуск,
выбор был бы обратным. Дизайн явно говорит, что это не так: ложный
critical — дефект поставки, но пропущенный дефект — то, ради чего судья
заводится.

### Объединение вердиктов, восстановленное из уже оплаченных плеч

Если понижающая ступень B вредна, напрашивается противоположная
конструкция: обе модели судят все строки, вердикт — максимум severity.
Такая схема не может уронить recall по построению. Отдельного прогона
под неё не было, но её и не нужно покупать заново: ступень B в каждом
плече пересуживает флаги другой модели, то есть ровно те записи, по
которым считается пересечение.

| Величина | Источник | Значение |
|---|---|---|
| дефектов в сплите | золотой набор | 232 |
| помечено `deepseek` | `cascade-ds-qwen`, ступень A | 215 (92.7%) |
| помечено `qwen` | `mirror-ds-qwen`, ступень A | 210 (90.5%) |
| дефектов «только `deepseek`» | `cascade.tier_b.overturned_wrongly` | 18 |
| дефектов «только `qwen`» | `mirror.tier_b.overturned_wrongly` | 8 |
| чистых во флаге у `deepseek` | `cascade`, эскалация минус дефекты | 6 из 251 |
| чистых во флаге у `qwen` | `mirror`, эскалация минус дефекты | 20 из 251 |

Объединение считается с двух сторон и даёт `215 + 8 = 223` либо
`210 + 18 = 228` дефектов из 232.

| | `deepseek` один | объединение |
|---|---|---|
| recall H | 94.0 | **96.1-98.3** |
| специфичность H | 96.8 | **90.8-91.2** |
| чистых строк во флаге, из 251 | 6 | 22-23 |
| auto-pass на прод-пуле | 80.3% | **74.9-75.0%** |
| пропуск среди auto-pass | 1.36% | **0.41-0.95%** |
| цена полного COL4 fr | $1.12 | $1.30 |

Без единого допущения границы объединения были бы [92.7%, 100%];
реконструкция сужает их вчетверо.

**Вывод не в пользу объединения по умолчанию.** Оно снижает пропуск
втрое, но уводит на разбор ещё пять пунктов строк, а цель плана по
auto-pass (≥90%) не выполняется и при 80.3%. То есть схема улучшает
метрику безопасности и ухудшает продуктовую; это выбор владельца
продукта, а не инженерный. Ложные тревоги объединения почти целиком —
вклад `qwen`: 20 чистых строк во флаге против 6 у `deepseek`.

**Чего эта реконструкция не заменяет.** У неё есть систематический изъян,
который не виден по внутренней сверке. Ступень B судила батчи, целиком
набранные из эскалированного подмножества, то есть примерно на 95%
дефектные, а композиция батча влияет на поведение модели. Сверка
пересечения (197 против 202 по дефектам, 3 против 4 по чистым, то есть
около 2% расхождения) ограничивает **шум**, но не смещение: оба плеча
делят один и тот же изъян и промахнулись бы согласованно. Прогон обеих
моделей как ступени A по полному смешанному сплиту с дампом построчных
вердиктов (~$0.16 и правка скрипта: сейчас сохраняются только агрегаты)
снимает конфаунд и позволяет проверить разницу тестом Макнемара.

### Смешанный сплит: объединение измерено напрямую

Реконструкция выше опиралась на допущение, что ступень B в батче из
одних эскалированных записей ведёт себя как ступень A в смешанном. Чтобы
снять допущение, обе модели прогнаны как ступень A по одному и тому же
train+dev с дампом построчных вердиктов (артефакт
`col4-judge-union-traindev.json`, $0.32).

| | предсказано реконструкцией | измерено |
|---|---|---|
| union recall | 96.1-98.3% | **97.8%** |
| union специфичность | 90.8-91.2% | **91.6%** |

Реконструкция попала по recall и была на 0.4 пункта пессимистична по
специфичности. Метод годен; допущение вреда не нанесло.

Заодно измерено то, чего реконструкция дать не могла: тест Макнемара по
границе H. На train+dev `deepseek` обходит `qwen` на 35 записях против
11 в обратную сторону, p = 0.0005 — различие значимо. Это станет важно
через один раздел.

### Запечатанный test: единственный прогон

Прогон сделан один раз, обе конечные точки объявлены заранее: первичная
— одиночный `deepseek/deepseek-v4-pro`, вторичная — объединение
`deepseek` и `qwen`. Итераций после прогона не было и не будет.
Состав: 433 записи, 167 чистых, 146 major, 120 critical. Артефакт —
`col4-judge-SEALED-test.json`, $0.34.

| | recall H | спец. H | recall R | critical -> pass | major -> pass | ложный flag | терминология |
|---|---|---|---|---|---|---|---|
| `deepseek` один | 90.6 [86.5, 93.6] | **98.2** [94.9, 99.4] | 95.0 [89.5, 97.7] | **3 из 120** | 22 из 146 | **1.8%** | 97.4 |
| `qwen` один | 92.1 [88.2, 94.8] | 89.8 [84.3, 93.5] | 97.5 [92.9, 99.1] | 0 из 120 | 21 из 146 | 10.2% | 84.4 |
| объединение | **97.4** [94.7, 98.7] | 88.6 [82.9, 92.6] | **98.3** [94.1, 99.7] | **0 из 120** | **7 из 146** | 11.4% | **98.7** |

**Отбор модели на train+dev не подтвердился.** Сравнение тех же двух
моделей на данных, которых они не видели:

| | train+dev | test |
|---|---|---|
| `deepseek` recall H | 94.8 | **90.6** |
| `qwen` recall H | 87.9 | **92.1** |
| Макнемар | b=35, c=11, **p = 0.0005** | b=30, c=20, **p = 0.20** |

На отборочных данных `deepseek` превосходил `qwen` значимо; на
запечатанных они статистически неразличимы, и по recall `qwen`
формально впереди. Часть преимущества, за которое `deepseek` был выбран,
оказалась шумом отбора из семи кандидатов — ровно тот эффект, ради
обнаружения которого сплит и запечатывали. Падение recall 94.8 -> 90.6
измеряет цену выбора.

**Решающее различие лежит не там, где его искали.** Обе модели
сопоставимы по границе H, но по релизному гейту расходятся: `deepseek`
пропускает **3 critical из 120** в auto-pass, `qwen` — ни одного, и
объединение — ни одного. По дизайну critical удерживает строку от
сборки, поэтому пропущенный critical — не промах метрики, а строка,
которая уедет в игру сломанной.

Ошибки моделей в существенной мере не пересекаются: помечено обеими 228,
только `deepseek` 16, только `qwen` 34. Именно поэтому объединение
поднимает recall до 97.4% — две разные посредственности перекрывают
друг друга лучше, чем одна хорошая модель перекрывает себя.

### Цель auto-pass >= 90% арифметически недостижима

Порог, записанный в план, противоречит собственному замеру B0. При доле
дефектов 18.2% даже безошибочный судья оставит в auto-pass ровно чистые
строки, то есть 81.8%. Чтобы получить 90%, судья обязан пропустить
часть дефектов:

| Судья | recall H | спец. H | auto-pass | пропуск среди auto-pass |
|---|---|---|---|---|
| безошибочный | 100 | 100 | **81.8%** | 0 |
| `deepseek` | 90.6 | 98.2 | 82.0% | 2.09% |
| `qwen` | 92.1 | 89.8 | 74.9% | 1.92% |
| объединение | 97.4 | 88.6 | 72.9% | **0.65%** |

Формально: auto-pass >= 90% при p = 0.182 требует recall <= 54.9%, то
есть судью, который **пропускает 45% дефектов**. Цель надо переписать —
либо как «доля разбора <= X% сверх неустранимых 18.2%», либо как прямой
бюджет времени продюсера. В нынешнем виде она поощряет ровно то
поведение, против которого построена вся конструкция.

Обратите внимание на строку `deepseek`: его auto-pass 82.0% **выше**
теоретического потолка безошибочного судьи. Это не парадокс, а признак
пропусков: он отправляет в auto-pass чистые строки плюс 9.4% дефектов.

### Пороги плана против измеренного на запечатанном test

Это и есть go/no-go. Числа взяты с запечатанного test, n = 433
(167 чистых, 146 major, 120 critical), первичный кандидат — одиночный
`deepseek/deepseek-v4-pro`, в скобках рядом — объединение.

| Порог плана | Требование | `deepseek` один | объединение | Статус |
|---|---|---|---|---|
| reject-recall на critical | ≥95%, нижняя граница CI ≥88% | 95.0 [89.5, 97.7] | 98.3 [94.1, 99.7] | **пройден обоими**, у `deepseek` впритык |
| (flag ∪ reject)-recall на терминологии | ≥80% | 97.4 [91.0, 99.3] | 98.7 | **пройден обоими** |
| false-flag на чистых | ≤10% | 1.8% [≤5.1] | 11.4% | `deepseek` пройден, объединение **не пройдено** |
| false-reject / false-critical на чистых | ≤2% | 0 из 167, верхняя граница CI 2.2% | 0 из 167, та же граница | **не сертифицируем ни для кого** |
| critical в auto-pass | ~0 | **3 из 120** | **0 из 120** | `deepseek` **не пройден**, объединение пройдено |
| auto-pass | ≥90% | 82.0% | 72.9% | **не пройден никем и не может быть**, см. раздел выше |
| miss-rate среди auto-pass | major ≤1-2% | 2.09% [1.33, 2.88] | 0.65% [0.19, 1.18] | `deepseek` на границе, объединение пройдено |

Три оговорки, без которых таблицу читать нельзя.

**Ни один кандидат не проходит всё.** `deepseek` роняет релизный гейт
(3 critical уходят в сборку), объединение роняет порог ложных флагов
(11.4% против 10%). Разница в цене ошибки несимметрична: ложный флаг
стоит внимания продюсера, потому что по дизайну `flag` даёт state 20 и
строка **всё равно отгружается**; пропущенный critical стоит сломанной
строки в игре. Порог, который защищает поставку, весит больше порога,
который защищает внимание.

**Про auto-pass.** Разрыв не закрывается судьёй: при доле дефектов
18.2% потолок безошибочного судьи — 81.8%. Цель ≥90% несовместима с
корпусом и подлежит переписыванию, а не достижению.

**Про порог false-reject.** Ограничение по мощности из B1
подтвердилось и на test: 167 чистых строк не хватает, чтобы
сертифицировать «≤2%» интервалом даже при **нуле** ложных reject —
верхняя граница Wilson 2.2%. Порог требует пересмотра либо чистой
страты не меньше 189 строк.

### Рекомендация

1. **Судить двумя моделями сразу: `deepseek/deepseek-v4-pro` и
   `qwen/qwen3-235b-a22b-2507`, вердикт — максимум severity.** На
   запечатанном test это единственный кандидат, который закрывает
   релизный гейт: 0 critical из 120 в auto-pass против 3 у `deepseek`
   одного, recall 97.4% против 90.6%, пропуск среди auto-pass 0.65%
   против 2.09%. Оба семейства отличны от переводчика
   (`google/gemini-2.5-flash`), инвариант 3 соблюдён.
2. **Второй судья стоит 5% бюджета первого.** `qwen` — $0.042 на 1000
   строк против $0.62-0.75 у `deepseek` (разброс от reasoning-токенов
   между прогонами). Полный COL4 fr: `deepseek` $2.4-3.0, плюс `qwen`
   $0.17. За эти семнадцать центов покупается +6.8 пункта recall и
   закрытый релизный гейт — лучшая покупка во всём замере.
3. **Не выбирать одну модель по train+dev.** Отбор давал `deepseek`
   значимое преимущество (p = 0.0005); на запечатанных данных различие
   исчезло (p = 0.20), а по recall вперёд вышел `qwen`. Если по каким-то
   причинам нужен ровно один судья, у `qwen` при вдвадцатеро меньшей цене
   нулевой пропуск critical, но ложный флаг 10.2% и терминология 84.4
   против 97.4 — то есть выбор между «дешевле и безопаснее» и «точнее по
   терминологии», а не между лучшим и худшим.
4. **Ступень B в дизайновом виде — с правом снимать флаг — не добавлять
   ни при каком выборе моделей.** Замер каскадов однозначен: она снимает
   дефекты, а не шум.
5. **Порог auto-pass ≥90% переписать** — при доле дефектов 18.2% он
   требует судьи, пропускающего 45% дефектов. Осмысленная замена —
   бюджет разбора сверх неустранимых 18.2% либо прямой лимит времени
   продюсера.
6. **Порог false-reject ≤2% переписать или расширить чистую страту**:
   167 чистых строк не дают сертифицировать его даже при нуле ошибок.
7. **Test израсходован.** Обе конечные точки объявлены до прогона и
   измерены один раз. Любое существенное изменение промпта или состава
   судей требует нового среза, а не повторного чтения этого.

## Трек C. Дрейф не-глоссарных повторов

Прогон: `docs/misc/col4-repeat-drift-probe.py` на `col4/data/fr`
dev-зеркала, 3941 юнит, 153 глоссарных термина исключены. Read-only, без
LLM-вызовов, $0. Полный результат — `docs/misc/col4-repeat-drift.json`.

Пробник меряет двумя слоями, потому что они неравно достоверны.

### Слой A: одинаковые источники — факт

146 групп юнитов с идентичным нормализованным источником, 372 юнита
(9.4% корпуса).

| Показатель | Значение |
|---|---|
| групп | 146 |
| расходятся, raw | 106 (72.6%) |
| расходятся, после нормализации | 84 (**57.5%**) |
| юнитов в расходящихся группах | 215 |
| **видит стоковый чек `inconsistent`** | **0 (0.0%)** |
| групп, где хотя бы два юнита делят context | 0 |

Нормализация (casefold, trim, схлопывание пробелов, снятие финальной
пунктуации) снимает 22 группы из 106 — то есть пятая часть «дрейфа» была
косметикой, которую слой 0 убирает бесплатно, а четыре пятых — нет.

Примеры расхождений: `промолчать` (9 юнитов) → `garder le silence` /
`laisser la parole` / `ne rien dire` / `se taire`; `лежать и не
шевелиться` (3) → `rester allongé sans bouger` / `rester immobile`. Это
кнопки ответа в диалогах: четыре разных перевода одной кнопки — то, что
игрок видит как несогласованность.

### Посылка плана про `inconsistent` оказалась неверной

План трека C исходил из того, что «детекцию закрывает стоковый чек
`inconsistent`». Он не закрывает ничего: ноль из 84 расходящихся групп
им помечены. Причина структурная и проверяема по коду —
`Unit.objects.same()` (`weblate/trans/models/unit.py:380-388`) фильтрует
по **source И context**:

```text
result = self.filter(
    source__lower__md5=MD5(Lower(Value(unit.source))),
    context__lower__md5=MD5(Lower(Value(unit.context))),
    ...
)
```

В ключевом игровом формате у каждого юнита свой msgctxt, поэтому
`propagated_units` для внутрикомпонентных повторов всегда пусто. Это не
ошибка конфигурации и не следствие `allow_translation_propagation`:
проверено отдельно, ни в одной из 84 групп два юнита не делят context.

### Слой B: повторяющиеся подфразы — прокси

У подфразы внутри предложения нет выравнивания на целевой стороне,
поэтому «одинаково переведена» решается прокси: группа согласована, если
некоторая подстрока длиной `ratio × len(фразы)` встречается во всех
таргетах группы. Репортится при двух порогах, потому что число заметно
двигается с порогом.

5253 максимальные группы (из 9223 кандидатов после снятия вложенных
фраз с тем же следом). Разбито на страты, иначе одно число утонуло бы в
обычной лексике:

| Страта | групп | raw @0.5 | норм. @0.5 | raw @0.75 | норм. @0.75 |
|---|---|---|---|---|---|
| многословные фразы | 2627 | 13.1% | 11.8% | 32.3% | 31.0% |
| одиночные имена собственные | 26 | 23.1% | **19.2%** | 38.5% | 26.9% |
| одиночная общая лексика | 2600 | 27.6% | 25.7% | 41.6% | 39.1% |

Страта общей лексики приведена, чтобы её шум был виден, а не подмешан в
заголовок: `даже` встречается в 49 юнитах и не имеет канонического
французского перевода — считать это дрейфом значит измерять русский
язык, а не наш конвейер.

Страта имён собственных мала (26 групп) именно потому, что реалии в
основном уже в глоссарии и исключены из группировки. Оставшийся хвост —
то, что глоссарий не покрывает, и он воспроизводит доминирующий класс
дефекта, найденный B0:

- `чествование` (5 юнитов) → `défilé des bannières des ménages` /
  `cérémonie des drapeaux de maison` / `célébration des bannissements de
  la faction`
- `хриплого` (5) → `hriplog` / `hriplogo`
- `гнилушку` (3) → `l'écume` / `la pourriture` / `le pourri`

Отдельная методическая заметка: первая версия пробника относила к именам
собственным любой токен, встреченный с заглавной буквы вне начала
предложения, и страта протекла до 102 групп за счёт ALL-CAPS-заголовков
(`лаборатории`, `парень`). Признак заменён на долю титульных вхождений
(≥2 и ≥60% от всех), после чего страта сжалась до 26 честных групп.

### Вывод трека C

**Дрейф материален и не детектируется.** По правилу плана («дрейф
материален → рантайм-канон встаёт в фазу 2/4 отдельным дизайном») трек C
закрывается не «замером в ноль», а постановкой задачи. При этом дизайн
должен решать две разные проблемы, а не одну:

1. **Детекция.** 57.5% групп с идентичным источником переведены
   по-разному, и ни одна не видна ни в интерфейсе, ни в статистике.
   Самый дешёвый шаг здесь — не рантайм-канон, а чек, который сравнивает
   юниты с одинаковым источником **внутри компонента, игнорируя
   context**. Это ровно тот запрос, который `Unit.objects.same()` уже
   умеет строить, минус одно условие.
2. **Предотвращение.** Рантайм-канон first_mentions по образцу правки
   10.1 Cathedral. Порядок батчей и concurrency ломают семантику канона,
   поэтому его надо проектировать, а не копировать.

Первое дешевле второго на порядок и даёт цифру, по которой второе можно
будет оценить.
