# План: соседние реплики диалога в контексте судьи (плечо H2)

Дата: 2026-08-20. Статус: ожидает одобрения.

Правка дизайн-дока: `2026-08-13-judge-native-ui-design.md`, поправка
2026-08-20 в разделе «Что показываем принципиально». Этот план — её
исполнение. Ничего из нижеследующего не делается до одобрения.

## Что установлено до плана

- Сегмент судьи не содержит соседних реплик: `_segment()`
  (`weblate/trans/judge.py`) кладёт `id, key, source, target, rendered_*,
  note, glossary, checks` — и ничего о соседях. `compute_context_hash`
  (`weblate/trans/models/judge.py`) хеширует `source + note +
  glossary_terms` — правка соседней строки не протухляет вердикт.
- Сегменты идут по `JUDGE_BATCH_SIZE = 5`, но батч — транспортная
  единица, модель не уведомлена, что строки последовательны; на границах
  батчей контекст исчезает в принципе.
- Наблюдённые промахи класса «изолированный сегмент» (аудит
  heart-abyss/hub-1, `misc/heart-abyss-hub-1-translation-qa.md`):
  - `hub1_ramen_1_13`: RU «Нам нужно где-то остановиться.» → FR «nous
    arrêter quelque part» — «притормозить» вместо «снять комнату»;
    нужный смысл задаёт хвост сцены (`hub1_ramen_1_18`: «Нам нужна
    комната на несколько дней»), до которого 5 реплик, и соседние
    реплики `1_12`/`1_14` его тоже не дают. Судья флагал корректный
    перевод из-за изоляции.
  - `hub1_teahouse_1_11`: обрывок фразы («Чем ты дойдёшь до соседней
    улицы.»), чей смысл даёт предыдущая реплика `hub1_teahouse_1_10`
    («...захочет сдать за награду раньше...»); судья не видел начало
    фразы.
- Методология замера на месте: корпус — запечатанный срез S&T2
  summer-update ru→zh_Hans, 124 юнита (`docs/misc/st2-zh-units.jsonl`),
  ground truth `st2-zh-groundtruth.json` (7 critical, 24 major+, 83
  чистых), драйвер `docs/misc/st2-zh-recalibration.py` со сменными
  плечами (A–I), скорер `st2-zh-score.py`, 2 модели × 5 повторов,
  медиана. Продовое плечо — H (базовый промпт + `{project_context}`),
  измерен и принят (`docs/misc/2026-08-20-judge-prompt-universalization-run.md`).

## Границы

### Входит

- Плечо H2 в драйвере: то же, что H, плюс в каждый сегмент payload'а
  добавляется `context: {prev_source, next_source}` (source-строки
  непосредственных соседей по `position` в той же translation) и одна
  строка в промпт о назначении поля.
- Сравнение H2 против H на том же корпусе, моделях, повторах; те же
  гейты (D6), что и в универсализации: `missed_crit = 0` в каждом
  прогоне, `REAL@14`/`REAL@24` не ниже H, `FP` не выше H, шум не выше.
- Прод-код (задачи 4–6): `JudgeRequest` получает поля соседей, `_segment`
  их сериализует, `compute_context_hash` включает их в digest, строка в
  `verdict.txt` — в блоке, где описаны `glossary` и `checks` как
  справочный материал.

### Не входит

- Соседние target: отдельная гипотеза (судья может начать копировать
  соседний перевод или флагать его дефекты). Не входит в этот срез.
- Пересуд по правке соседа (инвалидация кэша вердиктов при изменении
  соседней строки): механика `context_hash` уже обеспечит протухание —
  после включения соседей в hash правка соседней строки делает старый
  вердикт «протухшим» автоматически. Отдельный UI для «пересудить из-за
  соседа» не нужен.
- Кросс-компонентный контекст, контекст из VCS-истории, speaker labels:
  не входило в постановку и не входит сейчас.
- Смена batch size, порядка сегментов в батче (луч 3.6 best-practices —
  отдельный эксперимент).
- Динамическое расширение контекста (окно k>1): если H2 провалит гейты,
  расширение окна не делается, дыра остаётся задокументированной.

### Гипотеза и её честная цена

`prev_source/next_source` дают судье минимум дискурс-контекста для
диалоговых сцен. Анекдоты мотивируют класс проблемы, но не гарантируют
эффект окна: `teahouse_1_11` окно ±1 закрывает (смысл — в предыдущем
юните), `ramen_1_13` — нет (смысл — в `1_18`, пять реплик дальше).
Ожидание от замера поэтому скромное: окно ±1 должно снять часть ложных
срабатываний на обрывках фраз и **не добавить** шум на строках, где
сосед нерелевантен (UI-строки, разные спикеры в подряд идущих ключах).
Именно поэтому гейты G4-G5 (FP и шум не выше H) — равноправная часть
решения, а не дополнительный фильтр.

Стоимость: +2 source-строки на сегмент, ~+30–40% входных токенов на
сегмент (оценка на материале hub-1: средняя длина реплики ~40 символов,
2 соседа ≈ +80 симв. на сегмент ~ 40–60 токенов), плюс строка промпта.
Батч из 5 сегментов вырастает с ~25 строк текста до ~35. При
положительном решении платим всегда, включая UI-компоненты, где поле
чаще всего бесполезно: дифференциация «контекст только для диалоговых
компонентов» не входит в этот срез (нет метрики «диалоговости»), окно
едет одинаково для всех.

### Точка отсечения в коде

Сосед определяется по `Unit.position` в той же `Translation` (сосед =
position ± 1). Это окно в 1 юнит с каждой стороны, всегда, для всех
компонентов. Известное следствие: на монолингвальных компонентах порядок
`position` присваивается при парсинге файла и может не совпадать с
порядком диалога в сцене. Риск зафиксирован, но не блокирует: на
heart-abyss/hub-1 (po-mono) position-порядок и порядок реплик в файле
совпадают по построению (parser хранит порядок файла). Если замер
покажет, что соседи по position не помогают (диалог в корпусе S&T2
последователен), расширение окна или поиск соседей по ключу - отдельная
гипотеза, не входящая в этот план.

## Решения

| # | Решение | Альтернатива | Почему так |
|---|---|---|---|
| D1 | Контекст - поле сегмента `context: {prev_source, next_source}`, а не порядок батчей | отсортировать юниты по position и уведомить модель, что это диалог | Контекст появляется/исчезает на границах батчей по `JUDGE_BATCH_SIZE = 5`, неизмерим, противоречит стойке 3.6 best-practices (сегменты независимы, отвечаются по `id`) |
| D2 | Только source соседей | source + target соседей | Соседний target - отдельная гипотеза: судья может начать копировать соседний перевод или флагать его дефекты; не входит в этот срез |
| D3 | `compute_context_hash` включает `prev_source`/`next_source` | отдельный neighbor-hash | Правка соседней строки должна протухлять вердикт - тот же класс протухания, под который hash проектировался; отдельный hash удваивает сущности |
| D4 | Окно = 1 сосед с каждой стороны | k>1 | Минимум дискурс-контекста; расширение - отдельная гипотеза, если H2 провалит гейты |
| D5 | Гейты H2 против H, не против D | гейты против D | H - измеренное и принятое плечо, которое едет в прод; сравнение с ним честнее, чем с историческим D |

## Задача 1. Плечо H2 в драйвере

`docs/misc/st2-zh-recalibration.py`.

### Step 1: Соседи в корпусе

Корпус `docs/misc/st2-zh-units.jsonl` читается как упорядоченный список:
`prev_source = units[i-1].source` при `i > 0`, `next_source =
units[i+1].source` при `i < len-1`. Срез запечатан, файл не меняется -
соседи вычисляются на лету, отдельный файл не создаётся. Идентичность
соседей фиксируется тестом драйвера `--dry-run`: первый сегмент без
`prev_source`, последний без `next_source`, средний с обоими.

### Step 2: Payload и промпт плеча H2

Плечо H2 = H (базовый промпт + `{project_context}`) плюс:

- в сегмент payload'а добавляется `context` с ключами `prev_source` /
  `next_source`; ключ отсутствует, когда соседа нет (первый/последний
  сегмент), - как `note` и `glossary` в продовом `_segment()`;
- в промпт, в блок GLOSSARY, добавляется одна фраза: соседние реплики -
  справочный материал для связности, не текст для перевода и не источник
  ошибок.

### Step 3: Dry-run и коммит драйвера

`--arm H2 --dry-run` печатает payload с `context` и обновлённый промпт.
Коммит: `test(judge): add the dialog-context arm to the zh driver`.

## Задача 2. Прогон и гейты

### Step 1: Прогон

`--arm H2` двумя моделями × 5 повторов (те же `deepseek/deepseek-v4-pro`,
`qwen/qwen3-235b-a22b-2507`), файлы в `docs/misc/st2-zh-recal/`.

### Step 2: Гейты

Те же D6, что и в универсализации, против H:

| Гейт | Критерий |
|---|---|
| G1 | `missed_crit = 0` в каждом прогоне H2 |
| G2 | `REAL@14` (медиана) не ниже H минус шумовой пол (1) |
| G3 | `REAL@24` (медиана) H2 >= H |
| G4 | `FP` (медиана) H2 <= H |
| G5 | Шум >=flag (медиана) H2 <= H |

### Step 3: Отчёт и решение

Отчёт в `docs/misc/2026-08-20-judge-dialog-context-run.md`: таблица
H против H2 по пяти метрикам, по-прогонные `missed_crit`, вердикт по
каждому гейту. Гейты пройдены - задачи 3-5 в код. Провалены - дыра
остаётся задокументированной в дизайн-доке, код не меняется, находка
записывается как отклонённая гипотеза.

## Задача 3. `JudgeRequest` и продовый `_segment`

### Step 1: Падающий тест

`weblate/trans/tests/test_judge_client.py`: сегмент с соседями содержит
`context` с `prev_source`/`next_source`; сегмент без соседей (крайний
юнит) не содержит ключа вовсе.

### Step 2: Реализовать

`JudgeRequest` получает `prev_source: str = ""`, `next_source: str = ""`.
`_segment()` сериализует `context` только когда хотя бы одно поле
непустое; значение `""` не сериализуется. `judge_loop` заполняет поля из
`Unit.position` ± 1 в той же translation (`source` соседа, не target).

### Step 3: Тесты - PASS, затем мутация

Мутация: `_segment()` молча роняет `context` -> тест падает. Мутация:
`judge_loop` подставляет target соседа вместо source -> тест падает.

## Задача 4. Протухание

### Step 1: Падающий тест

`compute_context_hash(prev/next меняются) != compute_context_hash(старые
соседи)`; существующие тесты hash без соседей не меняются (пустые
соседи = те же значения, что до плана, чтобы старые вердикты в DB не
протухли массово на обновлении).

### Step 2: Реализовать

`compute_context_hash(*, source, note, glossary_terms, prev_source="",
next_source="")` - в digest идут только непустые значения, поэтому hash
без соседей байт-идентичен старому.

### Step 3: Тесты - PASS, затем мутация

Мутация: сосед исключён из digest -> тест падает.

## Задача 5. Промпт и документация

`docs/admin/config.rst` (новые env нет - параметров и нет, секция судьи
