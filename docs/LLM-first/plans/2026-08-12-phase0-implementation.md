## Почему этот план существует отдельно от дизайн-документа

Сверка дизайн-документа фазы 0 с кодом 2026-08-12 показала, что три
пункта, помеченные там как «не сделано», уже отгружены коммитами
`c26a967` и `0549923` (оба 2026-08-11, раньше самого статуса, но не
включены в него):

- **json_schema на пути OpenRouter** — `RoutedLLMTranslation.get_chat_payload`
  / `_reply_format` (`weblate_customization/src/weblate_customization/machinery.py`)
  уже безусловно прикладывает `response_format.json_schema`,
  фиксирующий число элементов ответа, плюс `provider.require_parameters`.
  Реализация отличается от дизайна задачи A1 в дизайн-документе: схема
  нестрогая (`strict` не установлен), корень схемы — массив, а не
  объект-конверт `{"translations": [...]}`. В коммите отмечено как
  «verified live on both routed models», но юнит-тестов не было
  (`weblate/machinery/tests.py` и `weblate_customization/tests/test_machinery.py`
  не содержали ни одного упоминания `reply_format`/`response_format`/
  `json_schema` до задачи 1 этого плана).
- **Few-shot только из подтверждённых примеров** — тот же коммит:
  `BaseLLMTranslation._filter_confirmed_examples`
  (`weblate/machinery/llm.py`) уже требует `state__gte=STATE_APPROVED`,
  если у перевода включено ревью, иначе — исключает примеры, чьё
  последнее изменение было автоматическим.
- **Инкрементальная запись `process_mt`** — `0549923`:
  `AutoTranslate.store_batch()` (`weblate/trans/autotranslate.py`)
  коммитит каждый полученный батч сразу; возобновляемость получается
  неявно через фильтр по `state` в следующем запросе.

Это меняет объём оставшейся работы трека A и метод замера A2; решение
по каждому пункту закреплено ниже.

## Задача 1. Тесты на существующий механизм json_schema (XS)

**Выполнена 2026-08-12.**

Файлы: `weblate_customization/tests/test_machinery.py`.

Решение: не переделывать механизм на strict+конверт (апгрейд
сознательно отложен), только закрыть тестами то, что уже отгружено.

- Батч из N строк -> в payload `response_format.json_schema.schema`
  с `minItems == maxItems == N`, и `payload["provider"]["require_parameters"] is True`.
- Батч из одной строки -> то же самое с N=1 (текущий код не делает
  для этого случая исключения).
- `OpenAITranslation`/`AzureOpenAITranslation` (не `RoutedLLMTranslation`)
  не получают ни `response_format`, ни `provider.require_parameters`.
- `_expected_reply_length` на не-JSON или JSON без списка `strings`
  возвращает `0`, и в этом случае `response_format`/`provider` в
  payload не добавляются.

Приёмка: `./rundev.sh test weblate_customization/tests/test_machinery.py`
— все тесты зелёные, включая новые.

## Задача 2. Свежий снимок A2 на текущем коде (S)

Файлы: без изменения кода; результат — новая запись в

Решение (замена исходного 4-плечевого baseline/schema A/B, который
невыполним без переключателя схемы в коде): разовый прогон текущего
кода через уже существующий харнесс, сравнение с уже записанными
числами вместо контролируемого сравнения плечей.

- Подтверждено 2026-08-12: `dev-docker/data/python/weblate_customization/`
  побайтово совпадает с `weblate_customization/src/weblate_customization/`
  (включая `c26a967`) — синхронизация перед прогоном не нужна.
- Прогон `docs/misc/col4-eval-harness.py` внутри `dev-docker-weblate-1`
  (`weblate shell -c ...`, тот же base64-паттерн, что в докстроке
  скрипта) на `col4/data/fr`, batch/concurrency по умолчанию (без
  `EVAL_BATCH_SIZE`/`EVAL_CONCURRENCY`, чтобы совпадать с историческими
  прогонами).
- Если fingerprint результата не совпадёт с историческим
  `4db4b89dfd4b` — прогон остановить и сообщить, а не форсировать
  сравнение: это будет значить, что dev-зеркало разошлось с выборкой,
  на которой посчитаны исторические числа.
- Результат дописывается в `col4-eval-baseline.json` как новая запись
  `after` с `_commit` (текущий HEAD) и явной пометкой
  `_environment: "dev-docker mirror"` — в отличие от исторических
  прогонов, которые шли на проде (`_comment` файла: «против
  production»). Это межсредовое, направленное свидетельство отсутствия
  регрессий, а не строгий контролируемый A/B: прод может быть на более
  старом коммите, отдельного решения на деплой не было.
- Критерии no-regression (из дизайн-документа, трек A2): coverage
  100%, ноль unparsed, `end_stop` в полосе базлайна 18-29, glossary
  100%, cost в пределах +/-10% (сравнение cost — informational при
  смене среды: набор токенов может отличаться, даже если fingerprint
  совпал по id и source).

Реальная трата ~$0.10 на OpenRouter — согласована в рамках этой задачи,
отдельного подтверждения перед запуском не требуется.

Приёмка: `EVAL_JSON` из прогона записан в `col4-eval-baseline.json`;
вывод содержит сравнение с числами `baseline`/`after` и явный вердикт

## Задача 3. Скрипт калибровки судей `col4-judge-eval.py` (M, только код)

Файлы: новый `docs/misc/col4-judge-eval.py`.

Реальный платный прогон (~$8-15; оценка сохранена: каскад вызывает тир B
только на эскалированном подмножестве, но добавляется зеркальное плечо, и
цифра зависит от доли эскалаций) в объём этой задачи **не входит** —
только код. Прогон ждёт отдельного подтверждения.

По дизайн-документу `docs/LLM-first/2026-08-13-judge-native-ui-design.md`
скрипт меряет **каскад** из двух судей, а не двух независимых судей:

- Автономный скрипт без Django-импортов; ключ OpenRouter — из
  переменной окружения.
- Джойн по `unit_id`: метки/сплиты из `docs/misc/col4-judge-golden.json`
  (919 записей), контекст (глоссарий, note, failing checks) —
  из `dev-docker/data/col4-b0-units.jsonl` (первая строка — общий
  глоссарий, следующие — по юниту: `unit_id`, `context`, `source`,
  `target`, `note`, `checks`, `gloss_terms`, `gloss_missing`).
- Два судьи через OpenRouter из разных семейств (Anthropic mid-tier +
  OpenAI mini-tier); точные ID моделей — из каталога на момент прогона,
  фиксируются в результате вместе с распределением ролей A/B по плечам.
- Каскад: судья A судит каждую запись сплита; судья B — только записи,
  которые A пометил flag или reject. Если B сказал pass, флаг A — ложная
  тревога и запись считается прошедшей. Итоговый вердикт записи — вердикт
  B, если B запускался, иначе вердикт A.
- Плечи (выбор из CLI): `cascade` (по умолчанию), `mirror` (та же пара,
  модели A и B поменяны местами), `single` (один судья, контрольное плечо).
- Structured output строгий (`strict: true`) у обоих тиров, корень схемы —
  объект `{errors: [{span, category, severity}], verdict}` (конверт,
  в отличие от A1, не нужен — желаемая форма ответа уже объект).
- Батч ~10 записей. Инвариант транспорта: неразобранный/пустой ответ —
  сбой, не вердикт: ретрай один раз, затем пропуск строки со счётчиком
  `unparsed`, никогда не превращается в flag/reject. Действует на обоих
  тирах.
- 3x-агрегация — только на flag/reject, не на pass; правило:
  мажоритарное голосование (>=2/3), при равенстве голосов — в сторону
  более строгого вердикта (reject > flag > pass). Держится в коде, но
  дефолтным путём больше не является: доступна только как опция
  контрольного плеча `single` — второе семейство субсумирует
  самосогласованность (та сбивает дисперсию, но не смещение).
- Метрики: confusion matrix по классам; сквозные TPR/TNR каскада (по
  итоговому вердикту) и пер-тирные на границах R («есть critical»:
  reject vs flag+pass) и H («нужен человек»: flag+reject vs pass) с
  Wilson 95% CI; **recall судьи A на границе H** (A — фильтр полноты,
  это его критичная метрика); **precision судьи B на эскалированном
  подмножестве A**; reject-recall на critical-мутациях; (flag или
  reject)-recall на глоссарных дефектах; false-reject и false-flag на
  чистых test-строках; **false-critical rate на чистых строках с
  Wilson 95% CI** — метрика первого класса: по гейту severity дизайна
  вердикт critical удерживает строку из сборки игры, поэтому ложный
  critical — дефект поставки (отсутствующая локализация), а не просто
  шум; цена на 1000 строк отдельно для тира A (все строки) и тира B
  (только эскалированное подмножество), латентность; auto-pass rate со
  скорректированным по Rogan-Gladen miss-rate (bootstrap CI).
- CLI с `--split`: `train,dev` — для итераций промпта; отдельный явный
  `--split test` — для единственного запечатанного прогона.
- Few-shot примеры промпта судьи — только из `train`.

Приёмка: скрипт запускается на маленьком локальном сабсете (2-3
записи, без реального API-вызова — через `--dry-run`/мок, если он
предусмотрен, либо через ревью кода) и не делает сетевых вызовов, пока
не передан реальный ключ; плечо (`cascade`/`mirror`/`single`)
выбирается из CLI без правки кода; структура вывода (счётчики, confusion
matrix, метрики, раздельная по тирам цена) соответствует списку выше.
